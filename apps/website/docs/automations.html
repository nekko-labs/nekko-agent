Automations

View as Markdown llms.txt

An automation is a workflow that runs on its own: on a schedule, when something happens in a connected app, or when you start it. They live in the Workflows tab. This page covers the ready-made ones, how you hear about their runs, and how to stop them all at once. For building your own step by step, see the Workflows tab's How workflows work strip; for running a repo's CI on your machine, see Local CI runner.

#Turn on a ready-made automation

Workflows → New workflow opens on a gallery. An empty Workflows tab shows the same cards.

Automation When it runs What it needs
Summarize my GitHub notifications every morning Weekdays at a time you pick GitHub connected, the gh CLI signed in, a default model
Review every PR I open Each new pull request in a repo you pick (checked every 2 minutes) GitHub connected, the gh CLI signed in, a default model
Nightly dependency check Every night at a time you pick A project folder, a default model
Daily digest of my Linear or Jira tickets Weekdays at a time you pick Linear or Jira connected, a default model

Each card marks what you already have. Click one to open its setup sheet:

  1. What it needs. Anything missing has a button: Connect opens Connectors, Choose a model opens Models. A template that runs in a project asks which folder.
  2. Its questions. A time of day, or a repository (owner/name) and, optionally, a GitHub username so only that person's PRs are reviewed.
  3. Notify me. Digests default to After every run; change it here or later in the editor.
  4. Turn on. The automation is created, enabled and armed. The toast says when it runs first.

Customize opens the same automation in the workflow editor instead, where you can change its steps, triggers and model before saving.

Every ready-made automation only reads: it summarizes or reviews, and never comments, posts, installs or changes anything. Results land in the run history (and a notification, if you asked for one).

#How a run went

Expand a workflow to see its runs. The selected run shows how long it took and when it started, then either:

  • Failed at "step": the step that failed, its error, and a Transcript button for that step's chat, or
  • Result: the last agent step's answer, which for a digest is the digest itself.

The history on the right lists the last ten runs with their status, duration, what started them, and the step a failed run stopped at.

#Notifications

Each workflow's Notify me setting decides when a finished run tells you:

  • When a run fails (the default, also for workflows made before this setting existed),
  • After every run, for digests, or
  • Never.

Clicking a notification opens the Workflows tab on that run. Notifications follow Settings → Notifications → Desktop notifications, and stay quiet while the Workflows tab is on screen. A run cut short because the app quit is reported as a failure the next time it starts.

Phone notifications for failed runs are not available yet.

#Pause all automations

The Pause all automations switch in the Workflows header is the kill switch:

  • schedules, pull request and push events, Slack messages, connector polls and webhooks start no runs, and scheduled tasks (from a chat's ⚡ Automate menu) wait;
  • whatever is running when you switch it on is stopped;
  • the Run button, a task's Run now and nekko-agent workflow run still work.

A schedule that came due while paused runs once when you resume. Events that arrived during the pause are skipped, not replayed. The setting is shared, so pausing from one window or the web edition pauses everywhere.
