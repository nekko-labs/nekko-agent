# Claude policy (2026-10-19)

**Why:** Anthropic's terms let a third-party app use Claude on the user's own API key or cloud account without restriction, but a Claude plan only through the user's own, unmodified Claude Code, and they do not clearly cover some features for third-party apps on a plan. Philip's direction: those features are built and tested now, stay off for plan users until Anthropic approves them, and can then be switched on by Nekko (a reviewed release or a signed policy). Revised 2026-10-28: a user who has Anthropic's approval themselves can also switch them on for their own install, behind a clear warning (below; decision [0031](../../docs/decisions/0031-a-user-with-anthropics-approval-can-turn-on-the-plan-features.md)). Design: obsurdian `projects/nekko-agent/features/claude-code-harness/prompt.md` ("Claude policy table").

**One table decides every Claude capability.** `CLAUDE_POLICY` (`packages/shared/src/claude-policy.ts`) maps each auth (`api_key`, `cloud`, `subscription`, `unknown`) and capability (`interactive_chat`, `phone_remote`, `unattended_runs`, `nekko_tools`, `context_note`, `usage_limits`, `cost_estimate`, `model_routing`) to `enabled`, `awaiting_approval` (built and tested, off until Anthropic says yes) or `unsupported` (structurally impossible; nothing turns it on). nekkod enforces its Rust mirror (`crates/nekko-agent/src/claude_policy.rs`); a golden test (`packages/host/src/claude-policy.golden.test.ts` writes, `crates/nekko-agent/tests/claude_policy.rs` reads) keeps the table, the reasons and the auth mapping identical.

| | API key | Cloud (Bedrock, Vertex, Foundry) | Claude plan, and `unknown` |
|---|---|---|---|
| Chat, phone remote | on | on | on |
| Scheduled tasks, workflows, goals, watches, auto-continue (`unattended_runs`) | on | on | awaiting approval |
| Nekko tools inside a Claude Code chat (`nekko_tools`) | on | on | awaiting approval |
| Context note via `--append-system-prompt` (`context_note`) | on | on | awaiting approval |
| Usage limits in Nekko (`usage_limits`) | on | on | on for a plan since 2026-11-01: what the user's own Claude Code reported (below); `unknown` stays awaiting approval |
| Cost estimate | on | on | unsupported (billed to the plan; tokens only) |
| Model routing | on (Nekko engine) | on (Nekko engine) | unsupported |

- A Claude Code ("Claude Agent", provider kind `claude-code`) turn also never gets model routing on any auth: Claude Code owns the loop (`claude_code_owns_loop`).
- `unknown` (Claude Code's `claude auth status` not read yet, signed out, or an unrecognized method) behaves as a plan: fail closed.
- Auth is chosen per provider: `anthropic` is `api_key` (`subscription` for the legacy sign-in until it is removed), `bedrock`/`vertex`/`foundry` are `cloud`, and `claude-code` is `api_key` or `cloud` when Nekko sets the credential itself (`claudeCode.authSource`), otherwise what `claude auth status` reports.
- **Claude Code’s own plan on the plan sheet** (2026-10-31, [#1401](https://github.com/nekko-labs/nekko-agent/issues/1401)). On every auth, plan included, with no policy row: it is part of showing the chat. Nekko reads what the unmodified Claude Code printed (the same principle as plan usage) and adds no tool, prompt or flag to its session. See [plan sheet](../chat/plan-sheet-on-the-composer.md).
- **Reasons.** Every row that is not enabled carries a `ReasonId` whose one-line copy (`CLAUDE_REASONS`) is what a greyed control shows, followed by a "Why?" link to the "What works with a Claude plan?" sheet (`CLAUDE_PLAN_SHEET`). The comparison table under the provider cards is generated from the table (`claudeComparisonTable`); its plan column reads "Not yet" for the approval-gated rows (the design's "Off by default" for Nekko tools was dropped because there is no user toggle).
- **Gates.** nekkod admission refuses an unattended Claude Code turn (automation's `chat:send`, which now carries `unattended: true`) whose auth lacks `unattended_runs`, and tells the chat the reason. The harness calls `allows_nekko_tools`, `allows_context_note` and `plan_usage`, and records `claude auth status` with `note_auth_status`. The TS host's auto-continue applies the same rule (`claudeUnattendedRefusal`).
- **Signed override.** A release may carry `claude-policy.json` beside its update feed file. nekkod verifies its Ed25519 signature against the release signing key (the one key that also signs the update feed, `crates/nekko-native/src/release_key.rs`, decision [0039](../../docs/decisions/0039-one-release-signing-key-signs-the-update-feed.md)), accepts it only with a higher serial than the one applied, applies it all or nothing, and keeps it in the data directory. It can move rows only between `enabled` and `awaiting_approval`, never touch an `unsupported` row, and never turn an `unknown` row on. **Not live yet:** the release signing key has not been generated, so the key is an all-zero placeholder (TODO for Philip, steps in docs/signing.md, "The release signing key") and every override is refused.
- **The user's own approval** (`claudePlanFeaturesApproved`, Settings > Agents > **Claude plan features**). For someone who has Anthropic's written approval of their own (for example an agreement with Anthropic). On, nekkod turns every `awaiting_approval` `subscription` row on for that install: scheduled tasks, workflows, goals, watches and auto-continue, Nekko tools, the context note and plan usage (real data from Claude Code's stream, never the preview's example). It never changes an `unsupported` row (cost estimate, model routing) or the `unknown` rows, so an unread sign-in still fails closed, and only a literal `true` counts. The store reads the setting on every gate, so a flip applies to the next turn with no restart; `claude:policy` reports `userApproved`. Acceptance: off by default; the warning ("Only turn this on if Anthropic has approved it for you in writing", that Anthropic can limit or suspend an account that breaks its terms, that Nekko cannot check and the decision is the user's) is always visible beside the switch and is the switch's description; the "What works with a Claude plan?" sheet points to it. Nekko never claims or records an approval for the user. `[built and unit-tested 2026-10-28; not checked against a live plan sign-in]`
- **Renderer.** `claude:policy` (effective table, applied override, preview), `claude:capability(providerId, capability)` (row, reason id and line) and `claude:planUsage(providerId)`. No UI reads them yet (H4/H5b).
- **Plan usage on for a plan** (2026-11-01, decision [0035](../../docs/decisions/0035-plan-usage-on-for-claude-plans-from-claude-codes-own-output.md)). The terms forbid credentials, plan endpoints and request routing, not showing what the unmodified Claude Code printed, so `subscription.usage_limits` is `enabled`; `unknown` keeps it `awaiting_approval` (fail closed). The UI reads it through the ordinary limits path: `limitsKeyFor` gives a Claude Agent `claude-code:<provider id>` (TS and the phone views' Rust mirror), and nekkod answers `limits:get`/`limits:poll` for that key from the same source as `claude:planUsage` (`null` where the row is off, nothing was reported yet, or in the dev preview). The chat's usage chip reads as a subscription once windows arrive; the Models card, the Monitors dock and the phone show them like any other plan's. A running Claude Agent chat refreshes them every 30 seconds, an idle one every minute. `[built and unit-tested 2026-11-01; not checked against a live plan sign-in or on screen]`
- **Plan usage source** `[data path built 2026-10-23; not checked against a live plan sign-in]`. Claude Code documents two places where the unmodified binary reports plan usage in its own stream-json: a `rate_limit_event` (`rate_limit_info`: `status` allowed / allowed_warning / rejected, `resetsAt`, `utilization`, and `errorCode: "credits_required"` when the plan's included usage is spent) and, for `/usage`, a `usage_report.rate_limits` on the assistant message (each limit's `kind`, `percent`, `resets_at`, model scope and `severity`, plus extra-usage credits). The Claude Agent harness hands both up (`Mapped::PlanUsage`), `nekko_usage::parse_claude_code_usage` turns them into the same `SubscriptionLimits` windows every other provider uses (`five_hour` the current session, `seven_day` the week, a model scope its own window; a `rate_limit_event` replaces one window, a `/usage` report all of them), and nekkod keeps the latest per provider in memory. `claude:planUsage` answers `{ source: "claude-code", limits }` only where `usage_limits` is enabled for the auth, so on a Claude plan it stays hidden until Anthropic approves; Nekko never reads a credential, the plan usage endpoint or plan headers for it. Nekko does not send `/usage` on its own: a report arrives when the user runs it in the chat. Open: the docs leave `utilization`'s scale unstated (read as a fraction at or below 1, as the plan headers report it) and do not list `rateLimitType` (read when present, else the session window).
- **Preview (dev only).** `NEKKO_CLAUDE_POLICY_PREVIEW=subscription` renders the plan's approval-gated rows as enabled and answers `claude:planUsage` with example data (`claudePlanUsageExample()`, labelled "Example data"), for recording what Nekko would turn on. It is compiled only into nekkod builds with the `dev-tools` feature (`npm run dev`'s daemon), never the release build the app packages, and is ignored in a packaged app. The real Claude Code session in a preview still runs on an API key.
- **Routing between a local model and Claude Code** (planned 2026-11-01, decision [0037](../../docs/decisions/0037-route-each-message-once-to-a-local-model-or-claude-code.md)). A proposed `engine_routing` row, `enabled` on every auth: a Claude Agent chat may choose per message, before the turn, whether a local model answers or Claude Code runs it. On a plan the message reaches Claude Code unchanged and one hop only; `context_note` and `unattended_runs` keep enforcing that. Not in the table yet. See [routing between a local model and Claude Code](../agents/routing-between-local-and-claude-code.md).

Status: implemented and tested (unit, parity and an end-to-end daemon test); inert until the Claude Agent harness and UI use it.
