# Setting up a local model

Servers the user already runs live on **Model Providers**, under **Connected local servers**. Auto-discovery probes common localhost ports (Ollama 11434, LM Studio 1234, vLLM 8000, plus `127.0.0.1` to catch IPv4-only servers). They add or confirm a server, test the connection (green Connected / Offline), and the model list populates. Cloud providers are added the same way, grouped into **Local** vs **Cloud** sections. `[implemented, not visually verified]` The provider groups span the full window width (capped at 2200px; the engine card keeps its previous width), and each group's cards sit in one never-split container (extra cards wrap inside it) with a subtle border and tint in the group's accent colour (success green for local, info blue for cloud). Favorites pin to the top of the picker.

**DFlash2 for stock Qwen3.8-27B (#3541, reusing #3496).** `[implemented; renderer load/save verified with an isolated fixture; real GGUF Q4 and MLX 4-bit pairs verified through the isolated daemon and public model proxy on M1 Max; production chooser checked against the real daemon catalog; native drawer-to-daemon path blocked before renderer startup]` In the compatible target’s model details, **Draft model** offers its matching local head. **None** is the default; selecting a head passes its library ID to Load/Reload, and saves it for future loads. Nothing is paired or downloaded automatically. Ordinary drafts keep their same-architecture, same-format and quarter-size rules. A head is not a standalone model. See [the setup guide](../../docs/local-models.md#use-dflash2-with-stock-qwen38-27b).
- **MLX:** A `qwen3_5` vision target on Apple Silicon must have a recognized stock Qwen3.8-27B folder or mlx-community cache snapshot. The named head is classified as a draft from its config even though `model_type` can say `qwen3`. The daemon validates the configs and uses the external `mlx_vlm.server` from `mlx-vlm` 0.8.1 on its PATH. It keeps the upstream on loopback and requires both model readiness and confirmation that the draft loaded. A missing runtime or a mismatched target fails the load instead of quietly running without the draft. Ordinary MLX still uses `mlx_lm.server`. The public stock 4-bit target and full BF16 head streamed through the production router and supervisor in an isolated harness. The head accepted tokens, but decode was slower and greedy output differed in the measured run. See [the MLX measurement](../../docs/perf-history.md#stock-qwen38-27b-with-a-real-mlx-dflash2-head-3541-2026-11-27). The LM Studio basename `Qwen3.8-27B-MLX-8bit` is recognized when the configs match, but the public 8-bit run stopped at a memory-pressure warning before baseline readiness and never started the draft. No installed LM Studio weights were tested. See [the 8-bit preload record](../../docs/perf-history.md#unmeasured).
- **GGUF:** Use the exact stock header identity (`Qwen3.8-27B`, `qwen35`, 64 layers) and the named `Qwen3.8-27B-DFlash2` head (`general.architecture=dflash`), not a filename/ID prefix or another model of the same architecture. This uses the library's displayed header metadata, not a weight checksum. The backend passes `draft-dflash`; llama-server selects DFlash2 from the head's metadata. Ordinary drafts still use `draft-simple`. The managed build is `b12556`; see [the measured results on b12503](../../docs/perf-history.md#stock-qwen38-27b-with-a-real-gguf-dflash2-head-3541-2026-11-27).

**Local LoRA pairing (#3635, Rust engine).** The local library identifies LoRA weights as companions, not standalone inference models. A load names the base model and supplies the installed adapter's library ID as `adapterModelId`. The engine requires an exact Hugging Face repository match and matching GGUF architecture before starting llama.cpp with `--lora`. It does not guess compatibility from a model name, architecture alone, or a download suggestion. Missing or conflicting provenance fails closed, and an unsupported runtime does not silently load the base alone. MLX/safetensors adapters are identified but not loaded by this path. The Rust path is covered with synthetic local fixtures; real-weight inference, desktop selection, and companion download are not verified by this change.

**Per-variant configuration and external libraries (#3627).** `[implemented; real-weight inference with an external library not verified for this change]` Editing load settings saves them for this local library entry, without modifying the weights or reloading a running model. Opening another variant does not change its defaults. Show format, quantization and saved draft and context settings in Model Details. Opening the editor alone never writes a preset. On the next load, including chat and startup, use the saved settings. Regular MLX requests route by public library ID, then use the child’s launch-time model directory, not a Hub repository lookup. No external paths need to be sent to a cloud provider.

**Model settings: a memory meter, one recommended button, and big MoE models on small GPUs (2026-10-25).** `[implemented, unit-tested; renderer-verified in an isolated fixture; not yet loaded on real hardware]` A model's load drawer on Model Server is laid out for someone who does not know how models work. It leads with a **memory meter**: graphics memory and system memory as two bars (other apps, this model's weights, context and working space, and what is free), plus a line when part of the model is read from the SSD. A large **Use recommended settings** button picks the fastest setup that fits this model on this machine (GPU only first, then the lightest split at a useful 32K context, then as much context as that split holds), and "What this chose" says why, one plain sentence per setting; a model with no saved settings opens with it applied, and a "Recommended" tag stays on any value still equal to the pick. Next come **Run on** (GPU only or Hybrid; CPU only moved into Expert; a Mac shows one line, since its memory is shared) and a **Context** slider per session with a pages-of-text translation. In Hybrid, **How to split it** offers Custom (layers on the GPU), Fill the GPU and keep the rest in RAM (experts for a mixture-of-experts model, feed-forward for a dense one), All experts in RAM (with an expert cache in spare VRAM), Long coding sessions (the most context at q8_0, experts in RAM and a model's n-gram lookup table left on the SSD, the recipe people run big MoE models on 8 GB cards with), and Context in RAM. **More controls** holds sessions at once (recommended for the machine), memory precision (reliability against speed) and keep in memory (load when needed, keep loaded, pin), which says plainly that holding the model in RAM does not take the work off the GPU. **Expert** holds every other flag with a sentence and the flag it sets.
  - Acceptance: the meter is the placement planner's answer (`crates/nekko-engine/src/placement.rs`) for exactly the drawer's settings, and the launch passes that placement explicitly with `--fit off`, so llama.cpp does not re-place tensors behind it. On an 8 GB card with 32 GB of RAM, a 45 GB mixture-of-experts file with a 21 GB n-gram table is recommended a Hybrid setup that fits (the old drawer said it would not load at any context), and Long coding sessions reaches its full 256K.
  - The planner reads expert, feed-forward and lookup-table byte shares from the GGUF tensor table (a split model's shares come from its first shard) and places bytes in VRAM, RAM and on disk; the single-pool `compute_fit` and its recorded answers are unchanged ([decision 0023](../../docs/decisions/0023-place-bytes-in-three-places-and-pass-placement-explicitly.md)).
  - Parallel sessions share one KV pool (`--kv-unified`), each capped at its share (`--kv-unified-per-slot`); the drawer shows context per session and saves the total.
  - **Model Details: context and concurrent sessions (#3598).** `[implemented; real concurrent inference not benchmarked]` The installed-model pane has a **Model Details** heading and a separator above **Other builds from**. The Context slider marks the recommended per-session value; **Reset** returns only context to that value and retains the chosen session count and memory precision. The compact memory legend names the session count and context per session next to the combined cache bytes, not a per-session byte estimate. Default recommendations use the tighter of available GPU and system memory (with OS headroom) on a shared-memory Mac, and start with one session there or on CPU. A discrete GPU can recommend two when both fit fully on the GPU at a useful context. A fit estimate is not a concurrency benchmark; more sessions are a manual choice. New llama.cpp launches explicitly pass `--parallel 1` for a one-session configuration instead of inheriting the server's automatic slot count. Existing saved multi-session settings are not rewritten.
  - **What each part is for (2026-11-25, #3315).** `[implemented, unit-tested; renderer-verified in an isolated fixture]` Philip: "for a specific model, let's also clarify in the bar graph memory+vram consumption for different aspects like loading in memory, parallelization selected, etc." The meter's parts are named by the setting behind them, and a table under the bars gives each part's VRAM and RAM: **Model weights** (where the layers run, e.g. "all 36 layers on the GPU" or "24 of 48 layers on the GPU, experts of 40 layers in RAM", and how they load: mapped from the file, read into memory, or pinned), **Expert cache** (split out of the weights when set), **Context** ("4 sessions × 16k, balanced (q8_0)", drawn as one slice per session, and "kept in RAM" when it is), **Working space** (compute buffers, with the batch size when set) and **Pinned copy**. Pointing at a part, in the bar or the table, fades the others. The live bar on Loaded models uses the same names (`memoryBreakdown.ts`).
  - Not built: a persistent speculative n-gram cache on disk (`--lookup-cache-dynamic`). The engine cannot keep an incognito chat's tokens out of a per-model file, so it waits for a per-request opt-out.

**The built-in engine loads with a q8_0 KV cache (2026-11-25, #3325).** `[implemented, unit-tested; load drawer renderer-verified in an isolated fixture; not yet checked on Windows/Linux GPUs]`
- **The default changed from f16 to q8_0.**
  - **Applies to:** a load that names no KV type, the recommended settings ("Use recommended settings", the context and speed goals), and the preset a fresh download starts with.
  - **Why:** measured on Qwen3-8B at 26k of context with llama.cpp b12470 on Apple Silicon. q8_0 takes half the memory of f16, so the same RAM holds twice the context. Decode was 26% faster and prefill 8% slower, all 8 planted facts were retrieved, and greedy output was token-for-token identical to f16 for 400 tokens on two tasks. Details in #3325.
  - **Not affected:** a load that names f16 keeps it. With Flash Attention switched off, the default is f16, because llama.cpp refuses a quantized V cache without it. Ollama, LM Studio and vLLM set their cache server-wide, so their planning keeps f16 first and offers q8_0 as a compromise. MLX ignores the setting (see below).
- **Names.** The precision slider and the "What this chose" rows read **Full** (f16), **Standard** (q8_0, the default) and **Compact** (q4_0). They replace "Most reliable / Balanced / Fastest", which implied q8_0 was less reliable than our measurements show. Compact is described as best kept for chat: its long replies left the f16 path within a few dozen tokens in our test.
- **A quantized cache that will not start falls back to f16 once.**
  - **When:** a llama.cpp build that breaks it, or a backend without the kernel, as `f8_e4m3` aborts on Metal in b12470. If llama-server fails to start with a q8_0 or q4_0 cache and the failure is unexplained or names the cache, the engine tries once more with f16.
  - **What the user sees:** the load reports success with a note ("It runs with a full-precision (f16) KV cache: the q8_0 cache did not start on this machine.") and `kvFallback: "f16"`.
  - **No retry:** out-of-memory errors (f16 needs more), a missing runtime, or a load that already asked for f16.

**The memory meter counts a quantized KV cache as llama.cpp stores it (2026-11-25, #3325).** `[implemented, unit-tested against sizes measured on llama-server b12470]`
- llama.cpp's q8_0 and q4_0 keep an f16 scale with every 32 values, so they take 1.0625 and 0.5625 bytes an element, not 1 and 0.5. The planner used the round figures and undercounted a q8_0 cache by 6% and a q4_0 cache by 12.5%, so a model could be shown as fitting when it did not. Measured on Qwen3-8B at 32k: f16 4,608 MiB, q8_0 2,448 MiB, q4_0 1,296 MiB, which is what the meter now shows.
- **An MLX model is planned with an f16 cache.** `mlx_lm.server` is started without `--kv-bits`, so the cache stays f16 whatever the KV setting says. The meter counts it that way, and the planner neither offers nor falls back to q8_0 for MLX.
- **Never offered, measured on Metal (b11224 and b12470):**
  - **Mixed K and V types:** with K q8_0 and V q4_0, prefill falls from about 1,200 to 20–70 tokens a second.
  - **`f8_e4m3`** (new in b12470): aborts at load ("cannot run the operation (SET_ROWS)").

**A model loaded with a small context window (2026-10-23).** `[implemented, unit-tested; not yet checked against a live LM Studio or llama.cpp server]` A local server can load a model with a window smaller than Nekko's system prompt plus its tool definitions (LM Studio loaded Gemma 4 E4B with 8,192 tokens, and the first "Hello" needed 10,510). When the server refuses a prompt as too long, the system prompt and tools are at least as large as the conversation, and they alone would fill more than 60% of the model's window (the window the server's error states as `n_ctx`, else the one Nekko knows for the model), the reply is sent once more without the tools, so the chat still answers, without tools for that reply. A long conversation that overflows is still left to elision and compaction, as before. When even that does not fit, the error names the window and the fix instead of the server's raw JSON, when the server says the numbers (`n_ctx`, `n_prompt_tokens`): "The model is loaded with a 8192-token context window, and this chat needs 10510 tokens. Reload the model with a larger context length (16384 or more) in your model server, then send again." Such an overflow is not compacted automatically either: when the error names the prompt size and the conversation is under half of it, a summary would free almost nothing, so the chat keeps the error with its fix (compacting a two-message chat used to end in "The conversation changed during compaction"). Not yet: the system prompt itself is not shortened for small windows.

**Claude in Amazon Bedrock (2026-10-19).** `[implemented, unit-tested; not yet checked against a live Bedrock account or visually verified]` Teams that already pay for Claude through AWS can add **Claude in Amazon Bedrock** as a cloud provider with their own Bedrock bearer token. It runs on Nekko's own engine with every Nekko feature, the same as Claude on an Anthropic API key, against Bedrock's Messages endpoint (`https://bedrock-mantle.{region}.api.aws/anthropic`; the region is part of the base URL, `us-east-1` by default). Bedrock has no models list, so the picker shows the Claude models Bedrock serves (`anthropic.claude-opus-5-5` and so on), and model limits, effort and context windows are read from the Claude id after the `anthropic.` prefix. Usage is billed to the user's AWS account. Signing requests with an AWS profile (SigV4) instead of a token is not supported yet.

**Claude on Vertex AI and in Microsoft Foundry (2026-10-19).** `[implemented, unit-tested; not yet checked against live accounts or visually verified]` The same goes for Google Cloud and Azure customers. **Claude on Vertex AI** needs no key in Nekko: the base URL names the project and location (`https://aiplatform.googleapis.com/v1/projects/<project>/locations/global`), and the engine gets a short-lived access token from the user's own Google Application Default Credentials. That is the file `gcloud auth application-default login` writes, or `GOOGLE_APPLICATION_CREDENTIALS`. A user credential is exchanged directly, and anything else is handed to `gcloud`, which signs for it. The token is cached until shortly before it expires and is never saved. Requests go to `…/publishers/anthropic/models/<model>:streamRawPredict` with the version (`vertex-2023-10-16`) in the body. **Claude in Microsoft Foundry** takes the Foundry resource's key and its base URL (`https://<resource>.services.ai.azure.com/anthropic`). The picker lists Foundry's default deployment names, and a custom deployment name is typed in like any unlisted model. Neither platform serves Anthropic's models list or rate-limit headers, so the picker shows a shipped list and the capacity panel says **no usage API**. Entra ID sign-in for Foundry is not supported yet.

**Groups share rows when there is room (2026-10-16).** `[implemented, unit-tested; isolated renderer captures]` On Model Providers, a group’s cards stay together: each group first fills whole rows of its own, and only the cards left over (fewer than a row holds) sit beside another group’s leftovers when they fit on the same line. Leftovers that do not fit move to the next line as a unit rather than splitting. With two columns, one local server and one cloud provider share a row; one local and two cloud put the cloud pair on its own row; one local and three cloud show the cloud pair, then the local server beside the third cloud card. Columns come from the available width (cards at least 340 px wide, so one column on narrow windows) and the page is wider than before (max-w-6xl) so wide windows fit three. Each group’s heading appears once, above its first cards; cards sharing a line stay top-aligned. Layout only: no provider, network or settings behaviour changes.

Each local server then renders as a **runtime card**: a power toggle that really starts and stops it, its address ready to copy or edit in place, and the models it currently holds with the real split between GPU and system memory. Picking a model opens a **fit drawer**, where one context slider drives a live memory projection: weights, KV cache, and runtime overhead stacked against what the machine actually has free, with a marker where that memory runs out. Dragging the slider past what the machine can hold turns the bar amber and then pushes it past the marker, so a user learns a 64k context will spill onto the CPU *before* waiting through the load rather than after. Underneath, one plain sentence says what will happen and why ("12 of 32 layers will run on the CPU, because the KV cache alone needs 14.2 GB"), and up to three one-click fixes offer a smaller context, a cheaper KV cache, fewer parallel slots, or a smaller build. Expert controls (parallelism, KV cache type, GPU offload share, TTL) sit behind an Advanced disclosure, and settings a server only reads at startup are shown as the exact environment line to set, marked restart-required, rather than as a control that would silently not apply.

**Catalog companion downloads (#3635).** `[implemented; catalog and isolated desktop fixture checks; full downloads not exercised]` Find a DFlash2 draft or supported GGUF LoRA through the catalog without treating it as a standalone recommendation. The details identify the verified installed base or name the downloadable runtime build and its size. Downloading only the companion never queues the base; downloading both is explicit. The daemon reuses a verified installed base and refuses unresolved pairings. Download does not activate the companion or change the base preset.
