# Setting up a local model

Servers the user already runs live on **Model Providers**, under **Connected local servers**. Auto-discovery probes common localhost ports (Ollama 11434, LM Studio 1234, vLLM 8000, plus `127.0.0.1` to catch IPv4-only servers). They add or confirm a server, test the connection (green Connected / Offline), and the model list populates. Cloud providers are added the same way, grouped into **Local** vs **Cloud** sections. `[implemented, not visually verified]` The provider groups span the full window width (capped at 2200px; the engine card keeps its previous width), and each group's cards sit in one never-split container (extra cards wrap inside it) with a subtle border and tint in the group's accent colour (success green for local, info blue for cloud). Favorites pin to the top of the picker.

**Claude in Amazon Bedrock (2026-10-19).** `[implemented, unit-tested; not yet checked against a live Bedrock account or visually verified]` Teams that already pay for Claude through AWS can add **Claude in Amazon Bedrock** as a cloud provider with their own Bedrock bearer token. It runs on Nekko's own engine with every Nekko feature, the same as Claude on an Anthropic API key, against Bedrock's Messages endpoint (`https://bedrock-mantle.{region}.api.aws/anthropic`; the region is part of the base URL, `us-east-1` by default). Bedrock has no models list, so the picker shows the Claude models Bedrock serves (`anthropic.claude-opus-5-5` and so on), and model limits, effort and context windows are read from the Claude id after the `anthropic.` prefix. Usage is billed to the user's AWS account. Signing requests with an AWS profile (SigV4) instead of a token is not supported yet.

**Claude on Vertex AI and in Microsoft Foundry (2026-10-19).** `[implemented, unit-tested; not yet checked against live accounts or visually verified]` The same goes for Google Cloud and Azure customers. **Claude on Vertex AI** needs no key in Nekko: the base URL names the project and location (`https://aiplatform.googleapis.com/v1/projects/<project>/locations/global`), and the engine gets a short-lived access token from the user's own Google Application Default Credentials. That is the file `gcloud auth application-default login` writes, or `GOOGLE_APPLICATION_CREDENTIALS`. A user credential is exchanged directly, and anything else is handed to `gcloud`, which signs for it. The token is cached until shortly before it expires and is never saved. Requests go to `…/publishers/anthropic/models/<model>:streamRawPredict` with the version (`vertex-2023-10-16`) in the body. **Claude in Microsoft Foundry** takes the Foundry resource's key and its base URL (`https://<resource>.services.ai.azure.com/anthropic`). The picker lists Foundry's default deployment names, and a custom deployment name is typed in like any unlisted model. Neither platform serves Anthropic's models list or rate-limit headers, so the picker shows a shipped list and the capacity panel says **no usage API**. Entra ID sign-in for Foundry is not supported yet.

**Groups share rows when there is room (2026-10-16).** `[implemented, unit-tested; isolated renderer captures]` On Model Providers, a group’s cards stay together: each group first fills whole rows of its own, and only the cards left over (fewer than a row holds) sit beside another group’s leftovers when they fit on the same line. Leftovers that do not fit move to the next line as a unit rather than splitting. With two columns, one local server and one cloud provider share a row; one local and two cloud put the cloud pair on its own row; one local and three cloud show the cloud pair, then the local server beside the third cloud card. Columns come from the available width (cards at least 340 px wide, so one column on narrow windows) and the page is wider than before (max-w-6xl) so wide windows fit three. Each group’s heading appears once, above its first cards; cards sharing a line stay top-aligned. Layout only: no provider, network or settings behaviour changes.

Each local server then renders as a **runtime card**: a power toggle that really starts and stops it, its address ready to copy or edit in place, and the models it currently holds with the real split between GPU and system memory. Picking a model opens a **fit drawer**, where one context slider drives a live memory projection: weights, KV cache, and runtime overhead stacked against what the machine actually has free, with a marker where that memory runs out. Dragging the slider past what the machine can hold turns the bar amber and then pushes it past the marker, so a user learns a 64k context will spill onto the CPU *before* waiting through the load rather than after. Underneath, one plain sentence says what will happen and why ("12 of 32 layers will run on the CPU, because the KV cache alone needs 14.2 GB"), and up to three one-click fixes offer a smaller context, a cheaper KV cache, fewer parallel slots, or a smaller build. Expert controls (parallelism, KV cache type, GPU offload share, TTL) sit behind an Advanced disclosure, and settings a server only reads at startup are shown as the exact environment line to set, marked restart-required, rather than as a control that would silently not apply.
