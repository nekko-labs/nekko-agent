# Running a model with nothing else installed

**Model Server (2026-09-30; named Nekko Server until 2026-10-18).** The desktop page for the Local Model Server, shown as **Model Server** in the app. On wide screens its left column combines Model server and Agent server controls, each independently switchable, with runtime installation, endpoint settings, CLI and MCP access. The right column holds the searchable model library, downloads and folders. Narrow screens stack these sections while preserving every control. Navigation destinations can be dragged into a user-chosen order, with keyboard reordering and persistence across restarts; hidden experimental destinations keep their saved positions.

**Local image generation.** Image models use the optional stable-diffusion.cpp runtime rather than llama.cpp. Before installing it, the app shows its release version, hardware backend and full download size including runtime-library companions. Downloading an image model recommends the runtime but does not silently install it or prevent downloading weights alone. A managed runtime can be uninstalled without deleting models, and external binaries are never removed. Image models can be loaded and used through the model server's OpenAI-compatible image-generation endpoint, or from chat. `[shipped 2026-10-01]` Every chat has a **MultiModal | Image** switch in the composer. An Image chat sends each prompt to a local image model instead of a chat model: the composer's controls become the image model (image models only), size, steps, CFG and seed, with a one-press download when the model lacks its text encoders, and the agent-only controls (tool mode, tools, MCP, reasoning, effort, attachments, Automate) step aside. Each reply is the picture, shown with the model, size, steps, CFG, the seed actually used and the time it took, so any image can be reproduced; prompts and pictures stay together as the chat's history. Settings are kept per chat and picking a model adopts its family's tuned steps and CFG. The Agent board shows an Image chat as its own kind of worker (🎨), with the image model and count, thumbnails in place of text turns, a live "Loading the image model" / "Generating" line while it works, and a reply box that generates the next image. Model Server keeps each image model's setup (companions, paths, memory) and opens an Image chat on it with **Generate in chat**. Decision models are not a chat type: they answer typed questions about a state rather than converse, so they belong to the agent's tools and a test panel, not the composer. Missing text encoders or VAE files are named with configurable companion paths; borrowed model folders remain read-only. `[shipped 2026-10-01]` For the families it knows (FLUX.2 klein 4B and 9B, SD3.5, FLUX.1), the Generate panel lists the text encoders and VAE the model needs, which are already on disk, and what the rest weighs, and one press downloads them into a Nekko-owned folder shared across the family; the panel also starts from the family's tuned steps and CFG. A VAE whose Hugging Face repo is gated is fetched with the user's token when there is one, and otherwise a small openly licensed decoder (TAESD) stands in so the model still runs, which the panel says.

**Runtime updates.** An external GitHub Actions job checks upstream releases on a schedule and also accepts dispatch events. A newer usable release creates or updates a PR to the runtime-version manifest, not an automatic download or an in-app polling loop. Checks run every six hours and keep a seven-day release-age buffer before recommending new binaries; already newer pins are never downgraded. A GitHub App installed only on this repository creates the PRs with Contents and Pull requests write permission, triggering normal CI without enabling the broader GITHUB_TOKEN PR-creation/approval option. Credential provisioning is a separate confirmation-gated activation step. Incomplete releases are skipped; the PR goes through verification before becoming the recommended install.

**One user-data home.** Desktop, web and CLI default to `~/.nekko-agent`, including settings, sessions, tokens, runtime installs, launcher metadata and desktop profile data. Managed models live under `models/{type}` (chat, vision, embedding, image, audio, draft or unknown). Explicit data-directory overrides and borrowed model folders remain supported. Existing Nekko Agent desktop data and `~/.nekko` can be moved only after user confirmation, with conflict refusal, recoverable migration and saved references preserved. No old-brand compatibility is reintroduced.

**Consolidating earlier installs.** `[implemented, headless-verified; desktop dialog and a real terminal run unverified]` The single-profile move above refuses a destination that already has data, which leaves anyone who ran several earlier names (`~/.nekko`, `~/.agent-nekko`, `%APPDATA%\@agent-nekko`, `@kotrain`, `@open-paw`, `@nekko`, an installed Kotrain or Open Paw, their updater caches and `kotrain-*` temp folders) with data split across folders. Two entry points do the same additive merge. **Desktop:** every launch, before the engine starts, checks that those locations exist (existence checks only) and, if any hold data, asks: *Merge and clean up*, *Merge, keep old copies*, or *Not now*. *Not now* is not remembered, so the question returns next launch; nothing is hidden or silenced. **Terminal:** `nekko-agent migrate [--dry-run] [--yes] [--keep-old] [--no-restart]` lists what it found, and if the desktop app is running closes it (a normal close first, forced only after 20 seconds), merges, cleans up and reopens it. It reopens a packaged app; a development build is not relaunched, and the command says so. The normal close is a `taskkill` (no `/F`) to the app's main process only; the app treats a bare close request from another program as *quit*, not *hide to tray*, so the engine shuts down cleanly in well under a second (measured 0.4 s with a page open in Browser, against 20.5 s and a forced kill before). A person closing the window (close button, Alt+F4, taskbar Close window, which arrive as SC_CLOSE or no WM_CLOSE) still hides it to the tray. `[implemented, unit-tested, measured on Windows against an isolated desktop app]` The launch prompt is never shown when the data folder is set explicitly (`NEKKO_DATA_DIR`): the old folders belong to the real profile and must not be merged into, or deleted for, a scratch one.

The merge never overwrites: sessions and files already in `~/.nekko-agent` win; usage and quota logs are unioned line by line (spending history is the union of every source); providers, workspaces, favourite models, prompts, connectors and MCP servers are unioned by id, name or path while scalar settings keep the current value and gain only keys the current file lacks; sign-ins are merged by key, the newer wins; managed models move into `models/{type}`; an old folder's engine build moves over only when `~/.nekko-agent` has none, and otherwise is a superseded download that is neither mixed into the current build nor a reason to keep the old folder; saved paths that pointed into an old folder are rewritten; a workspace pointing at an earlier repo name follows the rename when the new folder exists. Per-machine state (`window-state.json`, `cli-link.json`, `migration.json`) is not merged. Before anything changes, the files that will change are copied to `~/.nekko-agent/backups/legacy-<time>/` (sessions, settings, tokens, usage; model files are moved, not copied). Cleanup deletes a folder only after confirming everything in it is present in `~/.nekko-agent`, runs an install's own silent uninstaller first, and keeps (and reports) anything it cannot prove is merged. It refuses to start while another Nekko process is serving from any involved folder. A failed merge deletes nothing and re-running continues.

After the merge, duplicates are folded (`profile-repair.ts`): folders by path (case, separator and trailing-slash insensitive on Windows; drive roots kept), local servers by kind and address (`localhost` = `127.0.0.1`, `/v1` ignored), subscriptions only when both tokens are known to belong to the same account (never on a guess). The id with the most history survives; sessions, usage, quota history and favourites are rewritten to it so totals are unchanged. `scripts/repair-profile.mjs` applies the same fold to an already-merged profile (dry run by default, `--keep`, `--remove`, `--account`, refuses while the app is serving). `[implemented, unit-tested]`

**Folder list hygiene.** `[implemented, unit-tested]` The host's `saveSettings` keeps one entry per folder on every write, and the composer's folder picker shows a folder saved twice once. Revoking a folder with its × keeps the menu open.

**Model picker resilience.** `[implemented, unit-tested; live check against an unreachable LAN server done via the app API]` Each provider's model list fills in as it answers instead of waiting for all; core list requests time out after 5 s (ChatGPT catalog 8 s, falling back to the curated list). An unreachable server no longer leaves the whole picker, including the default model, on "loading…".

**Agent window companions.** `[implemented; renderer-verified in the Local Web UI, Electron webview unverified]` Changes (with its count), Files and Browser sit in each agent window's header beside Logs; the Agents title bar no longer carries them. On the wall the companion column has a 26 px close button and a drag/keyboard resizer (20–75 %, per chat, double-click resets). Files opens the chat's own checkout of its primary folder, else the primary folder, else its first supporting folder, and follows a folder change. A no-op workspace update no longer re-renders every wall window.

**Dev launcher banner.** `[implemented, verified in a terminal]` `npm run dev` prints an ASCII banner once the app reports in: version, pid, API URL (or that it is off), renderer URL, data folder, and the stop keys (q / Enter clean stop, Ctrl+C twice to force). No colour when `NO_COLOR` is set or output is not a terminal.

Out of scope and unverified: macOS and Linux paths are covered by unit tests with injected directories but not run on those systems; `Nekko Paw` and `Nekko Notes` installs are not touched (separate products); the Windows uninstaller call is not exercised in tests.

The **Model Server** tab contains the **Nekko Agent engine**: the model server Nekko Agent runs itself, so the answer to "how do I run a local model" is no longer "first install LM Studio". It is llama.cpp underneath, and everything around it (getting the engine, getting models, keeping them, serving them) happens in the app. It sits beside **Model Providers**, which is the other question entirely — where models come *from* (a Claude subscription, an API key, a server on another machine) — and the two used to be one crowded page.

**Getting an engine.** The card names the build this machine should run in terms of the hardware rather than the acronym ("An NVIDIA GPU with a current driver", not "CUDA"), picked from what the GPU probe actually found: CUDA only where an NVIDIA reading exists, Vulkan for a GPU we cannot identify, Metal on Apple Silicon, CPU when there is no evidence of anything else, and the rest of the list still offered for anyone who wants to override. A few hundred megabytes come from llama.cpp's own releases, and only after the user presses the button. Anyone who already has a `llama-server` can point at it instead, and a binary they point at is theirs: we run it and never update or remove it.

**Getting models.** Models are **one surface, not two tabs**: a single search box filters the models already on this machine and searches Hugging Face at once, so "do I have it" and "can I get it" are the same question, answered in one scroll with the installed models on top and the catalog below. An empty box opens the catalog on a short curated list, because the question a new user has is "what should I run", not "what exists". The sizes are explained in place rather than assumed known: the parameter count is labelled as billions of parameters (a bigger model knows more and needs more memory), each model's smallest build is checked against this machine's actual memory pool and chips as **fits here** / **tight fit** / **needs more memory**, and the model page marks the build most people should take (Q4_K_M when the repo publishes it, otherwise the lightest build that fits) with one-line notes on what the other quantizations trade. A row answers "which of these" and nothing more; opening one gives the model **its own page**, because "should I run this" needs what a row has no space for: the publisher's model card, how many people pull it and how many like it, when the repo last moved, what it was converted from, its license, and the full ladder of builds with the real download size and per-build fit verdict of each. The card is rendered from markdown we parse ourselves rather than injected as markup, images in it are dropped rather than fetched, and any HTML the publisher wrote is reduced to its text — it is prose from a stranger's repository, and it is treated that way. Downloads resume after an interruption, report their rate and time left, cancel for real, and land only after the file parses as a GGUF, so a half-finished model never appears in the library wearing the right name. `[updated 2026-10-01]` A finished download is also the moment the engine knows the file's geometry, so it plans the fullest fit the GPU can hold (every layer offloaded when they fit) and saves that as the model's preset, and **Start with Nekko** switches itself on, so the model a user just asked for runs next time the app opens with nobody visiting settings first. A machine whose hardware probe cannot answer skips the preset rather than writing a guess.

**Models you already have.** A GGUF is a GGUF whoever downloaded it, so a machine that has already pulled Qwen through Ollama or LM Studio should not have to pull it again to run it here. On first run Nekko Agent looks in the usual places for **Ollama, LM Studio, Jan, GPT4All, llama.cpp, KoboldCpp, LocalAI, Bionic, text-generation-webui and the Hugging Face cache vLLM serves from**, and every one of those folders that actually has models in it becomes a row in the library, named, sized and loadable. Ollama gets its own reader: it stores models as content-addressed blobs with no extension, so a directory walk finds a pile of hashes, and the manifests are read instead so `llama3.2:latest` appears under the name you would type at `ollama run`.

**What each file actually is.** A GGUF is not always a chat model: people also keep image generators, speech recognizers, embedding models and speculative-decoding draft heads on disk, and llama.cpp cannot serve most of those. The library reads each file's declared architecture, names what it is on the row (**chat**, **vision**, **embedding**, **image gen**, **audio**, **draft head**), and when the engine cannot serve it says why in a sentence ("an image-generation model, it runs in stable-diffusion.cpp") instead of offering a Load that can only fail. Vision models that need an `mmproj` projector say whether it is present and offer to fetch it from the model's own repository; companion files fetched that way land in a Nekko-owned folder, never in the borrowed app's. Chat templates and projectors found beside the model or in its tokenizer config are picked up at load and passed as `--mmproj` and `--chat-template-file`, so a borrowed vision model answers with working eyes rather than llama.cpp's opaque missing-file failure.

The **Folders** tab is that list, and all of it is editable: retype a path, switch a folder off without forgetting it, delete a row, or add one nobody guessed. Each row shows what it contributes (how many models, how many gigabytes) and whether it is on disk at all. The folder downloads land in is pinned at the top and cannot be deleted, because a download has to have somewhere to go. Everything else is **read, never written**: a borrowed model loads here exactly like one we downloaded, says which app it came from, and offers no delete, because that file belongs to that app and removing it from here would break it silently. A GGUF anywhere else can still be adopted by path without being copied.

**Two control surfaces over one state.** **Simple** is a single question, *how much of this machine may it use?*, and one slider from "leave my machine usable" to "everything it has". It solves through the same fit planner into a real context length, GPU offload and KV cache type, then says what it chose and what it costs in plain words ("32k of context, entirely on the GPU. About 7.3 GB of VRAM, leaving 12.1 GB for everything else."). It deliberately does not predict tokens per second: memory can be measured and speed would be invented. **Advanced** is every flag llama.cpp takes, context length, GPU offload, KV cache type, parallel slots, flash attention, batch and physical batch, CPU threads, mmap and mlock, RoPE base and scale, seed, and idle TTL. They are the same state, not two modes: moving the slider fills the fields, editing a field moves the projection, and settings can be saved as a model's default so it loads the same way every time. The same drawer answers the other half of "how should this model behave when I am not looking": **load when the engine starts** and **keep it loaded** sit together with the missing-projector fetch, because startup and eviction are one question asked about the same model. `[updated 2026-10-02]` The Advanced surface leads with a **Runs on** pick, GPU only, Hybrid or CPU only, instead of a bare layer number: GPU only writes an explicit all-layers offload rather than trusting the engine's default to agree, Hybrid reveals the layer split and the CPU threads it needs, and on a machine the planner found no GPU on, the two GPU choices disable rather than offer a load that could never use one.

**Serving.** The engine presents **one address** (`http://127.0.0.1:11500/v1` by default) that any OpenAI-compatible tool can point at, with a `llama-server` process per loaded model behind it. The address and port are shown whether the server is running or stopped, so another tool can be configured before the engine ever starts; the default port is a shared constant, never re-typed per surface. Several models stay resident at once; a request for one that is not loaded loads it; an idle model is evicted on a timer; and the address stays valid across loads and unloads, so a chat or an external tool configured once keeps working. Models marked **on start** load in order with their saved settings when the engine starts, a failure logged and never blocking the rest; and the library's **In memory** section shows what is resident (when it loaded, when it was last used, how much VRAM and context it holds, when it expires) with an unload action and a per-model idle timeout that can be changed without a reload. `[updated 2026-10-02]` A model still on its way in appears there the moment the load starts rather than at the next refresh: a progress bar with a percentage where the drop in free VRAM can be measured against the share of the file headed to the GPU, an indeterminate bar where it cannot (a CPU load, or no GPU probe), and a queue note while it waits behind another load. Each resident row says how long it has been idle and when it will evict, in words a person can't misread. Flags are written in the dialect the installed build speaks: newer llama.cpp takes `--load-mode` where the builds before it took `--no-mmap` and `--mlock`, and the engine probes `--help` once per binary so either era launches cleanly. A failed load is kept on the model's row as a readable reason, translated from llama.cpp's log where a known cause matches, rather than lost. The left column's **Model server settings** disclosure carries what every other local model server puts in its own app: port, whether it is reachable from the network or only this computer, an API key, allowed browser origins, how many models may be resident, the idle timeout, load-on-demand, start-with-the-app, and where models are kept. The defaults are the safe ones, and the two settings that can expose the machine say so in the sentence next to them rather than in a tooltip. `[updated 2026-10-15]` **Reaching the engine from the network requires a key** (#549): the router only checks a Bearer token when a key is set, so a LAN bind with an empty key would have put every route on the network for anyone to call. The engine (daemon side, in both the Rust and TS hosts) now refuses to start or reconfigure with **This computer and my network** selected and no key, returning a sentence the settings card shows rather than silently listening open; the last good listener stays up when a reconfigure is refused. The settings card does not leave the user to run into that refusal: picking **This computer and my network** with an empty key field fills in a generated 32-character key, a key already typed is kept, and switching back to **This computer only** never touches the key. `[updated 2026-10-01]` The card's own header answers the two questions asked first: a sliding switch turns the server on and off with its state (**serving** / **stopped**) named immediately beside it, and **Start with Nekko** sits on the same row rather than inside the settings disclosure, because whether it will be on tomorrow is as important as whether it is on now.

Because the file is ours, its GGUF header is read directly, so the layer count, KV head count, head dimension and trained context are **facts rather than gaps**: the memory projection for a model the engine holds is exact where the same projection for another server's model has to report parts of itself as unknown. After a load the real residency is measured against what was projected, and the difference feeds the same calibration record the other runtimes use.

**The fastest local tokens/s** `[in progress]`. With one user, every engine runs into the same wall (memory bandwidth), so Nekko Agent competes with Ollama, LM Studio and vLLM on what an agent actually does rather than on kernels it did not write. Measured results, method and the places it is not ahead are in [docs/benchmarks.md](docs/benchmarks.md).

- **The fastest backend for this machine, picked for you.** llama.cpp with CUDA on NVIDIA, and Vulkan on AMD and Intel GPUs, found from the operating system's own adapter list so those machines are no longer offered the CPU build. `[shipped 2026-09-30]` On an Apple Silicon Mac, **MLX** is offered as an optional runtime beside llama.cpp: one press installs it with its own Python (the system's is never touched), MLX model folders already on the Mac (LM Studio's MLX downloads included) appear in the library tagged MLX, and they run through the same engine address as every other model. `[shipped 2026-09-30, not yet verified on a Mac]` MLX models can be searched and downloaded from the in-app catalog too, one folder per model. `[shipped 2026-10-01, not yet verified on a Mac]`
- **Older and non-NVIDIA GPUs are found through the engine itself.** `[Preview, implemented 2026-10-08; hardware output verified on one machine only]` When `nvidia-smi` is missing from PATH, refuses to run (an old driver on a hybrid laptop such as a Surface Book 2 answers "not administrator / no TCC device"), or the GPU is AMD or Intel, the GPU probe asks the installed engine's own `llama-server --list-devices`, which names the GPUs the model will really load on. Those readings feed the same memory meters, the "will it fit" chips and the preset a finished download saves, so such a machine gets a GPU offload and context plan instead of silently loading on the CPU with a 2k context. Only discrete GPUs count: an integrated part's memory is system RAM, so it is never added to a card's VRAM, and a machine with only an integrated GPU still reads as having none. The reading carries no utilization figure (the dock names its source as `llama-server`), is cached for 15 seconds because it costs a process spawn, and a load's before/after measurement always takes a fresh one. Acceptance: with `nvidia-smi` failing and a discrete Vulkan GPU present, the library reports the GPU's memory; with neither, nothing changes. Verified: deterministic parser, vendor-priority, cache/fresh-read and recursion-safe binary-lookup tests, and a real `--list-devices` read on a GTX 1050 laptop. Discrete RX Vega 56/64 cards are retained; integrated Vega 8/11 Graphics are excluded. Registering an engine invalidates an earlier no-GPU monitor reading. The probe reads only local engine/device information, starts a hidden bounded process, makes no network request and does not install a runtime or change existing saved presets. Running-app GPU display and download-to-preset acceptance are still unverified. Tracking: [T185](TASKS.md#gpu-fallback-preview-added-2026-10-08). **Planned, not built:** a visible "GPU found but unused" notice on a CPU-only load, a Windows hint when a GPU is in an error state (restart or reseat), and AMD or Linux verification.
- **Loaded models survive the engine's own restarts.** `[shipped 2026-09-30, desktop]` The model servers and the address in front of them run in the engine daemon, so if the rest of the engine restarts, loaded models keep answering and are picked up again; the daemon's router adds about 0.1 ms per request.
- **Opening a chat never waits on a busy agent.** `[shipped 2026-10-01, desktop]` The chat list and opening a chat are served by the engine daemon straight from disk, not by the part of the engine running agents, so an agent streaming in one tab no longer holds up switching to another. With that part busy, opening a 7 MB image chat took 14 ms instead of 403 ms, and listing 301 chats 22 ms instead of 797 ms. Renaming, pinning, queuing a follow-up and the chat's other settings are saved by the daemon too, and a change made while a turn is running is kept when the turn saves.
- **The prompt cache survives between turns.** `[shipped 2026-09-30; controlled by the default-on Prompt caching setting as of 2026-10-07]` An agent resends a large system prompt, the project context and every tool result on each turn. The engine keeps each chat's cache in place on the GPU and reuses cached chunks around an edit, with a RAM prompt cache behind it for chats that lose their slot. Coming back to one of six rotating chats takes 0.8 s to the first token, against 1.3 s in Ollama and 1.6 s in LM Studio.
- **Speculative decoding by default.** `[shipped 2026-09-30]` Prompt lookup guesses upcoming tokens from text already in the conversation and the model checks them in one pass, with no second model needed. Code edits repeat much of their input, and there it runs about 4.5x the speed of Ollama or LM Studio on the same file; ordinary replies are about a third faster too. It is on by default (vision models included) and switches off per model. A small same-family draft model can be attached per model as well; it is opt-in because a draft that is too large slows ordinary replies down.
- **Sub-agents run side by side.** `[shipped]` The engine serves several requests at once from one loaded model with a shared cache pool (llama.cpp's automatic slots), instead of queueing them one after another as Ollama does by default.
- **Published, reproducible benchmarks.** `[shipped 2026-09-30]` `crates/nekko-bench` runs the same model file at the same quantization through any OpenAI-compatible server (Nekko Agent, Ollama, LM Studio, vLLM where the platform supports it) and reports time to first token, decode and prefill tokens/s, concurrent throughput, a multi-turn agent session and a six-chat rotation. Results are published with the machine they ran on, including where Nekko Agent is behind (the first turn of a brand-new long conversation is still slower than Ollama's); a claim that the numbers do not support is not made.
- **New flags only where the installed engine knows them.** The engine reads its own binary's help once and passes only the flags that build supports, so an engine installed before these changes keeps starting.
