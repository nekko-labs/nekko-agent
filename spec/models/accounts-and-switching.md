# Accounts and switching (2026-10-23)

**Why:** Philip asked for easy account switching for every provider, and for several Claude accounts running in one window, with the docs clear on what Anthropic allows. People keep a work and a personal plan, or a client's API key beside their own, and want each chat on the right one without reconfiguring anything. Decision: [0014](../../docs/decisions/0014-claude-agent-accounts-through-claude-config-dir.md). User docs: [docs/accounts.md](../../docs/accounts.md).

**An account is a provider.** Adding a second provider of the same kind is a second account: another ChatGPT sign-in (told apart by its email), another API key or cloud account (by its label), or another Claude Agent account (by its name). Local model servers are machines, not accounts.

**Switching** `[implemented 2026-10-23; renderer tests]`. When the chat's provider has another enabled account of the same kind, the model picker opens with an **Account** row (`accountSiblings`): one pill per account, the current one checked, named by email or label. A click moves the chat to the same model on that account; an account whose model list lacks the model is greyed with the reason. Nekko-engine providers keep the chat's history, so the conversation continues. For Claude Agent the picker says the switch starts a new Claude Code conversation. New chats start on the last used provider and model (`defaultProviderId`/`defaultModelId`), or the one set with **Set as default**.

**No automatic rotation onto a Claude plan.** Switching is the user's click. Auto's opt-in **Follow capacity & cost** may still run a spent provider's turn on another provider (another ChatGPT plan, say), but never on a Claude Agent: the cross-provider pools leave out `claude-code` providers, and a Claude Agent chat has no Auto.

**Several Claude Agent accounts** `[implemented 2026-10-23; daemon end-to-end test on a fake claude; not yet against two live signed-in accounts]`.

- First connection `[updated 2026-11-06; fixture-tested with a stub bridge, a real install and sign-in not yet run]`: choosing Subscription shows a three-column workflow, **Install Claude Code → Sign in → Connect**, starting at whichever step this computer has reached (a finished step shows what was found: version, then email and plan). One button sits on the current step. Pressing it runs that step and starts each later one as the last finishes: the installer in a terminal in the panel, then Claude Code's browser sign-in, then saving the provider. Nothing runs until the first press, since choosing Subscription is not consent to install or to open a browser. **Hide** on the terminal, picking API, a terminal that cannot open, or a login already connected stops the run and returns the button to the current step. Each step's line fills and the next column lights up; reduced-motion shows the same states without animation. Once connected, the workflow stays only with the success banner; reopening the panel shows the short status line instead.
- Setup `[updated 2026-10-23]`: Add provider → Claude → Subscription connects the usual Claude Code login first. **+ Another subscription account** (also offered before the usual login is connected, #2334) asks for a name, which becomes `claudeAccountName` (lowercase, `[a-z0-9-]`, up to 32), shown as the folder `~/.claude-<name>`. The status check and **Sign in to <Name>** run on that folder, in a terminal inside the panel; the user signs in with Claude Code's own `/login`. Saving makes a provider labelled `Claude subscription · <Name>` with `claudeCode: { account }`. `[#2334; renderer tests]` A normalized name a saved provider already uses (disabled ones included) is refused before sign-in and on save, so another profile's login is never overwritten; a blank name never saves the usual account. Claude Code status reads are keyed by provider and profile and sequence-guarded, so a late answer for one profile can never show as, or authorize saving, another. API connections (Anthropic, Bedrock, Vertex, Foundry) ask for their **Connection name** up front rather than under connection settings, and each save is its own provider.
- Add-account check (`claudeAccountCheck`, shared): `claude auth status` prints a plan login's `email`, `orgId`, `orgName` and `subscriptionType`, which `claude:codeStatus` passes through (`nekko_harness::AuthStatus`). The new login is compared with every connected subscription account. **Same login** (same email, case-insensitive, and same organization): refused with the reason (a second copy could only rotate around plan limits) and a **Sign in with a different account** button. **Another personal plan** (Free, Pro or Max beside a personal plan already connected): Anthropic's "ordinary, individual usage" line is quoted and **Add** stays off until the user ticks "This account is for separate work, not for adding up my limits." **Different person or organization** (a Team or Enterprise seat, or another person): added. The explanation shows only while adding another account.
- Where accounts come from: the Models page keeps every Claude provider in a **Claude** group ("2 subscription accounts through Claude Code, 1 API account"), and each card's line names its source: `Subscription · Claude Code <version> · <folder> · <email> · <plan>`, or `API · Anthropic API key`, `API · Amazon Bedrock · <region>`, `API · Google Vertex AI`, `API · Microsoft Foundry`.
- Engine: nekkod maps the account to `CLAUDE_CONFIG_DIR=~/.claude-<name>` (`nekko_harness::account_config_dir`) for the chat's Claude Code child, for `claude auth status` (`claude:codeStatus(providerId?, account?)`), and for the sign-in terminal (`terminal:create` `claudeAccount`). Only a checked name is accepted, never a path; an invalid one fails the turn instead of using the default login. The account is a launch setting, so a change relaunches the child.
- Sessions: Claude Code keeps a session in its account's folder, so the chat saves `claudeCodeAccount` beside `claudeCodeSessionId` and resumes only a session made under the same account; after a switch the next launch starts a new Claude Code session there.
- Boundaries unchanged: Nekko never reads the folder, never reads, copies or stores the login, never sets a token, never wraps the binary. Plan usage is shown in Claude Code only.

**What Anthropic allows** (as documented 2026-10-23, shown on the docs page as a table and a diagram): your own plan through the unmodified Claude Code, separate accounts for separate people or work, and any number of API keys or cloud accounts are fine; one person holding several Pro or Max plans to add up limits is "ask Anthropic first", since plan limits "assume ordinary, individual usage"; sharing a login, a third-party Claude sign-in or credential handling, and rotating accounts to get around rate limits are not allowed, and Nekko does none of them.

**Nekko Cloud account** `[updated 2026-11-03]`: the one account that is not a provider. It is signed into and deleted in Settings > Sync (**Delete account**, with the account's email typed to confirm); see [End-to-end encrypted sync](../chat/end-to-end-encrypted-sync-for-pro-and-team.md). Provider accounts are removed by removing the provider, and Settings > System > Delete everything removes every sign-in on the computer.

**Not yet:** Claude Agent chats on another computer (today an SSH terminal from Terminal → SSH hosts reaches another machine's Claude Code, as a terminal, not a chat); a live check with two signed-in Claude Code accounts on macOS and Windows.

## Same-email personal and organization subscriptions (#2094, 2026-11-07)

The existing named-profile path is the supported implementation: the same email with a different organization remains a distinct account. Connected-card identity now includes the organization name when Claude Code reports it. The documented `auth status` describes only the current profile; no documented membership-list command was found. Nekko therefore does not list unconnected organizations from one saved login, reuse credentials, or silently choose a billing organization. The user signs in separately through unmodified Claude Code for each named profile, selecting the intended subscription in Anthropic's browser flow where offered. Real same-email multi-organization sign-in remains unverified; [sources, limitations, and manual verification](../../docs/claude-account-selection.md).
