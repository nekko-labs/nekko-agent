# Prompt caching across providers (2026-10-07)

[Implemented; automated provider/host/daemon parity and Windows managed-runtime checks verified; live cloud billing unverified.] Settings > Agent loop offers a persisted Prompt caching switch, enabled for new installs and existing settings that omit the field. Switching it does not shorten context, omit history or tool results, reuse answers, or hide file/memory changes. Every request continues to carry its complete assembled context.

Native cache preparation marks reusable prefixes for Anthropic, OpenRouter Claude, and conservatively supported OpenRouter Gemini text models. OpenAI/ChatGPT and compatible automatic-caching services retain their full requests and expose cache counts only when the service reports them. Ollama and externally managed local servers retain their automatic KV behavior; unsupported remote endpoints are not treated as explicitly cached. Cache thresholds, retention, routing and actual hits remain provider-controlled. Specialized or unknown Gemini models are not given speculative cache directives.

Off removes Nekko explicit cloud cache requests and disables managed llama.cpp request reuse. Managed launch policy changes take effect when the model reloads, using only flags supported by the installed binary. External providers may still cache automatically. Only the current host-owned endpoint receives managed cache controls, never a persisted assertion on an arbitrary endpoint. KV reuse remains in RAM/GPU memory; this feature adds no disk prompt/KV store, external service, or additional prompt recipient. Cloud caches follow the selected provider retention policy.

Usage records and live turn prices distinguish noncached input, cache reads and cache writes, without inventing missing counters. When the engine daemon drives a turn it writes that turn's usage and reply lines itself, in the TS host's exact format, and keeps the subscription-limit snapshots (header capture, throttled polls, failure backoff, quota history) and serves the usage summary; the TS host only renews sign-ins for it and relays limit changes to the phone. Without a daemon the TS services keep doing all of it. `[implemented 2026-10-12, PF14]` Historical records without cache fields retain their existing meaning. TS and Rust loops, sideband calls and supported daemon contracts carry the setting and counters; older daemons fall back to the current TS path. Observed sideband usage is preserved on success, errors and timeouts. Accounting remains best effort across crashes, lost upstream counters, orphaned daemon events lacking attribution, and failed persistence; exactly-once recovery is not implemented.

## Persistent session command logs

Implemented with focused host and renderer tests: `<session-id>.commands.log` sidecars live beside `<session-id>.json` in local session storage. Live terminal events remain immediate; ordered asynchronous appends retain raw command output and ANSI sequences without rewriting session JSON. Snapshot restoration reads only the last 256KB from disk, including when the backend has no live terminal state; appending after restart retains old history. Disk history is append-only without automatic size rotation. Session deletion queues sidecar removal after pending appends and prevents late writes from recreating it. Session discovery ignores sidecars. Disk failures are logged and snapshot reads surface an error rather than implying successful persistence.

Privacy: files contain potentially sensitive command output, remain local with the same data-root access boundaries as sessions, and request owner-only creation permissions where supported. No automatic upload or redaction. Already-lost historical logs cannot be recovered. Pending asynchronous writes can be lost on abrupt process termination; no fsync or power-loss durability guarantee. Desktop backend graceful shutdown drains pending log writes before exit; abrupt termination remains best effort. Process-restart integration and large-log verification are required; filesystem restoration and write-order/deletion/error paths have focused tests. No layout or styling changes in this persistence batch; only the missing-output explanatory text changes.

## Selected native window capture

Native screenshot enumeration requests no thumbnails. Only the chat-selected window is granted to an isolated hidden, non-focusable capture helper, which encodes one native video frame as PNG and stops the stream. This avoids capturing unrelated windows and their Windows Graphics Capture errors. Acquisition and first-frame waits are bounded; unavailable targets fail without restoring or focusing them, changing capture permissions, or substituting another source. Hidden owned-page capture remains separate.

**Windows background fallback** `[implemented 2026-10-16; unit-tested; checked against a real Windows Terminal window WGC refused and a real exclude-from-capture window]`. Windows Graphics Capture refuses some ordinary, same-privilege windows (Windows Terminal is one), which surfaced as `CreateForWindow failed with hr: -2147024891` (E_ACCESSDENIED) and "The OS refused to capture the selected window". For a **screenshot** on Windows, the same selected window is then rendered with GDI `PrintWindow` (PW_RENDERFULLCONTENT) through a hidden PowerShell helper (no native module). The result is labelled `source: native-window-printwindow`. Deliberate refusals are kept: a window that asks not to be captured (display affinity set), a minimized window (never restored), a process elevated above the app, and a frame that renders as a single flat colour all fail with a reason instead of returning an image. Recordings have no fallback. It does not focus, raise or restore anything; checked by comparing the foreground window before and after.
