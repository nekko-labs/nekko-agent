# Models & providers

- **Provider support** `[shipped]`, Anthropic (native), OpenAI-compatible streaming SSE (covers OpenAI/OpenRouter/LM Studio/vLLM), Ollama native (list/pull/ps/load/unload), with OpenRouter presets. Base-URL `/v1` normalization for bare `host:port` entries. `[updated 2026-09-30]` OpenRouter is now a first-class provider rather than a preset: one-click **OAuth sign-in** (PKCE, browser authorize, loopback callback, the returned API key stored host-side and never shown to the renderer) alongside the plain API-key path; its `/key` endpoint validates a credential and reports usage, its model list carries real per-token pricing, its requests identify the app (`HTTP-Referer`, `X-Title`), and its errors (rate limits, exhausted credits, bad key) surface as readable text instead of a raw status. `[updated 2026-10-09]` Anthropic's model list is **live, not compiled in**: `GET /v1/models` lists every model the credential can call, API key or subscription sign-in, under the API's own names and context windows, so a new Claude model appears without an app release. The picker groups it by family, Opus, Sonnet, Fable, Mythos, then Haiku, newest first within each. The built-in list (`[updated 2026-10-10]` now including Haiku 5.5) is the fallback when the call fails, returns nothing, takes longer than five seconds, or no credential is set; the app's model table fills a window the API leaves out. `[implemented 2026-10-22; nekkod integration test]` The live Anthropic and ChatGPT catalogs are reused for five minutes, so opening chat panes, the model picker and `spawn_agent`'s model check share one request instead of each going to the network. The cache is per provider and keyed by its resolved configuration (credential, account, base URL), so a new key or sign-in is asked fresh; the six-hourly model-list check always asks the provider and refreshes it; a fallback list is never kept, so after an outage the next caller tries the live catalog again. A model released upstream can therefore take up to five minutes to appear.
- **Claude Agent: the user's own Claude Code as a provider** `[engine built 2026-10-19; setup UI added 2026-10-19, not yet checked against a live signed-in Claude Code]`. **Adding it:** Add provider shows **Claude Agent** ("Runs your installed Claude Code · sign in there") beside **Claude** ("API key or cloud account · every Nekko feature"). Its setup panel reads `claude --version` and `claude auth status` through nekkod (`claude:codeStatus`, re-read when the window regains focus) and shows one of three states: not installed (link to Anthropic's install guide), installed but signed out (**Open Claude Code to sign in** opens a Nekko terminal running `claude`, where the user types `/login`; Nekko never sees the login), or signed in, naming how (your Claude plan, an Anthropic API key, or a cloud account) with **Add Claude Agent**. Under it, and in the **What works with a Claude plan?** sheet that every greyed control's **Why?** link opens, a comparison table generated from the Claude policy shows what each Claude path can do and who bills it. Scheduling a task on a Claude Agent that runs on a plan shows "Scheduled runs need Claude with an API key." and keeps Create disabled; the capacity panel says **usage shown in Claude Code** for it. Anthropic's terms let a Claude plan power work in another app only through the unmodified Claude Code binary, signed in through Claude Code's own `/login`. So a `claude-code` provider makes Nekko the cockpit around Claude Code instead of a model client: nekkod runs one headless `claude -p` (stream-json both ways, partial messages on) per chat in the chat's folder, with the user's environment unchanged, and maps its stream into Nekko's own events and transcript, so streaming, history, search and the phone work as in any chat. Claude Code's session id is saved on the chat (`claudeCodeSessionId`), so after the 15-minute idle reap, a crash or a restart the next message continues with `--resume`. `[updated 2026-10-22]` The idle reap skips a child that still runs background tasks (Claude Code's `background_tasks_changed`), since ending it would end them. **Wake-ups:** Claude Code starts turns of its own when a background command or sub-agent finishes (`task_notification`, then a whole turn, with nothing written to it). Between turns nekkod watches the child, and such work becomes a Nekko turn of the chat (no user message, the last Claude Agent turn's settings): the chat shows it running, its output lands in the transcript, its permission prompts wait in Nekko's approvals, and a permission prompt that arrives with no turn running (a background sub-agent) starts that turn instead of being refused. A message sent meanwhile waits for it, then runs. `[updated 2026-11-01]` A wake-up reads the child that woke whatever it was launched with: a change of mode, model or folders after the turn applies at the next message. Before this (#1408), a chat whose mode changed after its turn dropped every wake-up as out of date, restarted it about ten times a second, and showed Done while Claude Code kept working unseen. Each message is written with a `uuid` and `--replay-user-messages`, so a turn ends at the `result` that comes after Claude Code took its message up (`command_lifecycle` `started`); output of a wake-up still in the pipe is shown in the turn and no longer ends it one reply early. Before this, a chat whose background tasks finished after its turn refused every later tool call ("No Nekko Agent turn is running for this chat") and answered one reply behind. Verified with a recorded-shape fixture and a fake `claude` end to end in nekkod, and the stream shapes checked against a live Claude Code 2.1.303; the wake-up turn itself not yet run against a live signed-in Claude Code in the app. Stop sends the stream-json interrupt and keeps the process (a process-tree kill only when no answer comes within 5 seconds); Steer interrupts and then sends, since Claude Code only queues a mid-turn message. Every permission prompt goes through the approval bridge (`--permission-prompt-tool mcp__nekko_bridge__approve`, served by `nekko-agent mcp --bridge`) into Nekko's approvals, decided by the chat's mode (Ask: always asks; Guardrails: safe commands and edits inside the chat's folders run; YOLO: Claude Code's `acceptEdits`, only destructive commands and edits outside the folders ask; deny rules block in every mode). Permissions fail closed: without the bridge Claude Code does not start, and a bridge that did not connect stops it before it acts. **Boundaries:** Nekko never reads, copies or stores Claude Code's credentials (sign-in state comes from `claude auth status` only), never sets `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_AUTH_TOKEN`, sets `CLAUDE_CONFIG_DIR` only for a named second account (`[updated 2026-10-23]`, see [Accounts and switching](accounts-and-switching.md)), never patches or wraps the binary, and never passes `--system-prompt`, `--bare`, `--dangerously-skip-permissions` or `bypassPermissions`; `--append-system-prompt` and Nekko's own MCP tools wait for the Claude policy table. **Context window** `[updated 2026-10-20]`: the chat's model is one of Claude Code's aliases (`opus`, `sonnet`, `haiku`); the picker names the selected alias's resolved version once Claude Code reports it after a turn, while unstarted chats say Claude Code chooses the version. The window guess (`guessContextWindow` TS, `guess_context_window` Rust) reads as 1M, since each alias names the newest model of its family; that guess stands only until the chat's first turn. `[updated 2026-10-20]` After each turn the composer's context gauge, the chat's Agent board card and the Context panel's window show **what Claude Code reported**, not Nekko's transcript estimate (which misses Claude Code's own system prompt and tools, about 20k tokens, and never drops when Claude Code compacts): occupancy is the input side (`input_tokens` + cache reads + cache writes) of the turn's last main-thread model call (a sub-agent's calls run in their own context and are left out; `result.usage` sums every call of the turn and is still what usage accounting and turn stats read), and the window is `result.modelUsage[<model>].contextWindow`. nekkod saves them on the chat as `claudeCodeContext` (`used`, `window`, the resolved `model`, and the chat's `modelId` they belong to); they are trusted only while the chat keeps that model, and while a turn runs the gauge adds what the turn has streamed so far. A turn that reports no window (an interrupted one) keeps the last one for the same model. Verified with recorded stream-json fixtures (including a two-call turn) and a fake `claude` end to end in nekkod; not yet against a live signed-in Claude Code, and the gauge moves only at turn end, not after each model call inside a turn. Nekko never compacts these chats (see Context capacity and continuation). **Not yet:** the provider card and setup states (H4), the policy gates (H5), plan detection on launch, and a live run against a signed-in Claude Code; verified so far with recorded stream-json fixtures, a fake `claude` end to end in nekkod, and a signed-out smoke run of the real binary.

- **Runtime control plane** `[shipped 2026-09-09]`, local model servers are started, stopped, and driven from their card rather than merely observed. Ollama is supervised as a child process we own (so it stops with its own handle and never outlives the app); LM Studio uses its real `lms server start|stop` lifecycle; **vLLM is connect-existing only** and says so, because it serves one model per process configured entirely at launch and no machine here can verify a spawn path. What each runtime offers is declared as **capabilities** rather than inferred from its name, so the UI never presents a control a server cannot honour, and a future bundled engine slots in without UI changes. Stopping a process **Nekko Agent did not start** asks for confirmation first and names what it would kill, replacing the previous silent kill-whatever-holds-the-port behaviour; a process we started stops without ceremony. A failed start surfaces the server's own captured output ("address already in use" and "command not found" are different problems), and a runtime that is not installed says so instead of offering a Start button that cannot work.
- **VRAM fit planner** `[shipped 2026-09-09]`, the answer to "will this model fit, where will it run, and why", *before* the load. Weights plus KV cache (`2 x layers x kvHeads x headDim x context x bytesPerElement x parallelSlots`; for a GGUF the engine holds, read layer by layer from the file instead, see below) plus runtime overhead, measured against one memory pool, producing a verdict (fits / tight / spills / will-not-load / **unknown**), the estimated layers that land on the CPU, structured reasons carrying the numbers that drove them, and re-planned one-click fixes. Three honesty rules are load-bearing. **`unknown` is a first-class verdict**: capacity is never inferred from a model's name, so a missing layer count says so rather than producing a confident wrong number. **Unified memory is never double-counted**: on Apple Silicon the budget is system memory, not a card's VRAM plus RAM. And **multiple discrete GPUs are not pooled**, since without tensor parallelism a model must fit on one of them. Where a server reports less than the planner needs (LM Studio publishes no layer geometry), the projection is **partial rather than absent**: the real weights figure is still shown, a will-not-load verdict is still certain when the weights alone overflow the machine, and the missing terms are named. After a load the measured residency is reconciled against the projection and the residual feeds a per-runtime calibration record, so the overhead constant improves with use instead of staying a guess nobody can check.
  - **KV cache read layer by layer** `[implemented 2026-10-23; unit-tested, checked against llama-server b11429 on real files]`. For a GGUF the engine holds, the uniform formula overstated current models several times over (Gemma 4 12B at 32k: 48 GiB of cache, against llama.cpp's 1952 MiB), so the planner called models that run comfortably "will not load". The header's tensor table now gives the cache per layer (`KvLayout`): a recurrent layer of a hybrid model keeps none (Qwen3.5, Qwen3.6), a sliding-window layer holds its window plus one micro-batch per sequence (Gemma 4, gpt-oss), the last `shared_kv_layers` add nothing, and keys without a values tensor count as both. Sized as `llama-server` allocates: the full-attention layers hold the context once however many slots share it; a one-slot load (the engine passes no `--parallel`) runs four sequences over one unified cache, each with its window; `--parallel N` gives each slot `context / N` and its own window. Exact against llama.cpp at 32k for Gemma 4 12B (1 and 2 slots), Qwen3.5 4B and Qwen3.6 35B A3B. Library rows described before this read the layout once on the next listing, keeping everything else. Ollama, LM Studio and vLLM keep the uniform estimate with a cache per slot (Ollama allocates `num_ctx` per parallel request). Not counted: the fixed recurrent state of hybrid models (about 50-250 MiB), inside the overhead allowance. The model recommendations use the same formula ([hardware-aware model recommendations](hardware-aware-model-recommendations.md)).
- **The Nekko engine** `[shipped 2026-09-16]`, the model server Nekko Agent runs itself, so a fresh install can run a model with nothing else present. llama.cpp is acquired from its own releases on explicit consent, with the build chosen from what the GPU probe actually found rather than from the platform (CUDA only where there is an NVIDIA reading, Vulkan for an unidentified GPU, CPU otherwise), and a `llama-server` the user already has is used instead when they point at one. Models come from a short curated list or a Hugging Face search, with each build's real download size, and transfers that **resume**, cancel for real, and land only once the file parses as a GGUF. Serving is **one OpenAI-compatible address** fronting a `llama-server` per loaded model, so several models are resident at once, a request for one that is not loaded loads it, an idle one is evicted, and the address survives every load and unload; port, network binding, API key, CORS, resident limit, idle timeout and models folder are all configurable, with the safe defaults left in place and the two settings that can expose the machine saying so. The controls come in **two surfaces over one state**: one slider asking how much of the machine the model may use, solved through the fit planner into real settings and explained in memory rather than in invented tokens per second, and the full llama.cpp flag set behind it, each moving the other. Reading each file's own GGUF header makes the projection **exact** for a model the engine holds, where another server's model leaves terms unknown. Verified end to end on an RTX 5090: engine installed, Qwen3 4B downloaded, loaded at 32k context taking a measured 7.94 GB against a 7.75 GB projection, and answering through the router at 162-292 tokens per second.
  - **The NVIDIA engine actually uses the GPU on Windows** `[fixed 2026-10-12; unit-tested, repair not yet run on a live machine]`. The CUDA build needs a separate runtime-library archive, and every llama.cpp release carries a Linux one beside the Windows one with the same toolkit and arch. The installer matched on toolkit and arch alone and took the Linux archive, so Windows got `.so` files it cannot load: `llama-server` started, reported healthy, found no CUDA device and ran every model on the CPU, so chats sat on "working" for minutes per reply with no error anywhere. The runtime archive is now matched on platform, toolkit and arch together, and a missing match fails the install with a message rather than taking another platform's. An install already in that state is recognised from its files (a managed Windows CUDA build with no `cublas64_*.dll` beside it) and Model server shows, in words without CUDA in them, that models are running on the processor, with a **Repair engine** button that reinstalls the same build. A reinstall unpacks into a clean folder, cleared only after the new archive has downloaded so a failed download leaves the old engine in place, and the server is stopped only at that moment. Not covered yet: a CUDA build that has its libraries but still finds no GPU (driver too old for the toolkit); that would need the engine's own device list, which is a process launch and too slow for the status poll.

- **Decision models** `[runtime, UI and agent tool shipped 2026-10-01; hosted exports and in-app download implemented 2026-10-17, verified on Windows/DirectML and Linux/CUDA; CoreML on a real Mac not yet verified]`, a decision model answers named, typed questions about a text or JSON state (`choice`, `score`, `noul`) with calibrated probabilities in one forward pass and never generates text. The engine daemon runs **Laya** (open weights, Apache 2.0) natively on ONNX Runtime, on the GPU where it can (DirectML on Windows, CoreML on macOS, CUDA on Linux builds that include it) and on the CPU otherwise, reporting which it used. Requests and answers follow TypeSafe Jev's shape, on `POST /v1/decisions` and `/v1/systemone` at the engine's address, so a Jev client can point at the local engine. Its answers match the reference `laya` package's on a 60-request golden set for each of the three checkpoints (identical model input, same answer on every question in fp16 and fp32). All three Laya checkpoints are offered: **English** (512 tokens), **multilingual** (100+ languages, 1,024 tokens) and **typed decisions** (fine-tuned on four business workflows, 1,024 tokens), as ONNX exports hosted on a release of this repository that is never the app's update feed, every file pinned by size and SHA-256 (the only other public export is wrong). The base models are near chance on some benchmarks zero-shot and ship over-confident, which the answers do not hide. See [docs/decision-models.md](docs/decision-models.md). In the app, Model Server's **Decisions** tab lists the three; **Download** fetches the chosen precision (fp16 recommended) through the engine's download queue, shown with the other downloads and resumable, and refuses any file that is not the published one. It also takes an export folder the user adds (read in place; removing it never deletes files), loads it at a chosen precision and shows the accelerator in use, keeps a TypeSafe key for the hosted **Jev**, and has a Try-it panel with probability bars for either. While either one is available, chat agents get a `decide` tool that sends typed questions to it, so routing, triage and yes/no calls come back as probabilities rather than the chat model's guess.

- **Models from other apps' folders** `[shipped 2026-09-17]`, a GGUF is a GGUF whoever downloaded it, so the library reads the folders the rest of the machine already keeps models in. On first run the usual locations for Ollama, LM Studio, Jan, GPT4All, llama.cpp, KoboldCpp, LocalAI, Bionic, text-generation-webui and the Hugging Face cache (which is what vLLM serves from) are probed, and each one holding models becomes a row. **Ollama needs its own reader**: it files models as content-addressed blobs with no extension, so its manifests are parsed and models appear under the name you would type at `ollama run`. The **Folders** tab is the whole list and every part of it is editable — path, on/off, add, remove — with what each contributes shown beside it. Borrowed folders are **read, never written**: their models load like ours, wear the name of the app they came from, and offer no delete, because the file belongs to that app. Ids stay unique across folders and our own models keep their bare ids, so nothing already saved in a preset or typed into another tool stops resolving.
- **One models surface** `[shipped 2026-09-30]`, the library and the catalog stopped being two tabs and became one search. - **A library that knows what each file is** `[shipped 2026-09-30]`, the model list stops pretending every GGUF is a chat model. Vision rows report whether their `mmproj` projector is present and fetch it, the tokenizer config and any `.jinja` or JSON-embedded chat template are picked up beside the model or from a Nekko-owned companions folder so borrowed folders stay read-only, and a missing split shard or companion fails before `llama-server` ever spawns with a message naming what is absent. `[updated 2026-10-01]` Rows lead with the model's **name** with its file path beneath as secondary text, and the list **groups by the folder each model came from**, so a shelf of twenty models reads as libraries, not paths. - **Load times, groundwork for the model scheduler** `[shipped 2026-11-01, #1462 Phase 0]`. The engine remembers how long each model's last few loads took (the load itself and the whole wait, with the file size and when), across unloads, and reports them on `engine:loadTimes`; nothing in the UI shows them yet. They are what the scheduler will use to start loading a model early enough for a scheduled task. Measured on an RTX 5090: a 5 GB model takes 24 s from a hard disk and 3 s once its file is in memory, and 3.4 s from a fast NVMe, where llama.cpp's load path rather than the disk is the limit ([report](../../reports/model-switching-phase0-2026-11-01.md)). `[Engine test covers retention across unloads and the cap of 8; channel not yet used by the app.]`

- **Effort that follows the model** `[shipped 2026-09-28]`, the effort menu offers the levels the chat's model actually has: Anthropic's five (**Low, Medium, High, Extra high, Max**) on Claude models that take an effort level, and the three temperature steps everywhere else. **Default** follows the model and names the level it resolves to, because that is not the same everywhere (Opus 5.5 defaults to Medium, Opus 5 to High). Claude Opus 5.5 is in the catalog. `[updated 2026-10-02]` On the ChatGPT subscription provider the level goes out as the Codex backend's `reasoning.effort` rung: it rejects `temperature` and `max_output_tokens` outright (a 400 that used to fail every ChatGPT turn), so those are never sent and there is no output cap on that provider. `[updated 2026-10-02]` The same care on the OpenAI-compatible providers (OpenAI API key, OpenRouter, LM Studio, vLLM, llama.cpp, generic servers): an OpenAI reasoning id (o-series, gpt-5 and newer, codex, gpt-oss) sends `reasoning_effort` plus `max_completion_tokens` on the OpenAI API and `reasoning.effort` through OpenRouter, never `temperature`. - **Capacity across every provider** `[shipped 2026-09-28, expanded 2026-09-30]`, a collapsible **Capacity** panel above the resource meters lists every cloud provider that can be measured, with each usage window it reports (bar, percent, time to reset), its credit balance where it has one, and a plain status where it reports nothing. An **Anthropic API key** shows its own per-minute rate limits (requests, input tokens, output tokens) read from the standard rate-limit headers on each reply, so they appear after the provider's first turn and go stale a minute after the last one (`[added 2026-10-19]`). Collapsed, it still shows the single most-spent window anywhere. - **Resource monitors** `[shipped]`, four live monitors, **CPU** load, **memory** use, **GPU** utilization, and **VRAM**, surfaced in two places that never fight for the same corner. A quiet always-on **monitor chip** sits bottom-right on **tabs other than Agent board** (one segment per enabled monitor, plus a VRAM micro-bar); hovering it opens the panel where each monitor is switched on or off and a per-GPU breakdown is shown. The chat's context panel carries the **full monitoring section** at its foot (CPU with core count and processor name, memory used/total with %, GPU utilization, VRAM used/total with % and per-device used/free). While that section is on screen the chip **warps into it**, shrinking, blurring and fading along a path that ends on the section (which answers with a one-shot glow), and flies back out when the panel closes, so the same numbers are never stacked on top of each other. **Switching a monitor off stops the work behind it**: the renderer polls only the probes the enabled monitors need, so turning GPU/VRAM off spawns no GPU probe and turning CPU/memory off samples no CPU times; with all four off the chip reads "Monitors off" and nothing is polled at all. CPU/memory come from `os` (portable, no native module, load measured as a delta between samples like a task manager). The GPU probe is **per platform**: `nvidia-smi` on Windows and Linux, and on **macOS** the accelerator driver's own counters read out of the IO registry (`ioreg -c IOAccelerator`), which needs no admin rights, unlike `powermetrics`. A Mac therefore reports its real GPU ("Apple M1 Max (32-core GPU)", live utilization) instead of the old "No NVIDIA GPU detected". Because Apple Silicon has **no dedicated VRAM**, the memory meter there renames itself **GPU memory**, measures the driver's current allocation against the unified pool, and says "unified with system RAM" so nobody reads it as a discrete card's VRAM; the dock names the probes it used (`os + ioreg`, `os + nvidia-smi`). A machine whose GPU can't be read says so plainly rather than naming a vendor it never checked for. Preferences persist in settings (`AppSettings.monitors`); one shared sampler feeds both surfaces so nothing is probed twice per tick.
