# Chat & cowork (unified surface)

- **Agents (split windows, no tabs)** `[shipped 2026-09-16]` `[renamed 2026-10-03]` `[page removed 2026-10-24; its agent list lives on as the Agent board's list]`, the Chat surface (reached from the **Agent** tab, which wears the Aphelion cat avatar in the rail and sits first in it, above Agent board; the rail is headed by the **cat mark** (the brand icon, see *App icon*), with the "Nekko Agent" wordmark beside it only where no title bar carries it) is a list of **agents**, each one a whole arrangement of windows you switch to as a unit. (They were called workspaces until 2026-10-03; the UI now says agents everywhere, "New agent", "No agents yet", "Close this agent", while the code keeps the workspace name.) An agent opens around a chat and grows whatever that work needs, a file, a terminal, a browser, a file explorer, a second agent, and every window in it is on screen at once: there is **no tab strip anywhere**, so opening a file never costs you sight of the agent that opened it. Windows are arranged as a split tree, up to **8 across and 8 down**, resized by dragging the divider between any two (pointer **capture**, so the drag keeps tracking over a window's own iframe or terminal; a focused divider also moves with the arrow keys) and rearranged by dragging a window's title strip onto any side of another (the target lights the band it would fill; the nearest edge wins, so each corner belongs to its shorter side). A new window is added through the **split compass**: hovering a window's **+** draws that window as a glyph with a target on each of its four sides and a line running out to each, the line under the direction you point at running faster and brighter; pick a side, then pick what goes there (chat, terminal, files, browser). Directions the 8×8 ceiling has used up are visibly spent rather than silently dead.
  - The left sidebar lists workspaces, grouped by project in collapsible folder sections (animated chevron + item-count badge when collapsed, accent-highlighted active workspace, spawned sub-agents nested under their parent). Project-less work sits in a **General** group kept at the **top** of the sidebar (hidden when empty), and a **new chat auto-files under the project it's about** the first time it runs, inferred from its attached folders and first prompt (a confident, non-ambiguous match only; a general chat stays under General). `[updated 2026-10-01]` The sidebar itself resizes horizontally by dragging its divider, bounded between 200 and 480px so it can be a strip of icons or half the window but never either extreme; arrow keys step it on the focused handle, double-click resets it, and the width is remembered between sessions.
  - **No duplicate subagent cards** `[implemented; 49 focused tests, desktop typecheck and isolated Electron before/after checks pass]`. A child rendered beneath an active parent remains a compact subagent row even when its transcript has its own open workspace. Saved parents also retain their nested children. Filtering affects only panel presentation, never closes a workspace or changes a session. Children without a rendered parent, including missing or completed parents, remain reachable through the existing standalone fallback.
  - **Each card says what its agent is running**, in dense lines and without being opened: title with live state (working / waiting on you / stopped) and time since the last reply; the **model** ("Opus 5.5", with its source "Claude" as optional subtext on the next line, `[updated 2026-10-23]` see [view options](../agents/agent-panel-view-options.md)) and how full that chat's **context window** is (`155k/1M`, coloured by fill); the **branch** (with the worktree glyph when the chat works in a linked git worktree) and upstream drift, then a small separator and **each PR the chat made as its own link** (`#264`, coloured by state: open, draft, merged, closed), including the PR the checked-out branch is going into. Past three PRs they fold into a pull-request glyph and the count; hovering it (or clicking, for keyboard and touch) lists every PR with its title and state, each separately clickable. Following a PR link never opens the chat behind it. The project folder is not repeated, since the card already sits under its project's heading, and the uncommitted-file count is gone from the card; sub-agents and window count follow when there are any. The completion check that appears on hover is a size up so it is easy to hit. `[updated 2026-10-03]` The chat window's own header carries the same worktree, branch and PR, from the same cached git read, so the card and the window never disagree. The card uses one quiet surface rather than a different tinted background for each fact. This replaced a single run-info panel at the foot of the sidebar that could only ever describe whichever chat was open. `[updated 2026-09-29]` `[updated 2026-10-02]` Ages read in words that cannot be misread, "5 mins ago" and "3 months ago" rather than "5m" and "3mo", on the card, on the workspace rows and anywhere else a relative time is printed, because a bare m meant minutes in one place and months in the next.
  - Each chat window is independent, with its own provider/model picker, streaming, and Context Inspector, so agents run in parallel. The chat itself opens on a friendly empty state and a **unified composer card**: textarea, attach menu, Queue, and the **send control is Aphelion herself** (the cat avatar, no button fill, lifting on hover) in one rounded surface with a whole-card focus ring. `[updated 2026-10-03]` In the composer, **Tab on a list line indents it** two spaces and **Shift+Tab** takes them back (bullets, numbered items and task lines alike, every selected line at once), which is how a bullet becomes a sub-bullet; on any other line Tab still moves focus as a form expects. A chat that references a project shows a project chip on its window's title strip, so windows from different projects are tellable apart. `[updated 2026-10-02]` The strip reads name, then a `/`, then where it is working (the project chip, the git worktree and branch): the slash leads the location rather than trailing the title, and it stays hidden on a window with no location to name.
- **A resizable composer** `[shipped 2026-09-28]`, the line between the conversation and the composer drags: up gives the message box room for a long prompt, down gives it back to the transcript, which never shrinks below a readable minimum. The size is remembered; double-click the line to go back to growing with what you type.
- **The composer speaks Markdown back** `[shipped 2026-10-01]`, the message bubbles had always rendered Markdown, but the box you type it into did not, so the same syntax looked different on either side of send. Now a mirrored overlay behind the transparent-text textarea styles it while you write: `# ` heading lines, `- ` and `1.` list markers, `**bold**`, `*italic*`, `~~strike~~`, inline `code`, and `#tags`, with the caret still visible and the overlay's scrolling locked to the textarea's, so what you write previews exactly what the bubble will render.
- **Narration stays in the conversation** `[shipped 2026-09-28]`, what the model says between tool calls is written out as part of the conversation instead of folding into the collapsed steps as a "Said" row, and each stretch of steps between two such messages is its own group, so a long run reads as what it said, what it did, what it said next.
- **Questions one at a time** `[shipped 2026-09-28]`, when the agent stops to ask, each question is its own step with Next and Back, in the shape its answer takes (single choice, multi-select, free text), with options as a vertical list rather than wrapping chips.
- **Context capacity and continuation** `[shipped 2026-10-03]`, workspace cards show estimated transcript usage and update every four seconds while a chat is running. The in-chat capacity warning begins at 95%. At that threshold, automatic compaction starts after the active reply completes, summarizes older conversation, and continues in the same session while retaining recent turns where possible. While it runs, the banner shows a progress bar ("Summarizing part 2 of 4") and two buttons: **Send summary to new chat** (the summary, plus the recent turns, starts a new chat with the same project, folders and model, which opens when ready; this chat is left untouched) and **Stop compacting** (nothing changes). Outside a run the banner offers Compact now, Send summary to new chat, and a blank New chat. Compacting never deletes anything: the earlier turns stay readable above a divider ("76 earlier messages compacted"), the latest summary sits open below it, and from then on the model is sent only that summary and what follows it, never the older turns (both the in-process loop and the engine daemon's loop). The context gauge and workspace card count only what is still sent. A long chat that is mostly tool output compacts in minutes rather than never: tool output is clipped to its head and tail before summarizing, chunks are summarized a few at a time at low effort, and each summary call has a four-minute limit that fails with a clear message instead of hanging. `[updated 2026-10-16]` Wherever the engine daemon admits turns (the desktop app and the web, npx and Docker editions), compaction runs in the daemon, which is also what refuses a new reply while a chat compacts; image-generation turns and "send this queued prompt now" run there too, and so do sandbox chats' turns, whose tools run in the daemon's own containers (same rules: ask before every call, only the copied folders, no host tools or context). The editions without the daemon keep the same behavior in the TS host.
  - **Running out of context does not stop the work** `[implemented 2026-10-15; unit, golden and parity tests pass; not yet exercised against a live small-window model]`. Three layers, cheapest first, the same in the in-process loop and the engine daemon's loop:
    1. *Stay inside the window during a reply.* Each turn learns the window the model was actually **loaded** with, not the id's nominal size: LM Studio's loaded context, Ollama's `/api/ps`, the engine's and OpenRouter's advertised context, else the id-based guess. Once a request would pass 80% of that window, the oldest bulky tool outputs (over 600 characters, never the newest four messages) are replaced in what is *sent* with a one-line note saying how long they were and that the tool can be run again, until the prompt is back under 60%. The saved transcript keeps everything. The cut point only moves forward, so consecutive requests share a prefix and prompt caches keep working.
    2. *Retry an overflow once, slimmer.* If the provider still rejects the request as too long for its context (OpenAI's "maximum context length", Anthropic's "prompt is too long", llama.cpp's "exceeds the available context size", and similar), the same request is sent once more with every eligible older tool output left out, before the reply is given up.
    3. *Compact and carry on.* If the reply still ends on an overflow, the host compacts the chat and sends it on by itself with a visible note asking the model to continue from the summary. This is bounded to two automatic continuations in a row (reset by any reply that finishes); past that, or if compaction fails, the chat says why and waits. A reply that finishes with the transcript at 85% of the window is compacted before the next one, even when no chat pane is open (agent watches, queues, the phone). Incognito chats, sub-agents, goal runs, archived chats and chats with queued prompts are never compacted or continued automatically. `[updated 2026-10-20]` Neither are Claude Agent (`claude-code`) chats, by hand or automatically: Claude Code keeps that chat's context in its own session and compacts it itself, so a Nekko summary would never reach it (and the provider has no model API to write one). Compacting one is refused with "Claude Code manages this chat's context and compacts it by itself.", and the in-chat 95% warning is not shown for them.
    The banner for a reply that outgrew its window says "Out of context" in the paused (not failure) colour and explains it carries on by itself; it clears as soon as the continuation starts. Compaction sizes its summary chunks from the loaded window too, so compacting an 8k local model no longer sends it 128k-sized chunks.
- **Runs that keep going when you look away** `[shipped 2026-09-28]`, every chat's live turn is followed app-wide rather than by the window showing it, so switching workspaces no longer drops output, and coming back shows the run exactly where it is. The status under a streaming reply says what it is doing in a few words ("Reading ChatPane.tsx", "Running npm") instead of "Streaming", and sub-agents appear in the plan rail while they work.
- **An editable plan rail** `[shipped 2026-09-28]`, each step of the decoded plan can be typed into and edited in place, dragged to reorder, and assigned to a sub-agent, and an assigned step reaches the agent as an instruction to delegate it. `[updated 2026-09-30]` The rail now also carries the **agent's own plan**: after reading the request the model reports the plan it is actually working through (a live checklist, distinct from the user's editable notes), instead of the rail restating the prompt as bullets.
- **Workspace titles that name the work** `[shipped 2026-09-30]`, a new chat's first reply quietly asks the model for a short task-shaped title ("Fix the CSV import") and applies it to the workspace card and sidebar row, so a list of chats reads as what each one is doing rather than the prompt's first forty characters. It runs after the first turn, never blocks or fails the reply it rode in on, and a title the user typed is never overwritten.
- **In-chat pull requests** `[shipped]`, a chat "has" a PR when a GitHub PR URL shows up in its transcript (the agent runs `gh pr create`, the URL lands in tool output, or the user pastes one). Those PRs surface as **cards inline in the chat**, as **links** on the chat's sidebar card (see the workspace card above), and as **badges** on the chat header (open count, "PR ready" when approved + green, merged count). An open PR's card keeps its info (repo/number, state, diff counts, checks) on the left and parks a **modern, right-aligned action cluster**: **Approve** (a solid green gradient primary), **Decline** (a quiet red ghost), **Review** (a bordered secondary that opens the diff), a subtle violet **Merge**, and a compact "open on GitHub" arrow, each behind a one-click confirm; the info-left / actions-right split keeps the card slim. A merged PR's card becomes a purple, star-dusted "PR merged" banner. `[updated 2026-10-05]` The banner is readable in both themes: every piece of text on it (repository and number, title, the merged label) keeps at least 4.5:1 contrast against the part of the gradient behind it, in light and dark and in each theme preset. The purple wash and star dust stay, but the text colours follow the theme instead of being fixed to light violet, which made the left side of the banner unreadable on a light background. The merged PR badges and links elsewhere in the app meet the same bar. **Review** opens the PR's diff as a window beside the chat (Devin-style, per-file, syntax-tinted). Live state, the diff, and the actions run through the **`gh` CLI**, falling back to the **GitHub REST API** with the GitHub connector's token when `gh` isn't installed; nothing about PRs is tracked or stored by Nekko Agent beyond what the transcript already contains.
- **Hover-expanding nav rail** `[shipped]`, the left icon rail expands over the content on hover (52 → 198px, including 10px extra right padding without reducing button width; springy width + label fade/slide animation) to reveal each destination's name, and collapses back when the pointer leaves; keyboard focus (Tab) expands it too. Its right divider is absent while collapsed for a quieter edge and appears only with the expanded rail, so it never crosses the mascot at rest.
- **Experimental surfaces, opt-in** `[shipped 2026-09-08]`, a new **Settings → Experimental** card holds a toggle per in-progress surface, keeping the sidebar to the stable set by default. **Model training**, **Design board**, and **Memory** each hide their nav destination (rail, phone bottom bar, and the command palette's navigation entries) until switched on; turning one off hides the tab again, and a surface you're standing on lands you on the Agent board instead of a dead end. The flags persist in settings (`AppSettings.experimental`) and apply across every edition, desktop, web, and Docker share the gate.
- **Terminals** `[shipped]`, persistent shell sessions rendered as Warp-style command **blocks** (command + streamed output + exit code + duration). Backed by one long-lived host shell per terminal (PowerShell on Windows, `$SHELL`/bash elsewhere) so cwd/env persist across commands; marker-delimited blocks capture status with no native PTY (honors the no-native-modules rule). Command history (↑/↑), best-effort interrupt, scrollback restore on tab reattach. New-terminal shortcut (Ctrl/⌘+`, the terminal key from VS Code, Cursor, and Zed; Ctrl/⌘+J still works).
- **Workspace prompt surface** `[shipped 2026-10-02]`, an empty chat shows a scrollable model catalog directly in the conversation, with recent models, starred models and the remaining provider lists, plus the multimodal/image choice. The prompt rail shows only the agent's published plan, not a second decomposition of the user's request; changes to the agent's plan are requested by follow-up. Finished sub-agents leave the live workspace list while their chat history remains on disk. Agent command logs are marked finished when their turn ends; the TypeScript fallback shell kills its process tree on Stop or timeout, matching daemon-owned bash cancellation.
- **Sub-agents & orchestration** `[shipped]`, a `spawn_agent` tool lets an agent delegate a scoped sub-task to a fresh child session (own context, same project, inherits the parent's tool-execution mode). An **orchestration strategy** (Settings) governs delegation: `solo` (no sub-agents, `spawn_agent` is withheld), `balanced` (delegate only clearly separable/heavy work, default), or `swarm` (act as orchestrator, proactively decompose into parallel sub-agents). The strategy shapes the system prompt and tool availability; **max nesting depth** and an advisory **parallel** count are configurable. Children stream their own events, and the Agent board renders the full **swarm as a recursive tree** under each agent (live status, descendant counts, click-to-open) and reports the final answer back as the tool result.
- **Streaming chat** `[shipped]`, markdown + code rendering, persisted collapsed reasoning summaries, expandable "Used `<tool>` tool" cards, approval prompts (the full command can be read by hovering it or with a Show full command toggle; implemented, visually unverified), and speech-bubble messages. A turn's **concluding text always surfaces as the answer bubble**, even when the run ends on a tool-calling step (cut short by the loop detector, an abort, or a model that concludes in the same message as its final tool call), so the wrap-up no longer folds into the collapsed activity group and vanishes. **Markdown covers both sides of the conversation**, the user's own messages render it too, since people type dashed lists, `code`, and links into the composer and expect them formatted: bullet and numbered lists (nested by indentation, and recognised even when the run is glued to the sentence above it, no blank line needed), headings, block quotes, rules, pipe tables, fenced code, and inline bold / italic / strikethrough / code / links plus bare-URL autolinking. Single newlines stay line breaks, and snake_case identifiers or `2 * 3 * 4` arithmetic are never mistaken for emphasis.
- **Composer attachments & the + menu** `[shipped]`, paste images directly into the composer or use the **+** menu to add photos, session files, or project folders. The + menu's **Skill** row **expands its skills as a side flyout on hover** (no click needed): every skill this chat can run (built-ins plus installed marketplace skills, starred ones first, each with its description) plus an **Add skill** row that opens the Skills tab. Picking one arms it in the composer exactly as `/name` does, so skills are discoverable by hovering rather than only by knowing to type a slash; a short close-delay lets the pointer cross to the flyout, and Escape closes the flyout before it closes the menu. Pasted and selected images travel with the user message as data URLs and are encoded for multimodal requests by OpenAI-compatible, Anthropic, and Ollama providers. Attachments **live inside the composer card**, a thumbnail strip across its top separated from the textarea by a hairline, so they can never cover the controls above it. Any chat image, thumbnail or full-size preview, has a **right-click menu**: *Copy image* (put on the clipboard as PNG) and *Save image…* (download it). Escape dismisses that menu without closing the preview behind it.
- **Photos from the web in replies, and the photo viewer** `[implemented 2026-10-18; host fetcher unit-tested (56 cases), renderer unit-tested, prompt parity golden-tested; isolated desktop fixture verification in the PR]`. *User intent (2026-10-18):* "support showing remote photos from internet searches. Make sure it's secure and safe. They should be downloadable, copied, etc in the right click menu, and clicking would show the full photo viewer mode. Support showing multiple and they can lazy load in." A Markdown image whose target is an `http(s)` URL (`![alt](https://...)`) renders as a **photo card** instead of a link; two or more such images with nothing else on their lines become a **gallery** of tiles. *Security boundary:* the renderer never loads a remote URL (its CSP stays `img-src 'self' data:`). The host fetches the picture on the `image:fetch` channel (`packages/host/src/remote-image.ts`) and the chat mounts an inert data URL. The host fetch allows http(s) on the default ports only, no URL credentials, and sends no cookies, auth or referrer. Every address the name resolves to must be public: loopback, private, link-local (cloud metadata), CGNAT, multicast, reserved, unique-local, and IPv4 ranges wrapped in NAT64/6to4/Teredo are refused, checked inside the socket's own DNS lookup so a rebinding name cannot slip through. Redirects are followed by hand (at most 5, each re-checked, never https to http), with 10 MB and 20 s caps, and the bytes must sniff as PNG, JPEG, GIF, WebP or AVIF (SVG and HTML are refused whatever the server claims). *Exfiltration rule:* a photo loads by itself only if its exact URL appeared in this chat's tool results (search results, fetched pages, browser output) or a user message. A URL only the model wrote (possibly steered by injected text to carry chat data in its query string) shows a **Load image** button naming the host it would contact. Outside a chat (the file viewer) remote images are always click-to-load. A paired phone cannot call `image:fetch`. *Lazy loading:* a card fetches only once it is within about a screen of the viewport, at most 4 fetches run at once across the app, and fetched photos are cached in memory (60) so the viewer and other cards reuse them; a failure shows the reason and **Retry**. *Viewer:* clicking any chat image (web photo, attachment or generated image) opens the **photo viewer**, which replaces the single-image lightbox: the photo as large as the window allows, its caption and source host, **Copy**, **Save…**, **More…** and Close (Escape or a click outside also close it), plus previous/next buttons, arrow keys and a counter for a gallery. *Right-click menu:* every chat image keeps **Copy image** and **Save image…**; a web photo adds **Copy image address** and **Open original in browser**. Saving names the file after the URL with the real type's extension. Copying or saving a photo that has not loaded yet fetches it through the host under the same rules. *Agent prompt:* the system prompt (TS and Rust, in parity) tells the agent it may show the direct https URL of an image found in a search result, fetched page or browser session, one per line, and never to guess an image URL. *Not done:* the native mobile apps still show alt text only; the Local Web UI uses the same host fetch but only the desktop is verified; there is no on-disk cache.
- **Photo / Video, model-aware attachments, paste anything** `[implemented 2026-10-15; unit-tested and typechecked; isolated visual check pending in the PR]`. The + menu rows carry icons (photo, file, folder, wand) and the first row reads **Photo / Video**. Its state follows the picked model through `modelMediaSupport` (shared): the catalog's `input_modalities` (OpenRouter) wins, then the model id/family (Claude 3+, GPT-4o/4.1/5, o-series, Gemini, Grok, Llama vision, Pixtral, Qwen-VL, LLaVA, Gemma 3+, and the local vision architectures the model library already labels), then the vendor (an unrecognised Anthropic/OpenAI/ChatGPT id counts as sighted). A text-only model greys the row and the menu explains in a sentence ("X can't take photos. Pick a model with vision input to send them."); a model that takes photos but not video says *photos only*; an unclassified local model stays enabled and a toast on attach says the first send will tell. Auto counts as sighted. **Videos** travel on the user message as data URLs (`videos` beside `images` on `ChatMessage`, `SendOptions` and queued prompts; drafts persist them and evict them first under the storage budget; 40 MB cap per clip). OpenAI-compatible servers receive them as `video_url` content parts (what OpenRouter forwards to Gemini and vLLM reads); Anthropic, ChatGPT and Ollama cannot carry video, so the text gets a note naming the omitted clips instead of dropping them silently. The transcript plays attached videos inline (`media-src 'self' data: blob:` added to the renderer CSP). **Paste and drop any file**: Ctrl/⌘+V, the right-click *Paste* action and dropping on the message box all go through one planner (`composerAttachments.ts`). Photos and videos the model can see become pending media; everything else is attached as a file: in place when the OS gives its path (`webUtils.getPathForFile` in the preload; a copied file in Explorer/Finder), otherwise imported through the new `attachment:import` channel to `<dataDir>/attachments/<chat>/` with a sanitised, non-overwriting name (50 MB cap). Unsupported files (PDF, Office, archives, audio, or a photo for a text-only model) are still attached and shown in the composer's strip as a **name only** chip with the reason in its tooltip; the agent sees the name, not the bytes. The strip now also lists the chat's attached file paths with remove buttons. *Not done:* PDF text extraction (chip says so), video for Anthropic/ChatGPT/Ollama (no API for it), Local Web UI has no file paths (everything imports).
- **A picture never bricks a text-only chat** `[implemented 2026-10-16; unit-, golden- and parity-tested (TS + Rust); not yet reproduced against a live llama-server]`. *User intent:* attaching an image to a small local model (Qwen3 4B, no projector) made llama-server reject the request, and because the picture stays in the transcript and is resent each turn, every later message in that chat failed too. *Prevention:* the Nekko engine's `/v1/models` rows now carry `input_modalities` (`['text']`, or `['text','image']` only when the projector was found; omitted for non-chat rows), in both `packages/host/src/engine/server.ts` and `crates/nekko-engine/src/server.rs`. Both provider ports read it into `details.inputModalities` (the Rust port gained the OpenRouter field too), so `modelMediaSupport` answers `no` and the composer greys Photo / Video for such a model instead of the previous `unknown`. *Guard:* each turn resolves `imageInput` from the same cached model list as the context window (`imageInputFor` in `context-window.ts`, `image_input_for` in `nekkod/src/providers.rs`; daemon fact `imageInput`). When it is false, the agent loop (`runAgent` TS, `nekko-loop` Rust) sends `withoutImages` / `without_images` copies: a user message's images and a tool result's screenshots become a one-line note. *Boundaries:* the stored transcript is never modified, so switching to a sighted model resends the pictures; an unknown model (unclassified compat server, no listing) still receives them; the Delete and Restart from here message actions are a separate entry below.
- **Delete a message, Restart from a reply** `[implemented 2026-10-16; unit- and component-tested, isolated before/after captures plus a click-through in a hidden Electron fixture]`. *User intent:* a way to take back the last message without losing the chat, and to make an earlier reply the end of the conversation again. **Delete** appears on the latest user message only (hover row, beside Edit / Reset here) and as **Delete last message** next to Retry in a failed-reply notice. It removes that message and the reply it got. **Restart from here** appears on the last reply of each turn that has something after it (in the reply's Copy row) and removes everything after that reply. Neither re-sends anything; that is the difference from Reset here, which re-runs the message with its pictures. Both confirm first, with a sentence naming how many messages go (`cutPrompt`). Both call the existing `truncateSession` (no new IPC); the cut points come from the pure `messageCuts` (`agent-console/messageCut.ts`), which never reaches behind a compaction summary. Hidden while a reply streams and in archived (read-only) chats. *Boundaries:* the cut is permanent (no undo); deleting an earlier user message is still done with Reset here / Edit.
- **Saved drafts & ready-to-type composer** `[shipped]`, an unsent message is never lost. A window that is closed is unmounted, so the composer's text **and its pending image attachments** are parked per chat and restored when you come back, whether you switched to another workspace, left the Chat view, or quit and reopened the app. Sending or queueing clears the parked draft. Opening a chat also puts the cursor straight in the composer (after any restored text), so a new agent is ready to type into the moment it appears.
- **Metrics bar** `[shipped]`, context used/total with an **expanded by-source token tooltip** (a segmented usage bar plus each source's token count and share of the window, a **Free space** row, and the total, Claude-Code style), tokens/sec, a passive streamed-reasoning indicator (no thinking toggle; cloud thinking stays on and local overrides live under model Expert options), a live **session cost** total plus a per-model **price estimate**, a **subscription-limits chip** for sign-in providers, compact provider/model switching, and an effort cycle (low/normal/high → sampling temperature). The model picker and **⚡ Automate** control live here rather than in the chat header, with the picker immediately to the left of effort.
- **Model auto-mode, with profiles** `[shipped, profiles 2026-07-28]`, a per-chat **✨ Auto (pick best)** option in the model picker, plus an **Auto profile** chip beside it that says how hard Auto leans on capability: **Cheap** (always the smallest capable model, whatever you ask), **Normal** (reads the prompt: complex/coding work gets the strongest model the provider offers, a quick question gets a small fast one), **Quality** (always the strongest available). Favorited models break ties. Auto never picks a model that can't hold a conversation, speech recognition, embeddings, rerankers, OCR, and image models are filtered out, because a local server lists those from the same endpoint as its chat models. The strip shows a live **"→ &lt;model&gt;"** of what the next message will actually run on (with the prompt empty as well as typed) and explains the choice on hover. Persisted per chat (`session.autoModel`, `session.autoQuality`). The Auto profile menu also carries a per-chat **Follow capacity & cost** opt-in `[shipped 2026-09-30]`: when on, Auto may move a turn to an **equivalent or better** model on another provider, either because this provider is spent (a binding usage window rate-limited or past ~95%) or because a same-tier model elsewhere is **materially cheaper** (provider-published prices first, the static table second, local and plan-included providers counting as free, and an unpriced model can never be claimed cheap). The switched pick shows as **"→ &lt;model&gt; · &lt;provider&gt;"** and the turn announces why it moved ("the 5-hour limit is used up", "…does the same tier of work for free"); the send then runs through that provider so usage and cost stay attributable. A provider with no measured limits reads as full headroom but loses ties to a measured one, a candidate below the home pick's capability tier is never taken, and a step up says so. The switch happens before dispatch, never mid-stream, so the transcript and tool state are untouched; it is off by default and disabled in offline chats.

- **Runaway-output backstops** `[shipped 2026-08-13]`, three things now bound a single response, because a local model that degenerates had nothing stopping it (one observed reply streamed 108,790 characters of reasoning, the same sentence 2,534 times, over nine minutes, and locked the window up). An **output cap** is sent to every **local** provider as its native limit (`max_tokens` / `num_predict`; default 8,192, 256–200,000 in Settings → Agent loop), where openai-compat and Ollama requests previously carried none at all and ran until they filled their own context window. `[updated 2026-10-03]` Cloud providers are **not capped**: the same 8k cap had been cutting long Claude and GPT replies off mid-sentence. OpenAI-compatible and Codex requests carry no cap; Anthropic's endpoint requires `max_tokens`, so it is sent the model's own ceiling (64k for Opus 4.5 onwards, Sonnet 3.7 onwards, Haiku 4.5, Fable and Mythos; `[updated 2026-10-10]` 128k for Haiku 5 onwards, #413; 32k for Opus 4 and 4.1 and for ids the app does not recognise), and a 400 that names a lower ceiling (`max_tokens: 64000 > 32000`) is learned for that model and the request goes again. A **repetition guard** watches each stream and cuts it off the moment the output collapses into a cycle, cancelling the request, keeping the useful head of the reply, and ending the turn instead of spending the rest of the step budget on the same loop. And streamed deltas are **batched into frames** rather than committing React state per token, with the live buffers capped, so a fast or runaway reply can't freeze the transcript.
- **Runs survive being cut off** `[shipped]`, a long agent run is checkpointed as it goes, so an interruption costs you the last step rather than all of them. Every completed step (the assistant message and each tool result) is **written to disk the moment it lands**, before the event even reaches the UI, so a run killed mid-flight by a timeout, a dropped connection, a crash, or a quit leaves its finished work on disk instead of only in memory. A reply whose stream breaks **keeps what the model had already written**, marked as cut off, rather than vanishing behind an error (a tool call it was still emitting is dropped: it never ran and its arguments may be truncated). Pressing **Stop** goes through the same path, so a stopped reply keeps its partial answer and reads as "Reply stopped", not as a failure. The failure notice then offers **Resume** as the primary action: the transcript is left exactly as it is, any tool call that never got to run is answered with a stand-in saying so (which is what makes an interrupted transcript valid to send again), and the model is told to continue from where it stopped and not repeat the work above. **Start over** remains beside it as the honest name for the destructive option, which re-answers the prompt from scratch and discards the run. (Before, a timeout on a long chat reported only "Reply failed", and the single **Retry** button truncated the chat back to the last user message, throwing away every step it had completed.)
- **Riding out a dropped network** `[implemented 2026-10-17; core, host and daemon tests pass, not yet tried against a real Wi-Fi drop]`, when the connection itself fails (DNS lookups, an unreachable network, a refused or reset socket, Node's "fetch failed"), a running agent keeps retrying the same model call for up to **65 attempts** with the usual backoff capped near 30 seconds, about half an hour of waiting, instead of giving up after the 5 attempts a provider that answered with an error gets. A laptop that loses Wi-Fi for a few minutes mid-run picks up where it was: each attempt starts the reply over from the last completed step, completed tool calls are never run again. Stop ends the wait at once. When the network is still down after the window, the reply ends as interrupted with its partial answer kept and **Resume** offered, and the model failover (if configured) gets its turn first, as after any exhausted retry. HTTP errors (429, 5xx), a stream that went silent, and auth failures keep the 5-attempt limit. A `spawn_agent` child whose network failure outlasted the window is not resumed again by its parent; the parent is told the child was interrupted. The TS loop (`isNetworkProviderError`, `MAX_NETWORK_STREAM_ATTEMPTS`) and the daemon's (`is_network_error`) classify the same failures, held together by the loop and delegation goldens. Not included: watching the operating system's online/offline signal to pause before a request (an earlier draft did this; nothing reports that signal yet, and pausing would cut the retry window short).
- **Execution-machine internet reachability** `[daemon implemented; shared UI follows; physical network testing unverified]`, native public-model turns use independent, debounced HTTPS reachability checks rather than a browser online flag. Confirmed loss interrupts only model requests; restoration recovery is strict opt-in (default off, additional provider usage may incur charges), bounded to 30 minutes and never replays completed tools. Timestamped notices are display-only metadata and command-log lines, not prompts. Existing provider-specific retries remain unchanged without confirmed machine loss. See [Internet recovery](internet-recovery.md) for destinations/privacy, scope, eligibility and verification limits; #1163/#1164.
- **Lifecycle hooks** `[shipped 2026-10-04]`, your own commands around the agent's actions (Settings → Hooks): **Before a tool** (`PreToolUse`: exit code 2, or `{"decision":"block","reason":"…"}` on stdout, blocks the call and the reason goes back to the model as the tool's error), **After a tool** (`PostToolUse`: whatever the command prints is appended to the tool result for the model, a linter's verdict, a reminder), and **When a reply ends** (`TurnEnd`: finished, failed or stopped, nothing waits on it). Each hook is a shell command that gets the event as JSON on stdin (event, chat id, tool name and input, the result for post-hooks, how the reply ended) and `NEKKO_HOOK_EVENT` in its environment, runs in the chat's workspace, has a tool-name matcher (a regular expression, empty for every tool) and a time limit (60 s by default); a hook that hangs or cannot start never blocks a tool. Since 2026-10-12 a turn the engine daemon drives runs its tool hooks in the daemon (`crates/nekko-tools` `hooks`, the same matching, payload and verdict rules), so tools keep running natively while hooks are on and a busy app no longer delays them; the rules are re-read for every call as before, and a hook that times out has its whole process tree stopped. `TurnEnd` hooks still run in the app (Claude Code's hooks, Codex's `notify`).
- **`fetch_url`** `[shipped 2026-10-04]`, the agent can read a public web page, a README, an API reference or a JSON endpoint without a browser window: one GET (30 s, 2 MB), HTML reduced to text with headings, lists, code and links kept (`label (href)`), JSON and plain text passed through, the first 20,000 characters by default (`max_chars` up to 100,000), binaries refused by name. No scripts, logins or searches; the browser tool remains for pages that need a real browser, and web search stays there until a search provider is chosen. Treated like reading a file: only Ask-everything mode asks first. - **Background processes** `[shipped 2026-10-04]`, the agent can start a dev server, a watcher or a long build and come back to it. `bash` is a round trip with a two-minute limit (and now says so), so agents used to hide long-running commands behind `start /b` or `&`, lose their output and leave them running; `start_process` runs the command detached from the turn under the same shell and guardrails as `bash`, returns an id at once, buffers its output (a megabyte, tail-kept) and mirrors it into the chat's agent terminal, `read_process` hands back what is new since the last read (optionally waiting up to two minutes for more, or listing the chat's processes), and `kill_process` stops one. Eight per chat; they stop with the chat's Stop and when the app quits (Claude Code's `run_in_background`, Codex's exec sessions). Since 2026-10-12 a turn the engine daemon drives starts and reads them in the daemon (`crates/nekko-tools` `process`), where they also die with the daemon, a crash included (its job object on Windows); a chat that uses tool hooks runs them in the daemon too since its hooks moved there.
- **Steer a running reply, and questions that do not wait for ever** `[shipped 2026-10-04]`, the two things a person needs from an agent they are not sitting next to. **Steering**: while a reply runs, **Ctrl/⌘+Enter** in the composer (or **Steer** on a queued follow-up) sends the text into the running turn instead of queuing it or stopping the reply: it joins the transcript as a user message at the next tool boundary, never mid-stream, so the next model call reads it and the work so far is kept (pi's steering queue, typing into a working Claude Code or Codex session). Enter still queues for after the reply; a reply with no tool step left (it was already writing its answer) queues the steering text to run next. Both loops take it (`pullSteering` in the TS loop, `loop:steer` into the daemon run's inbox). **Unattended questions**: Settings → Agent loop → *Unattended questions: decide after N minutes* (default 0, wait for ever) puts a limit on how long an `ask_user` question waits; past it the agent is told nobody answered and to choose the most reasonable, least destructive option itself and state the assumption, so four chats left running overnight do not each park on a question. Approvals of risky commands never time out this way.
- **Runs never left hanging** `[shipped 2026-10-04]`, a reply that stops making progress now ends, says why, and can be continued, instead of sitting on "thinking" for hours (the 2026-10-04 incident: two overnight Claude-subscription chats went quiet mid-tool and were found the next morning still "running"). Four safeguards, in both loops (the TS loop and the Rust daemon): **a stream idle limit**, a model response that sends nothing for five minutes (Codex's default too; `NEKKO_STREAM_IDLE_MS` changes it, 0 disables) is cut and counts as a transient failure, and the daemon's HTTP client also gives up on a connection that does not open in 30 s; **transient failures are sent again**, an overloaded provider (529), a rate limit (429), a 5xx, a dropped connection or a stalled stream gets up to five attempts with backoff (1 s doubling to 30 s, the provider's `retry-after` honoured, jitter so parallel chats spread out), each attempt regenerating the step from scratch, and the chat shows **Retrying (2 of 5, in 4 s: anthropic 529 …)** in its step rail while the partial text of the failed attempt is dropped; anything else (a 401, a 400 about the request) ends the reply as before, and Stop ends a backoff at once. (Fixed 2026-10-24: a failed send reached the loop already rewritten as "Can't reach ChatGPT at …" or "Can't reach the model server at …", which the classifier did not recognise, so those replies failed on the first network blip with no retry. That wording now counts as a network failure, and the daemon logs the underlying cause to `nekkod.log`.) **The tool request is checkpointed before the tools run** (`step` event), so a shell command, MCP call or sub-agent that never returns leaves the assistant message that asked for it on disk rather than losing the step. **A chat the app was closed on knows it**: the session carries `activeRun` while a turn runs; a host that starts and finds one appends an interrupted note ("The app closed while this reply was running") and the chat opens on a **Reply interrupted** notice with **Continue** / **Start over**, read from the transcript itself (any transcript ending on an unanswered tool call or an `interrupted` reply shows it), where before a restart showed a silently cut-off chat with no way to resume. Also: a daemon-driven run whose events stop is probed (`loop:alive`) every 30 s and ended as interrupted when the daemon restarted or cannot be reached; a run the daemon drives for a host that has since restarted still gets its checkpoints saved; Stop on a parent chat stops the sub-agents it spawned (they used to run on, and the parent's turn waited for them); streamable-HTTP MCP calls time out after ten minutes.
- **No tool-step limit** `[shipped 2026-10-03]`, replies have no tool-step limit at all; the concept was removed (no setting, no budget option in the TS loop or the Rust daemon, no `step_limit` stop). A reply runs until the model stops calling tools, a safeguard trips, a stream fails, or the user presses Stop.
