# Chat isolation and prompt customization

- New online, persisted chats use a dedicated Git branch/worktree for each selected repository, provisioned on first send after project selection. `[updated 2026-10-03]` The checkout's folder and branch are named in words rather than after the chat's id: `nekko/brisk-amber-otter` (an adjective, a colour and an animal, drawn at random and kept unique per repository), or a slug of the chat's title when the user or the agent has already chosen one (`nekko/fix-login-bug`, `-2` on a collision), since a new chat is usually provisioned before its title exists. Settings > Git management maps each folder back to its chat through the chat's own record of the checkout; folders named the old way still resolve. Existing chats are not moved; sub-agents share their parent's checkout. Non-Git folders remain ordinary folders. Provisioning failures stop the turn rather than falling back to a shared checkout.
- This is what lets several agent chats work on one repository at the same time: each has its own branch and folder, so their edits, builds and commits never collide with each other or with the user's own checkout. Terminals opened beside a chat (split from its pane) and its Agent commands log start in the chat's worktree.
- **Agent command log availability** `[implemented; desktop visual verification pending]`: the read-only Agent commands terminal contains shell/setup/background-command output, not the full agent transcript. Logs are created on first command and retained only in backend memory, so a restored chat after a backend restart may have no command snapshot. A missing/empty snapshot explains this instead of silently showing a blank terminal; a failed read shows an unavailable/retry message. First live output replaces the notice, and commands in subsequent turns reactivate the same log without dropping retained output. Snapshots remain local for `agent_` terminals even with daemon-owned PTYs; no new persistence or cross-chat access is introduced. Focused regression tests cover snapshot absence/failure, retained replay, first live output, and turn reactivation.
- A fresh worktree has only tracked files, so each project can name a **worktree setup command** (Settings > Git management, e.g. `npm install`) that runs in a new chat checkout before its first turn, with output in the chat's Agent commands terminal. A failed or timed-out setup (15 minutes) is reported in the chat's checkout notice rather than stopping the chat. Ignored local files the work needs, such as `.env`, are copied in when listed in a `.worktreeinclude` file at the repository root (gitignore syntax, the same file Claude Code reads); only paths that are both listed and gitignored are copied, and nothing is overwritten.
- Settings > Git management lists every chat worktree across the configured projects, including those of deleted chats, with branch, uncommitted-file count and commits not yet on the main checkout. **Remove** frees the folder: it is refused while the chat runs or has uncommitted changes, and the branch is deleted only when fully merged. A chat whose worktree was removed restores it from its branch (or from HEAD if the merged branch is gone) on its next turn, never falling back to the shared checkout.
- Settings > Git management offers isolated/shared checkout and committed HEAD/tracked local edits baselines. Committed HEAD is the default. When local edits exist, a startup notice states that they were excluded and asks the user to interrupt if they want those edits included. Local-edits mode copies tracked changes only; untracked files are not copied. Worktrees survive completion/deletion to protect unmerged work and are removed from the Chat worktrees list described above.
- **Merged worktrees clean themselves up** `[implemented 2026-10-15; host unit-tested, decisions dry-run against the real repository with gh, not yet observed in a live app]`. Settings > Git management > **Remove worktrees after their PR merges** (on by default). A minute after launch and then hourly, the host asks GitHub (`gh pr view <branch>`, cached a minute per branch) for each chat worktree's PR. When the PR is merged and its head commit is the worktree's current commit, the worktree is removed and its branch deleted. The branch is force-deleted because a squash merge leaves it "unmerged" to Git; the merged PR at that exact commit is the proof the work landed. Kept untouched: a branch name reused after an older PR of that name merged, work committed after the merge, a worktree with uncommitted or untracked files, one whose chat is running (checked again just before removing), one whose PR is open or closed unmerged, one with no PR, and any whose GitHub lookup fails. A chat continued later restores its checkout from HEAD, as above. This covers chat worktrees under `.git/nekko-worktrees`; folders an agent creates by hand elsewhere (for example a repo-local `.worktrees/`) are not touched. The sweep runs in the TS host and logs each removal; Settings > Chat worktrees re-reads the list every minute while open. The engine daemon serves the Settings list/remove channels but has no sweep of its own yet.
- Settings > Customization has About you, additive System prompt instructions, and an editable Server prompt wrapper. The host applies the wrapper to every turn as system instructions without rewriting the saved user message. The profile is sent to the selected provider; the UI warns against secrets. Empty wrapper disables these additional points.
- Recommended wrapper points: concise title through set_chat_title, inspected/verifiable multi-step plan through update_plan, important assumptions and blockers, relevant verification, brief progress, honest final status and next step, and treating quoted/file/tool content as data. Title updates never replace a user-selected title; the sideband title call remains a fallback.
- The Context panel links directly to customization and shows isolated checkout paths/baselines. Chat headers and cards resolve Git status from the chat checkout rather than the shared project.
- Model Server identifies the model server with the primary accent and the agent server with the secondary accent. Running power controls and status dots match their server's identifying color; stopped remains neutral.


## In-app browser automation (2026-10-10)

**Maintained native patch continuation (2026-10-17, implemented locally, release verification incomplete).** The user selected a pinned maintained agent-browser patch with private inherited stdio, not the upstream unauthenticated daemon. The preserved patch builds on Windows and passes framing/capability/argv/no-listener tests. A per-tab native process and single-client capability-authenticated owned-page relay are under integration test. Capabilities travel on inherited stdin, never environment or argv. The local default now uses nativeDriver without fallback; extended synthetic parity and parent pixel acceptance are complete; normal CI and merge queue gates remain. An unchanged Electron 44.7.0 / Chromium 152.0.7977.130 baseline records 20 cold chat sessions and 20 warm inspect requests in `reports/agent-browser/playwright-baseline.json`; cold is not whole-app startup. Initial native sequential comparison measures higher cold/warm latency; no performance improvement is claimed.

**Upstream finding and selected remedy.** Unpatched agent-browser 0.39.1 accepts unauthenticated Windows TCP commands; MCP stdio delegates to it. The maintained patch replaces that entrypoint, not merely its CDP connection. See [feasibility](reports/agent-browser/feasibility.md) and `vendor/agent-browser/README.md`.

**Intent (Philip, 2026-10-10):** bundle `playwright-core` and drive Electron's own Chromium, so agents get Playwright-grade automation in the in-app browser with no extra browser download.

**What agents can do.** The `browser` tool in dedicated mode keeps its original actions (navigate, inspect, click, fill, close; same outputs, the first matching element as before) and adds: `wait` (a selector or visible text reaching visible, attached, hidden or detached, at most 20 s), `type` (keyboard text into a selector or the focused element), `press` (one key or chord such as Enter or Control+A), `scroll` (a direction and pixel amount, or a selector into view), `extract` (innerText of a selector, or the page's links as label and URL), `evaluate` (a JavaScript expression in the page, result returned as JSON and capped at 6,000 characters), `screenshot` (the active tab's rendered page attached to the chat's images, never base64 in the text, 5 MB cap), `tabs`, `tab_new`, `tab_switch`, `tab_close` (up to 8 tabs per chat, each a hidden window in the chat's partition) and `logs` (console messages, page errors, failed requests and HTTP 4xx/5xx since the last `logs` call). Clicks and fills now use pinned native agent-browser interaction checks and real in-page input events instead of `element.click()` and a value setter. Existing mode (Stagehand over a user-started CDP port) keeps the original five actions and refuses the new ones with a pointer to dedicated mode. Web, server, CLI and sandboxed sessions still answer that browser control needs a local desktop chat; no Chromium is downloaded anywhere.

**Engine and security decision.** Native agent-browser connects to a single-use capability-authenticated loopback WebSocket relay per owned tab. The relay speaks CDP through Electron webContents.debugger and AgentCdpTransport, never an app-wide debugging port. The process command capability and relay URL are delivered only on inherited stdin. The only compiled native binary entrypoint rejects all argv and inherited agent-browser configuration, frames commands and responses at 1 MiB, allows only a bounded action vocabulary and rejects implicit browser launch.

- **The UI cannot be targeted.** Native discovery returns only the adopted tab. Flattened attachment accepts only its target id; browser-target attachment, contexts, permissions and global domains are denied. No global Electron enumeration occurs in the relay. Missing/wrong auth, renderer Origin and second connections fail closed.
- **Per-chat isolation.** Each chat retains its ephemeral partition and up to eight windows. Each tab has its own native process and relay; tab bookkeeping stays in the bridge.
- **Command policy.** Existing page-domain and file/navigation/download/certificate restrictions remain in AgentCdpTransport. Downloads remain denied by the partition regardless of acknowledged CDP setup calls.
- **Who sends the actions (2026-10-12).** A turn the engine daemon drives runs the `browser` and `capture` tools in the daemon (`crates/nekko-web`): the checks, the approval prompt and the bridge request are the TS host's, held to it by a golden set, and the daemon reaches the in-app browser and the window capturer through the same private bridge, whose address and token the desktop app hands the daemon in its launch config (never its environment, so the agent's own shell commands never see the token). Existing mode, the user's own Chromium on a loopback DevTools port the user enabled, no longer goes through Stagehand and Playwright in Node: a small CDP client in the daemon attaches to the most recently active page for each action (navigate waits for load, click is a left click at the centre of the one matching element, fill clears the field and inserts the value, then the title and the first 6,000 characters of text come back), CSS selectors only, refusing a selector that matches several elements as Playwright's strict locators do, refusing a DevTools endpoint that points off this machine, and disconnecting on `close` without closing the browser. Verified against a real headless Chromium (`crates/nekko-web/tests/cdp_live.rs`).
- **Existing guardrails unchanged.** Approval before every action (the approval names the evaluate expression and discloses that screenshot pixels go to the model), HTTP(S) only, popups denied, dialogs disabled, permissions denied, sandboxed renderer with context isolation and no Node, hidden non-focusable windows, idle reaping after 10 minutes, the private token-authenticated loopback bridge as the only entry point (it carries no CDP), and the window's debugger detached before the window is destroyed (destroying an attached window stalls Electron's main thread).
- **Residual risk.** `evaluate` runs arbitrary script in the page, so "read-only" is guidance to the model, not enforcement; the page is a sandboxed web renderer with no app access, and the approval shows the expression. A page can still see what the agent types into it.

**Packaging.** `node scripts/build-agent-browser.mjs` checks out the exact vendored pin, verifies the maintained patch and entrypoint, and runs Cargo locked release. Dist/release stage the binary, upstream license and pin under resources/agent-browser/platform-arch, outside asar. Desktop dev/start lifecycle hooks also build and stage the verified native source before launch. Native launch errors are surfaced with no Playwright fallback. Screenshots must preserve real viewport scrollbars and page layout without persistent DOM or emulation changes; owned hidden Electron compositor capture with a two-frame rendering barrier passed parent actual-pixel inspection of the matched v3 pair (1359x872) after a scrollbar mismatch in the initial evidence. Capture CI builds and stages the pinned native resource with a source-keyed Cargo cache, retaining source/patch verification and locked release builds on cache hits. Vendored verification inputs and source Git operations use explicit LF line endings so Windows checkout defaults cannot alter exact patch verification. The explicit Playwright driver remains only for reproducible baseline tests, not imported into production main. Installer/signing and non-Windows architectures remain unverified.

**Speed of a whole task (2026-10-18).** `[implemented; measured on Windows; macOS and Linux not measured]` User intent: an agent's browser task should take about as long as the page needs, not seconds of waiting on the tool. A hidden agent window that has gone idle renders about one frame a second, so a click (acknowledged on the next frame) took about 1 s and a screenshot (which waits two frames) about 2 s; Playwright's screenshot never finished. The bridge now keeps frames coming for just the duration of a click or screenshot on a hidden tab; the window stays hidden, nothing is subscribed between actions, and visible windows are untouched. Acceptance: on the synthetic signup flow (navigate, locate, fill, submit, verify, screenshot; 10 tool calls), a fresh chat's flow is 466 ms p50 instead of 3,322 ms, clicks about 11 ms and screenshots about 38 ms, with the same pixels apart from a blinking caret. The bridge also reports per-request phase timings (window, relay, native spawn, CDP attach, navigate, summary) to an optional diagnostics listener; they never reach the model. Measured by `scripts/agent-browser-flow-benchmark.mjs`; see `reports/agent-browser/flow-benchmark.md`.

**Snapshots and element refs (2026-10-18).** `[implemented; unit, golden and hidden-Electron tested on Windows; not yet observed with a live model]` User intent: an agent on an unfamiliar page should see what it can act on without writing a script, and act on it without guessing CSS. `snapshot` (dedicated mode) returns the page title and a compact list of interactive elements from the accessibility tree, one per line with role, name, state and a ref (`- textbox "Email" [required, ref=e43]`), capped at 6,000 characters like other replies; an optional CSS `selector` snapshots part of the page. A ref (`@e43`) works as the selector for click, fill, type, press, wait and extract; it is resolved by the native agent-browser process from its accessibility node, never by `querySelector`. Refs expire when the page changes: an unknown or stale ref fails with advice to take a new snapshot, and a ref that no longer resolves counts as detached for `wait`. Refs are refused for `scroll` (click, fill and type on a ref already scroll it into view) and as a snapshot scope. Existing mode does not offer `snapshot`. Same approval as every other action. Validation is shared by the TS host and the engine daemon (golden parity). Acceptance, measured on the synthetic signup flow (`reports/agent-browser/snapshot-refs.md`): the same 10 tool calls and retries as listing controls with `evaluate`, no script for the model to write, comparable time; a whole-page snapshot is the largest reply in the flow, a snapshot scoped to `main` is smaller.

**Status.** Native default implemented and tested in isolated hidden Electron synthetic fixtures. Full workspace typecheck/build pass; all 1362 desktop tests pass. Native smoke covers waits in four states, duplicate-selector first match, keyboard submission, extraction, page errors and HTTP/console logs, tabs, screenshots, popup/dialog/permission and file-navigation boundaries. Parent inspected both final v3 baseline/native actual pixels via owned browser capture (1359x872 rendered): heading, input and orange focus, submitted result, links, late text, right scrollbar and layout match. Visual signoff is granted for this synthetic browser surface only, not the full packaged/native app. Cancelled-download and Control+A/replacement checks pass. Full/signed installer, live model and macOS/Linux/arm64 runtime remain unverified.

## Browser approvals and token-speed accuracy

Dedicated browser tool sessions open an isolated, sandboxed Chromium window owned by Nekko, not Edge or another external browser application, driven by pinned native agent-browser through an authenticated owned-page relay (no debugging port; see *In-app browser automation*). Every action still needs explicit approval. Existing mode remains an explicit attachment to a user-enabled local CDP browser. Browser tool windows deny popups, downloads and device permissions and use ephemeral storage separate from the app and personal browser.

Token speed is shown only for turns with usable timing for every nonempty output step. Sub-100 ms buffered samples and missing timings hide the rate rather than pairing untimed tokens with other steps timings. Approval/tool waits do not enter decode time. Starting a new turn clears the previous speed.

## App control and isolated sessions (implemented subset; planned and unverified boundaries)

Normal is the default execution environment. The composer Mode menu has two independent columns: permission policy (Ask, Guardrails marked Recommended, YOLO) and environment (Normal, Sandboxed). Normal sessions may use already connected capabilities within their permissions; requesting a new app or connection prompts the user before it is connected. Settings groups app-control grants under Permissions, off until enabled and scoped to explicitly selected apps. Nekko Agent itself can be granted control, without an exemption for permission changes or other sensitive actions. Prefer semantic/accessibility control and the built-in browser over blind desktop coordinates. Revocation and Stop prevent subsequent actions.

Implemented subset: selecting Sandboxed opens consent-based setup for an already installed, running Linux Docker engine and an explicitly digest-pinned local image containing Python 3 and /bin/sh. Setup does not install a runtime, start its service or pull an image. Missing prerequisites fail closed with no host fallback. Managed installation and Podman, OrbStack and Apple container support remain planned, not available.


Indirect sandbox boundary: session-scoped host terminals, background processes, file explorer access, spec reads/writes and MCP calls are unsupported and denied before host side effects. Unscoped user file/terminal APIs remain host-only APIs, not sandbox capabilities. Direct daemon native loops reject sandbox declarations and persisted sandbox sessions. Daemon session creation and execution-policy patches route to the owning host so persisted new-chat defaults and setup preconditions are authoritative. Setup itself transitions an empty idle chat into sandbox mode; legacy gitIsolation patches cannot downgrade it. Session-scoped image generation is denied. Sandbox send context excludes host memory. Malformed or missing scoped daemon session lookups fail closed. Apply-back remains disabled at both the router and low-level executor because concurrent external host writes cannot be excluded; baseline hashes and advisory locks are not proof of exclusive ownership. A safe ownership/transaction design is required before enabling it. Regression tests verify denied replacements, additions and deletions preserve external host edits. Tool cancellation now owns its signal before readiness checks, rejects overlapping tool calls and passes AbortSignal to the Docker CLI; container kill remains best-effort and full host cancellation/recovery acceptance is unverified. Container file and bash tools remain the scoped execution path. Focused guard tests cover file/process denial; full caller propagation, container integration and Rust verification remain subject to the checks recorded with implementation.

A new sandbox begins in Ask. The implemented executor supports only seven scoped file/shell tools: read_file, write_file, edit_file, glob, grep, list_dir and bash. MCP, connectors, network, browser and delegation are denied, not available grants. Prompt for each required capability and action; users may choose Guardrails with sandbox settings or YOLO, but neither policy widens the isolation boundary or grants host access. Selected provider requests remain host-side; provider credentials are not injected into the container. Narrow connector brokers are planned, not implemented. Sandbox sessions cannot control host apps, including the host Nekko Agent window. A browser used in a sandbox must live inside its isolated environment. Since 2026-10-12 the engine daemon owns the containers (`crates/nekko-sandbox`, `crates/nekkod/src/sandbox.rs`): setup, status, the diff, cleanup and every tool call run there with the same isolation checks, and a Stop during a command stops the container itself. The reply still runs in the app, which asks before each call and sends it to the daemon.

Explicitly provided folders are copied into the isolated session, not mounted read-write. Work stays in the copy. Diff inspection exists at the executor boundary, but safe apply-back is planned and disabled: detecting baseline changes alone cannot exclude concurrent external writes. A verified ownership/transaction design is required before host writes can be enabled. All tool paths, MCP processes, delegated sessions, file context, terminal commands, previews and connector retrieval must honor the same session capabilities. No host filesystem, Docker socket, privileged container, host networking or unselected connector access is allowed. Containerization is a bounded isolation mechanism, not a promise against every kernel/runtime vulnerability.

Availability: the Normal/Sandboxed menu separates execution environment from Ask/Guardrails/YOLO permissions, persists new-chat defaults, and provides Docker setup UI. The container executor copies selected plain files into an owned volume with no host bind mounts, host networking or Docker socket; it checks container identity, limits and isolation before operations. Indirect host file/process/spec/MCP entry points fail closed for scoped sandbox sessions. Focused live renderer checks (24), real Docker checks (11) and Rust checks (9) are reported passed for this batch. Cleanup UI now requires explicit destructive consent and passes the persisted sandbox identity through both transports; idle-only cleanup verifies ownership labels and handles stopped containers, partial creation and host restart without modifying source folders. Reconnect verifies existing running resources rather than recopying; destroyed/stopped sandbox continuation requires a newly configured chat. Mocked transport-to-host-to-container-runner Stop propagation and cleared active-run state are tested, alongside readiness signal ownership and overlap denial. Real Docker cancellation/cleanup and restart acceptance, exhaustive indirect payload regressions, multi-platform behavior and actual desktop visual acceptance remain unverified. Send/indirect enumeration and ownership design limits are recorded in reports/pr398-lifecycle-audit.md. Hidden cleanup renderer interactions pass, but generated captures are not pixel-inspected because no image/video viewing tool is available. Captured wide/narrow light/dark screenshots await parent inspection. App-control adapters and broad sandbox capability brokers remain planned. This is an incomplete working sandbox, not shipped safe apply-back or a universal isolation guarantee.
