# End-to-end encrypted sync for Pro and Enterprise (2026-10-22)

`[implemented 2026-10-22 and tested end to end against the local Nekko Cloud stack; not live: the Supabase project isn't connected, Nekko Cloud isn't deployed with it, no outside cryptography review yet; the iPhone screens build only on macOS CI]` Design and threat model: [docs/SYNC-ENCRYPTION.md](../../docs/SYNC-ENCRYPTION.md). Decisions: [0005](../../docs/decisions/0005-supabase-for-identity-only.md), [0006](../../docs/decisions/0006-recovery-key-as-a-p256-key-and-sealed-account-record.md), [0007](../../docs/decisions/0007-lockout-recovery-without-a-vendor-key.md).

**User intent, round 2 (2026-10-22):** Philip asked to build the rest: Nekko Cloud sign-in with "our Supabase auth", a custom login screen in the existing design language, "a nice animated visual for the syncing", the sync engine and Settings → Sync on the computer, the iPhone's sync screens, the offline research key and an outside cryptography review; and to find out what other companies do for people who get locked out ("are they storing a backup key for the users?").

**User intent:** Philip asked (2026-10-22) for end-to-end encryption, "extremely secure", for storing and syncing messages on the server, as a Pro-and-up feature: Nekko Labs must not be able to see users' messages unless they explicitly allow us to use them to improve the app anonymously, and even then the data stays encrypted.

**Decisions:**
- **Zero-knowledge by construction.** Chats are sealed on the user's devices; Nekko Cloud stores only ciphertext, Padmé-padded sizes, keyed-hash object ids, revisions and device public keys. Keys: a 64-byte keyring per key epoch (record key ‖ id key) wrapped to each device's P-256 key (Secure Enclave on iPhone) and to a 256-bit recovery key; one AES-256-GCM key per record revision via HKDF from a fresh salt; account, epoch, collection, object id and revision bound as associated data (no relabelling or rollback).
- **No password recovery.** The only recovery is the recovery key shown once (55 Crockford base32 characters with a checksum). A password-derived key could be brute-forced by the server, which holds the wrapped keyring. Losing every device and the recovery key loses the synced copy, by design.
- **Revocation rotates.** Revoking a device kills its tokens and wraps; the remaining devices start a new key epoch, and Cloud accepts writes only under the newest one.
- **Pro and Enterprise only for writes; never locked out of your own data.** Free keeps everything local. After a downgrade, pull, decrypt and *Delete everything synced* keep working; only uploads stop. Storage: Pro 5 GB, Enterprise 20 GB per account (encrypted bytes).
- **Help improve Nekko Agent stays encrypted.** Off by default; turning it off changes no feature. The user picks what to share, the device redacts it, and seals it to Nekko Labs' research key, whose private half is offline only. Uploads carry no account, device or IP (unauthenticated route, request logging off, day-granular date), can be withdrawn with a delete token the device keeps, and expire after 180 days. Opting in never gives Nekko Labs the sync keys.
- **Adding a device needs the recovery key or an existing device.** By approval, the new device shows a one-time 16-character join code and the user types it on a syncing device: the code checks the new device's key there and the approver on the new device, so neither the server nor someone signed in to the account can get a key trusted ([decision 0008](../../docs/decisions/0008-authenticated-wraps-and-join-codes.md)).
- **Keys come only from trusted devices.** Keyring wraps are authenticated by the sending device. A device takes a newer key epoch only from a device its current epoch's sealed account record trusts, accepts records only under the epoch it holds, and never accepts an older revision than one it has seen. Removing a device starts a new epoch and seals every chat again under it.
- **Sign-in: Supabase Auth for identity only** (decision 0005). Email 6-digit code, or Apple, GitHub and Google in the browser with PKCE (loopback redirect on the computer, `nekko-agent://cloud-callback` on the iPhone). The Supabase access token is traded once for a per-device `nk_` token (180 days from last use) and dropped; the account, plan and all data stay in Nekko Cloud's Postgres. A beta signup's user is linked by email on first sign-in. `[updated 2026-11-01]` Only a proven address links (or moves) an account: a sign-in by an emailed code or link, or one whose Supabase Auth user record has `email_confirmed_at` for that address (looked up with the session at `/auth/v1/user`); `user_metadata`, which the user can write, is never taken as proof.
- **The recovery key is a P-256 key pair; the account record is sealed** (decision 0006). Each key epoch is sealed to the recovery key's public half, so devices never hold the recovery secret and rotations stay recoverable. A sealed account record lists the trusted devices and pins the recovery public key; rotation wraps only to devices in it.
- **What syncs:** every chat except incognito chats (never) and chats whose **Sync** switch is off (`syncOff`, per chat; until 2026-11-19 Local only mode chats were left out unless Settings → Sync included them). Pictures travel as their own `picture` records (since 2026-11-25, see below; before that they were left out); a chat whose text is over 16 MB is skipped and counted (1 MB until 2026-11-19). Newest `updatedAt` wins; a chat a turn is running in is never overwritten. Deletions sync as sealed tombstones. The iPhone reads synced chats (offline too) and approves devices; it doesn't change chats.
- **Where keys live:** macOS Keychain, Windows Credential Manager, a 0600 file on Linux, and on the iPhone a Secure Enclave key-agreement key (no Face ID per use: sync runs in the background and the app lock covers reading) plus the Keychain, this device only. A phone paired to a computer can never call the computer's `cloud:` or `sync:` channels.
- **Lockout** (decision 0007): no key Nekko Labs can use alone, ever. Today: the recovery key with a confirm-by-retyping step and a printable recovery kit (QR code), plus a prompt to add a second device. Proposed next, not decided: a recovery contact (split with the server), a Team admin recovery key (opt-in per member), and later optional PIN recovery in an enclave. Research: [reports/e2ee-lockout-recovery-2026-10-22.md](../../reports/e2ee-lockout-recovery-2026-10-22.md).

**Screens:** Settings → Sync on the computer (signed out, not on the plan, off, add this computer, waiting for approval, syncing, up to date, needs attention), a full-screen sign-in in the clean-start glass-and-prism style, the recovery key dialog (show once, copy, save kit, confirm), devices with fingerprints, Approve (type the join code) and Remove, and an animated picture (this device, the encrypted vault, other devices; sealed packets travel only while a sync runs, still otherwise and under reduced motion). On the iPhone: Settings → Nekko Cloud sync (also from the welcome screen before any pairing), the same states, a Canvas version of the picture, and read-only synced chats.

After sign-in on a computer that lacks keys for existing encrypted sync, desktop and Local Web UI Settings > Nekko Cloud > Sync explain why the same encryption key is needed. **Approve from another device** is primary; **Use my recovery key** opens the fallback. Neither option verifies account sign-in. **Unlock** reports **Checking recovery key…** immediately and prevents a second submission or device approval until the check finishes. Success returns to Sync; failure shows the error and keeps the entered key available for correction and retry. No change to key handling or native phone behavior ([#3216](https://github.com/nekko-labs/nekko-agent/issues/3216)).

**Acceptance criteria:** a database copy reveals no chat text, titles or the chat a record belongs to; a modified, relabelled, rolled-back or cross-account record fails to open; a revoked device can't read writes made after rotation; Rust and Swift produce identical bytes for the shared vectors; Free-plan writes answer 402 while reads and deletion work; donations are stored with no sender information and open only with the research key.

`[updated 2026-11-01]` **Proof of the epoch key.** Nekko Cloud now counts a sign-in as holding an epoch's keys only when its device has a wrap of that epoch and the token has shown the epoch proof, a one-way value only the keyring yields (HKDF-SHA256 of the keyring, info `nekko-sync-epoch-proof/v1` and the key id; the server keeps its SHA-256, migration `0008`). Starting an epoch, a self-wrap after a restore, and `POST /v1/sync/keyrings/:keyId/proof` (once per sign-in and epoch, from the computer and the iPhone) carry it. Without it a sign-in can't revoke devices, start an epoch, push or delete everything (beyond the existing fresh-sign-in delete), whatever devices or wraps it registered. Sync isn't live, so there is no migration path for older keyrings: a keyring without a proof hash makes no one keyed. Tested in `apps/nekko-agent-api` (`sync.test.ts`), `crates/nekko-cloud` (`tests/attacks.rs` against the local stack), the shared vectors, and the iPhone's `CloudSyncTests` (macOS CI).

`[updated 2026-11-03, GD10; engine tests against a stub Nekko Cloud, renderer tests, captured in a hidden window; the API route is built in parallel and not yet run end to end]` **Delete Nekko Cloud account.** Signed in, Settings > Sync shows **Delete account** beside Sign out. Its dialog says what Nekko Cloud deletes (the account, synced chats and keys, devices and sign-ins, any cloud computer; every device is signed out) and that chats on this computer and other devices stay, and asks the user to type the account's email before **Delete account** turns on. The engine sends `DELETE {api}/v1/account` with the device's bearer token (`cloud:deleteAccount`). Only a 2xx answer (204) makes this computer forget its token, device key, keyrings and sync state (`Cloud::forget_this_device`) and sign out. 401 keeps everything and asks the user to sign in again first; 502 (a cloud computer could not be shut down) keeps everything and says the account was not deleted. The renderer never sees the token.

`[updated 2026-11-19; renderer tests and the hidden sync evidence run against the real engine and the local API]` **An emailed code survives its window; Danger zone.** User intent (Philip): "if you click out of the code confirmation window, you have to restart the login flow, let's have it where clicking again reopens the current pending code request. They should have a cancel option too in the window to reset the process", and "move the delete account down to the danger zone options". Closing the sign-in window (clicking outside, Escape or ×) after a code was sent keeps that request: Settings > Sync's button reads **Enter your sign-in code** and reopens straight to the code boxes for the same email, with the resend wait carried over. **Cancel** (where *Use a different email* was) drops the request and returns to the sign-in choices; a code older than 10 minutes (the Supabase project's code lifetime) is dropped too, and signing in clears it. The request lives in Settings > Sync, so leaving Settings forgets it. Signed in, the bottom of Sync is a **Danger zone** group: *Delete everything synced* (once this computer syncs) and **Delete account**, which moved there from beside Sign out. The iPhone's sign-in is a full screen rather than a dismissible window and has no Delete account, so it has nothing to change.

`[updated 2026-11-19; engine and API tests, and a two-computer round trip of a 12.6 MB chat through the local API]` **Chats up to 16 MB sync.** User intent (Philip): "67 too large to sync" was strange, "I'm not sure we should impose a limit unless these are massive." His 67 skipped chats were agent sessions of 1 to 4.4 MB (after pictures are left out), mostly tool output. The cap per chat is now 16,000,000 bytes of text, which seals to just under Nekko Cloud's new 16 MiB object cap. The engine sends at most 6 MiB of chats per push request (a bigger chat goes alone; the push body limit is 24 MiB), and a pull page stops at 8 MiB of stored bytes (always at least one object), so a page of big chats stays small on the API's 256 MB machine. The iPhone already follows `more` and needed no change. Settings says "N over 16 MB, not synced".

`[updated 2026-11-19; the hidden sync evidence run against the real engine and local API, both a first and a second computer signing in through the window]` **Signing in turns sync on.** User intent (Philip): "syncing didn't automatically start. when someone logs in, we should have syncing enabled by default." A sign-in made in Settings > Sync on a Pro or Enterprise account whose sync isn't set up yet turns sync on at once and shows the recovery key; there is no separate Turn on sync step. An account that already syncs on another device goes to *Add this computer* as before, with no error. Only a sign-in the window sees counts: opening Settings while signed in, or with sync turned off, starts nothing, and Turn on sync stays for an account that signed in before this.

`[updated 2026-11-22; engine tests against a stub Nekko Cloud and API tests, #3186; not yet seen against the live service, whose API deploy is manual]` **A brief Nekko Cloud stall doesn't stop sync starting.** User intent (Philip): "the sync should auto start when someone signs in. It looks like there was an error" (the sign-in turned sync on, the API's database didn't connect in time, and Settings showed *Connection terminated due to connection timeout* beside Turn on sync). The engine tries a Nekko Cloud API call twice more, 0.5 s and then 2 s later, when nothing was listening, the API answered 502, 503 or 504, or it answered that its database didn't connect; any other failure, and every Supabase call (a second sign-in code email), is tried once. The API answers a database that didn't connect in time (node-postgres' connect or pool timeout, Postgres 57P03 or 53300) with 503 `unavailable` and `Retry-After: 5`, and no 5xx carries the error's own text: the log keeps it, the answer says `internal`. Whatever a 5xx said, the computer shows *Nekko Cloud is busy right now. Try again in a moment.* or *Nekko Cloud ran into a problem. Try again in a moment.*

`[updated 2026-11-26; Protocol package tests against a fake HTTP layer, #3343; app target not built here]` **The iPhone retries a brief Nekko Cloud stall too.** After the API restarted and an iPhone request landed in the gap, Fly's proxy answered a bare 502 and the app said *Nekko Cloud answered 502.* The iPhone's Nekko Cloud client now matches the computer: a call to the Nekko Cloud API is tried twice more, 0.5 s and then 2 s later, when the connection failed before anything was sent or the API answered 502, 503 or 504; every other failure, and every Supabase call, is tried once. It doesn't read `Retry-After` (its HTTP layer returns only the status and body), and it signs the fleet connection out only after the last try fails. After the tries, 502 to 504 and any 5xx coded `unavailable`, `database-unavailable` or `busy` (the API's queue-full answer) show *Nekko Cloud is busy right now. Try again in a moment.*; any other 5xx shows *Nekko Cloud ran into a problem. Try again in a moment.* No 5xx shows the server's own text. The 401, 402 and invite-only messages are unchanged. Android has no Nekko Cloud client yet.

`[updated 2026-11-19; engine, store and renderer tests]` **Sync is a per-chat switch.** User intent (Philip): "local only chats should be an option per chat, not a settings option to include them"; asked whether a chat in the Local only mode should still start unsynced, he chose that it syncs like any chat (the mode is about where models run). Settings → Sync's *Include Local only chats* is gone (with `sync:setIncludeLocalOnly` and `includeLocalOnly` in the status). Each chat has a **Sync** switch among the privacy switches beside the message box (Offline, Privacy Shield, Sync, Incognito), shown only while this computer syncs and never on an incognito chat. It is on by default; off sets `Session.syncOff`, which the engine skips (counted as `syncOff`). The flag is a user field: a running turn's save keeps it, and a fork carries it. Turning it off stops uploading that chat; a copy synced before stays in Nekko Cloud until *Delete everything synced* (removing it would mean a tombstone, which deletes the chat on the other devices too). Settings → Sync says where the switch is. Phones can't change it yet.

`[updated 2026-11-20; engine unit and live tests, renderer tests, #3089]` **What syncs, kind by kind.** User intent (Philip): "when the user is signed in to nekko cloud, new options should show up for fleet management, syncing options for chat, library, etc." Settings > Nekko Cloud > Sync lists **What syncs** between the sync row and Devices: **Chats** and, when the account has Library sync, **Library**, each with its own switch, on by default. They are per computer (`State.kinds_off` in `<data>/cloud/state.json`; an older file means everything on), set over `sync:setKind(kind, on)`, and reported as `sync.kinds`. While *Sync this computer* is off both rows are greyed and say so. A kind turned off keeps its records on this computer both ways: nothing of it is pushed, and pulled records of it are passed over without being applied or their revisions remembered. Every kind is pulled through one cursor, so turning a kind off records the cursor, and turning it back on moves the cursor back to it; the next pull brings in what arrived meanwhile (records already applied are skipped by their revisions), then the push sends what changed here, newest `updatedAt` winning as usual. A kind turned back on mid-pull bumps a counter the pull checks before each cursor step, so it carries on from the moved-back cursor instead of past what it passed over. With Chats off, a chat's **Sync** switch beside the message box is hidden, as it is while sync is off; Library's clouds read *Not backed up* with Library off. *Delete everything synced* keeps which kinds are off, from the start. Phones can't change these yet.

 **Each chat belongs to the computer that started it.** User intent (Philip): "we should support syncing multiple devices. Let's have chats that are unique per device, but you should be able to see the combined chats on any device." Decision [0112](../../docs/decisions/0112-each-chat-belongs-to-the-computer-that-started-it.md). A chat's sealed record names its computer (, the device's sync name). Every syncing computer lists every computer's chats, but only the computer a chat belongs to changes it in Nekko Cloud: the others hold a read-only copy that names its computer, never push it or delete it there, and refuse a turn in it ( answers *This chat belongs to Laptop*); forking it makes a chat of this computer. This replaces "newest  wins" between computers; it still decides between copies of one computer's own chat (a restore). A copy keeps this computer's pin, order and archive when a newer copy arrives. Removing a copy forgets it here only, and it is not taken again. On a key rotation every computer left re-seals its copies of other computers' chats as they are, so a removed computer's chats stay readable. Chats synced before this change are pushed once more with their computer; a chat two computers already shared goes to the first to sync after updating, unless the other has carried it on since. On the computer, a copy names its computer on its Agents card and window, and its composer offers **Continue here** ([connected computers](../desktop/connected-computers.md)). Phones read the computer from the record but don't show it yet (#3147).

`[updated 2026-11-25; record and engine unit tests, two live tests against the local API (two computers: pictures arrive exactly, nothing readable on the server, a missing picture fetched again, a deleted chat's pictures removed; a chat synced before pictures did sent again), renderer tests, #3298]` **Pictures sync with their chat.** User intent (Philip): Nekko Cloud syncing "should sync and enable seeing the chat images ... from chats on another device" (a synced chat showed a broken image where a pasted picture was). Decision [0120](../../docs/decisions/0120-chat-pictures-sync-as-their-own-records.md). A picture in a message (`images`, `toolResult.images`: pasted, attached, a tool's screenshot, a generated picture) leaves the chat's record as `nekko-blob:<sha256>.<ext>`, the name the chat store keeps it under, and travels once as a sealed `picture` record (local id: the chat's computer and that name), pushed before the chat. Another computer writes it beside its chats only when its bytes hash to its name, and the chat shows it from there. A chat that arrives first shows *Picture on its way* (glyph and words, the picture's size, never a broken image) until it comes; a picture still missing after a pull is fetched by itself. A chat synced before this shows *Picture not synced* where its pictures were, until its computer updates and sends it once more with them. **Limits:** up to 8 MB a picture; inline data that isn't PNG, JPEG, WebP, GIF or SVG (a PDF pasted as data) is still left out with the note. **Storage and removal:** pictures count toward the plan; a full plan holds them back (Settings counts them as not synced) while chats still sync. A computer sends a tombstone for each of its pictures once none of its chats refers to them; two computers with the same picture keep a record each. Another computer's copies re-seal their pictures with them after a key rotation. The per-chat Sync switch and the Chats kind cover pictures too. **Not yet:** the iPhone and Android read the reference but don't fetch `picture` records, so they show their placeholder (#3299).
