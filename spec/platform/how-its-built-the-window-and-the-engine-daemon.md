# How it's built: the window and the engine daemon

*A plain-language overview of the moving parts, for anyone reading the code or the task list. "TS" means TypeScript.* `[done 2026-10-19]`

**The window's first size** `[updated 2026-10-03]`: on a first launch (nothing saved yet) the desktop window opens at **70% of the screen's width and 80% of its height**, centred on the work area and never below 900 × 600; the size is decided before the window is created and the window is shown only once its page is ready, so it appears at that size rather than growing into it on screen. From then on the size and position the user leaves it at are what it reopens with.

On the desktop, Nekko Agent runs as two processes `[updated 2026-10-19]`:

| Part | Written in | What it does |
| --- | --- | --- |
| **The window** | TypeScript (React in Electron) | Everything you see and type into. It never does disk, network or agent work itself; it asks the engine. |
| **The engine daemon, `nekkod`** | Rust | The whole engine. The window talks only to it, over one local connection: chats and their turns, tools, providers, context, settings, automation, the model servers, the phone relay agent and the desktop-only services (the local API server, CLI install, the webhook listener, the local relay, network visibility). The CLI, the MCP server and the Local Web UI start it the same way. |

**Why split it.** The engine used to be one TypeScript process doing everything at once, so a long reply, a big file search or a slow tool in one chat could hold up opening another chat or typing in a terminal. Rebuilding the engine in Rust, piece by piece, gives each job its own lane, keeps loaded models and running servers alive when the rest of the engine restarts, and takes the heaviest work off the TypeScript event loop. The window itself stays web technology on purpose (see "Native desktop shell" above).

**How the pieces moved.** One service at a time. Each request the window can make has a name; once the daemon handled a name itself it answered in Rust, and every other name still went to the TS host, so the window never changed when something moved. Each Rust version was held to the TypeScript original by recorded test data (golden files): the TypeScript code wrote down what it did on a set of cases, and the Rust code had to reproduce it exactly. With the TS code deleted, those files are frozen records, edited by hand when a behavior changes on purpose. Each move also gets a live check on a real local model before it merges. Where the Rust version deliberately behaves differently (stopping a whole process tree rather than one process, say), the task list says so.

**Already in the daemon:**

- Terminals (2026-09-30).
- The local model servers (llama.cpp, stable-diffusion.cpp) and the OpenAI-compatible address in front of them, so loaded models survive engine restarts (2026-09-30).
- Decision models (Laya) (2026-10-01).
- Reading and saving chats: the chat list, opening a chat, and the user's own edits (rename, pin, options, queued follow-ups). With the TS host busy, opening a 7 MB chat went from 403 ms to 14 ms and listing 301 chats from 797 ms to 22 ms (2026-10-01).
- The agent loop that produces a chat reply, streaming from the model providers, with the reply's tokens going straight from the daemon to the window (2026-10-01).
- The short side calls after a reply: the chat's title, suggested replies, and filling in part of a prompt (2026-10-01).
- MCP servers (2026-10-01).
- The built-in file and shell tools (read, write, edit, list, glob, grep, bash), their guardrails, and the list of pending file changes (2026-10-01).
- The whole chat turn (2026-10-12): the tools on offer, the system prompt, the context read from disk (guidelines, memory, attachments), saving the user's message and every step, the agent's questions, setting the chat's title, completing it, and an ordinary chat's plan. (Claude subscription turns, whose rate-limit headers went to the TS host, were removed 2026-10-19 with Claude plan sign-in.) Anything waiting on a person, tool approvals and the agent's questions, is held and answered in the daemon, so the board, the chat and the phone all answer it there; with the TS host busy, approving a tool went from 451 ms to 6 ms.

**Nothing is left in TS.** `[done 2026-10-19]` The last pieces (admitting turns, sub-agents, hooks, the after-turn work, auto-continue, the desktop-only services) moved during step 5 of PF14, and the TS engine (`packages/host`, `packages/core`) is deleted. Its golden fixtures under `crates/*/tests/golden` stay as the record of what the TS code did.

**Native dialogs, the OS shell and updates.** `[implemented 2026-10-17; Windows verified in an isolated desktop sandbox; macOS and Linux install paths and the macOS microphone prompt not yet verified on hardware]` The desktop window shell (Electron main) no longer answers any app request of its own: the engine daemon draws the native file, folder and save dialogs and message boxes, owned by the app window (they sit in front of it and keep it disabled while open, though another process draws them); opens links in the browser and files and folders with their default app; reports and requests the microphone permission with the same answers as before (Windows privacy setting, macOS authorization, Linux "unknown"); and runs the self-updater. The updater reads the same release feeds electron-builder publishes for every release (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`), offers a version only when it is strictly newer, verifies the download's SHA-512 before keeping it, and installs it: on Windows the downloaded installer runs silently and relaunches the app once it has quit; on macOS the `.app` bundle is replaced from the release zip and reopened; on Linux the AppImage is replaced (or the `.deb` installed with an administrator prompt) and restarted. The update states, progress and "Install & restart" control the user sees are unchanged. Main keeps only what is about windows: the app window and its title bar, the macOS menu, the tray, the in-app browser and window capture, deep links, notifications, and starting or stopping the engine. On macOS, where a dialog must belong to the app's own process, the daemon asks main to draw it. Without a daemon (a development checkout with no daemon build) main still answers all of this the old way. A paired phone can call none of it.

**The phone relay in the daemon.** `[implemented 2026-10-12]` Remote access is the daemon's when it knows the data directory (the desktop app, and the web, npx and Docker editions behind it): `remote.json`, the device registry, pairing codes, and the relay agent that dials out to the relay. The protocol is unchanged for every phone app and for `apps/relay-server` (relay v2, the sealed HELLO, PBKDF2 and AES-GCM framing, the push ping when a run finishes), held to the TS code byte for byte. A paired phone now reaches exactly what the UI reaches, through the daemon's own router, so its requests land on the daemon's services rather than on stale copies in the TS host, and it hears the same events the UI hears. What it may call is decided on the computer, not by the phone (see "What a paired phone may do" below); the daemon's internal callbacks (`turn:*`, `loop:*` and the like), which the TS relay's dispatcher happened to expose, stay refused. Frames go out in the order they were produced. The TS agent stays only for the headless relay-agent mode (`NEKKO_RELAY_URL`) and the editions without a daemon. Not yet verified: the native iOS and Android apps against it (both use the same protocol, which the golden set pins), and the managed relay (never used for testing with real devices).

**Each window hears the chats it shows.** `[implemented 2026-10-17, #551; verified with daemon tests, a fan-out benchmark and the Local Web UI in headless Chromium; the packaged desktop app not yet checked live]` User intent: six chats streaming on the Agents wall must not make every window parse every chat's tokens, and a turn's events must cross the engine once. A window takes the full event stream (text, reasoning, tools, usage) only of the chats it has open, shown or kept warm, and of their sub-agents; for every other chat it still hears when a turn starts, when it waits on you (an approval or a question) and resumes, when the chat's record changes and when the turn ends, which is all the sidebar, the Agents wall and board indicators, notifications and the sub-agent rail need. Opening a chat in the middle of a reply shows the reply so far at once, with nothing drawn twice. A window that opens while other chats are running still shows them as running. The TS host is now sent only how a daemon-driven turn ends (when the daemon runs the phone relay, messaging and usage accounting), and no longer sends the daemon copies of its own events. Measured with six chats streaming 200 tokens each: 218 frames (22.5 KB) per window instead of 1,218 (125 KB), and the host's share of a turn from about 3.9 KB to 0.35 KB. Without a daemon (and with `NEKKO_AGENT_LOOP=ts`) every window still receives every chat's events, as before.

**Session clearing.** The daemon now implements clear today, this month and all when configured with a data directory. Date windows use inclusive local calendar boundaries against the chat's last update, not its creation date; archived and pinned chats are not exempt. Clear and single-session delete coordinate command-log removal through the host callback before deleting chat files, preserving the host's queued removal and process-lifetime append tombstone. Callback failures stop deletion rather than bypassing the queue. TS-generated parity fixtures verify deletion counts, retained files and summary-cache refresh; focused host tests verify queued-write removal and later append suppression, and daemon HTTP tests verify callback IDs. Month cutoffs resolve today's midnight before changing the date to day 1, matching TS setter order. Deterministic JS/Rust timezone fixtures verify midnight gaps, repeated midnight, skipped calendar days and month setter order. An isolated real-daemon/real-host-dispatcher HTTP harness verifies queued writes and racing appends cannot recreate removed logs. The host callback awaits queued unlink and propagates failure; daemon tests verify failed callbacks and disabled backends preserve JSON for both delete and clear. Deletion requires the host backend to be available because it owns the log queue and tombstone; unavailable backends fail closed. Non-Windows execution remains unverified. Without a daemon data directory, the TS host remains the fallback. This does not complete PF14.

**Automation tasks in the daemon.** `[implemented 2026-10-12]` Scheduled, recurring and background tasks are the daemon's when it knows the data directory: `tasks.json`, the task channels and the scheduler. A task still fires through a normal chat turn (the host admits it, as for any chat), keeps its own chat across fires, and the file format is unchanged. Two behaviors changed: a task now fires when it is due (the scheduler sleeps until the earliest due task) instead of up to 15 seconds late, and a task whose fire was cut short by a restart fires again at startup instead of never firing again. Without a daemon, the TS host runs tasks as before, with the same restart fix.

**Workflows in the daemon.** `[implemented 2026-10-12]` The workflow engine runs in the daemon when it knows the data directory: definitions, run history, connector-poll cursors, the schedule, connector listeners and webhooks. Prompt and skill steps are still normal chat turns, actions and shell steps behave as before (a timed-out shell step now stops everything it started), and the files keep their format. Without a daemon the TS host runs workflows as before.

**Training and goal runs in the daemon.** `[implemented 2026-10-16]` Training and goal runs are the daemon's when it knows the data directory: `training.json`, the Training tab's channels, the run engine that drives each run's turns, and the `training:updated` event. A run's turn is still a normal chat turn, now admitted and driven by the daemon, and the tools a run's agent uses (report an experiment, report an artifact, a goal's plan) are answered in the daemon too, without a round trip to the TS host. The file format, the agent's brief, the replies the agent sees, stall detection, the error limit, the turn cap and the 4-second pause between turns are unchanged; runs that were running when the app quit resume when it starts. The brief lost its em dashes. Without a daemon the TS host runs training as before.

**What a paired phone may do.** `[implemented 2026-10-14, both relay agents; not yet verified against the native apps on a device or the managed relay]` User intent: the limit on what a phone can do is enforced by the computer; locking the phone app is not a boundary. One allowlist in `packages/shared/src/phone-access.ts` is the source of truth; the TS relay agent (`packages/host/src/relay.ts`) applies it directly and the daemon's (`crates/nekko-remote/src/phone.rs`) reads the same lists from `crates/nekko-remote/src/phone-access.json`, which the TS golden test writes and fails on when stale; the same test records how the TS decides a set of requests (`tests/golden/phone.json`) and the Rust gate must reproduce every refusal message, host call and reply. Acceptance criteria:
- A phone may call only: `app:info`, `chat:abort`, `chat:answer`, `chat:pending`, `chat:queue`, `chat:send`, `models:list`, `providers:list`, `session:create`, `session:delete`, `session:get`, `session:setOptions`, `sessions:summaries`, `settings:get`, `settings:update` (filtered), `skills:runnable` (names and descriptions only, `[added 2026-10-16]`), `tool:approve`, `voice:status`, `voice:transcribe`, `workspace:list`: what the Expo, Android and iOS clients use, plus settings, completing/deleting a chat as the desktop does (`session:setOptions` with `archivedAt`, `session:delete`) and voice, for the next phone releases. Anything else is refused before the host runs it, with `Not allowed from a paired phone (<code>): <detail>`.
- Always refused even if added to the list: `data:wipe`, `settings:reset`, `file:write`, `workspace:addByPath`, `workspace:remove`, `voice:install`, `voice:uninstall`, `voice:cancel`, `connector:connect`, `connector:disconnect`, `providers:save`, `providers:remove`, `providers:importCliAuth`, and every `remote:*` (except `remote:status`, itself not on the list), `terminal:*`, `terminals:*`, `mcp:*` and `oauth:*` channel. Hooks are settings, so they are covered by the settings rule.
- `settings:update` from a phone may set only `defaultChatMode`, `chatPaneAction`, `skipDeleteConfirmation`, `voice.enabled` and `voice.language`, each with a checked value; any other key refuses the whole update and nothing is applied. A voice change keeps the rest of the saved `voice` object.
- **YOLO from a phone `[decided 2026-10-14]`:** the owner decided a paired phone may choose YOLO, both as `defaultChatMode` and as one chat's `mode`, with no confirmation on the computer. The chat modes a phone may pick are `PHONE_CHAT_MODES` (`ask`, `guardrails`, `yolo`); any other value is `value-invalid`.
- `settings:get` (and the reply to `settings:update`) returns an allowlisted view: theme, theme preset, accents, default provider/model, starred models, and the phone-settable settings; no provider records, keys, tokens, folders, hooks, guardrails or instructions. `providers:list` returns id, kind, label and enabled only.
- `session:setOptions` from a phone may set the model, title, pin, tags, `archivedAt`, thinking and the chat mode (YOLO included); not tools, execution mode, Git isolation, offline or incognito. `chat:send` from a phone may not attach paths on the computer. `[added 2026-10-16]` A `skill: { name, input }` on a phone's `chat:send` or `chat:queue` (whose object prompts may carry only `text`, `images`, `skill`) is expanded on the computer from its own `skills:runnable` list; the phone never receives or supplies a template.
- `[added 2026-10-20, IO-33]` Two classes on top of the allowlist: `PHONE_READ_CHANNELS` and `PHONE_CHANGE_CHANNELS` (both in `phone-access.json` as `readChannels` / `changeChannels`; FA-2 git is the first to fill them, see *Git on the iPhone*; FA-1 and FA-5 add files and logs, see *Files and logs on the iPhone*; FA-3 terminals add a third, `PHONE_TOKEN_CHANNELS` for `terminal:write` / `terminal:resize`, see *Terminals and SSH on the iPhone*). A classed channel must also be on the allowlist. The gate checks the calling device's switches, and for change-class calls the signed proof and the activity log (see *Full phone access, the foundation*). The channels above are in neither class and decide exactly as before (the frozen phone golden still passes unchanged).
- Consequence: the web app opened through a pairing link over the relay (`apps/desktop/src/renderer/web-client.ts`) is held to the same list, so most desktop screens (training, goals, Command Center, terminals, settings) no longer work there. This replaces the earlier "a phone browser gets the full app" promise in the remote-control section.

**Editions.** `[updated 2026-10-12]` The Local Web UI (`npm run web`, the in-repo server the CI speed contract measures) now runs behind the daemon too, in the desktop's topology: the server starts `nekkod` on a random loopback port with a per-launch token, `nekkod` starts the TS host as its backend (this same server script under Node, since there is no Electron), and the server stays the public front door. It keeps every existing rule for who may connect (localhost by default; `NEKKO_TOKEN`, `NEKKO_ALLOW_UNAUTHENTICATED`, `NEKKO_ALLOWED_HOSTS` and `NEKKO_ALLOWED_ORIGINS` for remote and Docker), applies the same Host, Origin and token checks to sockets, and passes requests to the daemon with the daemon's own token, so the public token never reaches the daemon, its backend or a terminal's environment, and no URL carrying a token is logged. Terminals stream over the daemon's binary `/api/term/:id` socket, as on the desktop. If either process crashes it is restarted with backoff (the server restarts `nekkod`, `nekkod` restarts the backend), and stopping the server, or killing it outright, leaves no process behind. Without a daemon binary the server says so in one log line and runs the engine in its own process as before; `NEKKO_DAEMON=nekkod` makes a missing or failing daemon an error instead, `NEKKO_DAEMON=ts` forces the in-process engine, and `NEKKOD_PATH` names a binary. The server looks for `NEKKOD_PATH`, then the platform's npm package, then `bin/` beside the script, then a cargo build in the checkout. The npx package (`npx nekko-agent-local-web-ui`) installs this platform's daemon from an optional dependency, `@nekko-agent/nekkod-<platform>-<arch>` (Windows x64, Linux x64 and arm64, macOS arm64; ONNX Runtime has no prebuilt library for Intel macOS, which keeps the in-process engine), built and published by the release workflow at the same version; a platform without one, or a binary that will not start (the Linux builds need a GCC 13 C++ runtime: Ubuntu 24.04, Debian 13 or newer), falls back to the in-process engine with the log line. The Docker image builds the daemon in its own stage and runs the Local Web UI behind it (`NEKKO_DAEMON=nekkod` is set, so a broken daemon stops the container rather than quietly falling back), on Debian 13 with `tini` as PID 1 so `docker stop` shuts everything down cleanly, and a health check on `/health`; `docker compose` is unchanged for users. Not yet: the relay-agent mode (`NEKKO_RELAY_URL`) still runs the engine in-process. `[updated 2026-10-18]` It runs on nekkod's relay agent now: the server starts nekkod on the data directory and joins the given room with the given key (`remote:attach`), keeping the devices already paired. `[updated 2026-10-18]` There is no in-process fallback any more: without a daemon binary, or with one that will not start, the server refuses to start and says why (`NEKKO_DAEMON` is gone; `NEKKOD_PATH` still names a binary). A platform with no nekkod build is refused up front with what still works (`--url` to an engine elsewhere): the server and the CLI's local mode run on Apple silicon, Windows (on Arm through the x64 build under Windows' emulation; its npm package lists both CPUs) and Linux x64 and arm64.

**No fallback.** `[updated 2026-10-18]` The desktop app and the Local Web UI need nekkod; neither runs the engine without it. A desktop app whose daemon is missing (a development checkout that never built it, an antivirus that quarantined it) or that Windows cannot load (a missing Visual C++ runtime) shows why the engine is down (reinstall, or build it in a checkout) instead of starting in a degraded mode, and the tray's Restart looks again. `NEKKO_AGENT_LOOP=ts`, the old diagnostic switch that kept turns in the TS host, is gone. A sandbox chat needs a daemon with containers (one that knows the data directory); without one its turn is refused. The CLI's local mode, `nekko-agent mcp` and the relay-agent mode moved in step 3 (2026-10-18); the parked Nekko Cloud prototype that ran a TS host per account was deleted with the TS engine (2026-10-19), and Cloud accounts will run on a shared nekkod (PF14 step 4). `[updated 2026-10-15]` The TS host's loopback wire (`apps/desktop/src/backend/wire.ts`, what the daemon called and what the shell talked to without a daemon; deleted with the desktop's TS backend in PF14 step 5, 2026-10-19) applies the daemon's own admission rules: a request or socket upgrade whose `Host` header is not `127.0.0.1`, `localhost` or `[::1]` (a page reaching the port through DNS rebinding) is refused with 403 before the token is checked, and a request body is capped at 25 MB, or 64 MB for `chat:turn` so attached images fit, with 413 `body too large` past that. `[implemented, unit-tested]`

**Starting and stopping the daemon, one per data folder.** `[implemented 2026-10-22; real-binary tests on macOS for SIGTERM, a killed daemon's leftovers and the lock; Linux and Windows paths not built or run yet]` User intent: quitting the app, logging out, or the engine crashing must never leave MCP servers, model servers, terminals' commands or other helpers running with nobody to stop them, and two copies of the engine must never write the same chats at once. Why a record rather than tracking each spawn, and stdin rather than a temp file: [decision 0009](../../docs/decisions/0009-daemon-config-on-stdin-and-a-child-record.md). Acceptance criteria:
- `nekkod` shuts down gracefully when its stdin closes (the app quit), on Ctrl-C, and on SIGTERM or SIGHUP (logout, Activity Monitor, a supervisor): it stops what it started, gives open connections two seconds, then ends any child process still running (SIGTERM, then SIGKILL after 1.5 s). A second signal during shutdown, or a shutdown past eight seconds, ends the children at once and exits.
- What it started is never left behind by a hard kill either. Windows keeps its kill-on-close job; on Linux the daemon and its MCP and voice children still die with their parent; on macOS the daemon leads its own process group. On every Unix the daemon keeps a list of its live child processes (pid, process group and start time) in `<dataDir>/run/children.json`, refreshed every two seconds and written atomically, and the next daemon on that folder ends whatever on the list is still running before it starts anything. A process is only ever signalled when its start time still matches, so a recycled pid belonging to something else is left alone; a process that detached into its own session on purpose (the updater's install script) is never touched. Children started in the two seconds before a hard kill may be missed.
- One daemon per data folder: the first takes an exclusive lock on `<dataDir>/nekkod.lock` for its whole life (the OS releases it however the process ends). A second waits up to ten seconds for it (a predecessor may still be shutting down), then exits with code 3 and names the holder's pid; the desktop app shows "another Nekko engine is already running on this data folder" instead of restarting into it, and the CLI and Local Web UI say the same in their log.
- The launch configuration, with the engine's token, goes to `nekkod` as the first line of its stdin (`--config-stdin`), never in its environment, which any process of the same user (the agent's own commands included) could read with `ps eww`. `NEKKOD_CONFIG` is no longer read. `--config <path>` still works.
- The desktop app restarts a daemon that never says it is listening within 30 seconds (SIGTERM, then SIGKILL), with backoff; a daemon binary that cannot be started at all (permissions, missing) fails waiting calls at once with why, and the tray's Restart tries again; stopping it closes stdin, then sends SIGTERM after six seconds and SIGKILL three seconds later, and a restart waits until the old daemon has exited.
- The window pings the engine over its socket every ten seconds (`daemon:ping`, answered by the socket itself, so a slow call never delays it). A socket silent for thirty seconds is treated as a wedged engine: every call in flight fails with "the engine stopped responding before it answered" and the window reconnects. Calls themselves have no deadline, so a long turn or download is never cut short.
- Only the app's own windows, from their top frame, get the engine's address and token or may start and stop it; the in-app browser's pages and embedded frames are refused.

**The end state.** `[reached 2026-10-19]` Everything moved, the TS host is retired, and the web, npx and Docker editions ship the daemon too. What remains of PF14 is Nekko Cloud on one shared nekkod (step 4). The plan and each step's details are in `TASKS.md` (PF14).
