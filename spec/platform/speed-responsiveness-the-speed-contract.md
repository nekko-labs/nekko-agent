# Speed & responsiveness (the speed contract)

Agent tools feel slow when the UI waits on something or redraws too much. Nekko Agent treats responsiveness as a feature with numbers, and CI fails a change that breaks them. The desktop UI stays web technology (Electron + React) for maintainability; the engine behind it moves into a separate Rust daemon so the window never shares a process with the agent loop, the terminals or the model server. `[in progress]` *As of 2026-09-30 (PF1-PF7): the chat composer, streaming, windowed-transcript, incremental-markdown and instant-switching rules hold, the engine runs in its own daemon with a terminal that keeps up, and every budget, the terminal's included, is measured in CI. The web, npx and Docker editions still run the TS host's terminals until they move behind the daemon (PF14).*

**The rules.**

- **The UI thread never does disk or network work.** Every read and write goes to the engine asynchronously; nothing on the input path waits on a file, a socket or the engine.
- **A keypress shows on screen within one frame: 8 ms at 120 Hz.** This holds in the chat composer and in the terminal, in a chat with a thousand messages, while a reply is streaming. It is measured in CI on every change.
- **Only the part of the transcript that is on screen is rendered.** A chat with thousands of messages scrolls and types as fast as a chat with ten.
- **Scrolling a chat always goes where the wheel says.** `[fixed 2026-10-16; isolated renderer-verified with emulated reduced motion on and off, light and dark; real desktop with the OS setting not yet checked]` With the OS "show animations" setting off (reduced motion), the global reduce-motion rule gave every element a 0.01 ms transition, which applied to every property, layout included. The windowed transcript's spacer padding then lagged a frame behind each row swap, so scrolling up stuttered back down and scrolling down stopped short of the latest message and bounced between two positions, with Jump to latest stuck on screen. Transitions under reduced motion are now 0s (never started); animations keep 0.01 ms so `animationend` still fires. Acceptance (`apps/desktop/scripts/transcript-scroll-integration.cjs`, 120-turn synthetic chat, real wheel input): wheel up and down never move visible content against the wheel, wheel down from mid-chat reaches the bottom, and a small nudge up and back returns to the bottom, in both motion settings.
- **Streaming markdown is parsed incrementally.** Finished blocks of a reply are parsed once and left alone; only the block still being written is re-parsed, at most once per frame.
- **Decorations do not cost a frame each.** `[implemented 2026-10-12]` The looping decorations (a working agent's beam and status rocket, the pixel cat, the needs-you glow, pulsing dots) animate things the compositor cannot run alone, so Chromium used to tick them on the main thread on every frame, and the page never went idle while an agent worked. Their steps are 15 fps or slower, so the app now pauses them and advances them on a 30 Hz clock of its own: the same frames at the same moments to within a tick, an idle main thread in between, and still held while the window is hidden or unfocused.
- **Nothing polls or animates for a view nobody can see.** `[implemented 2026-11-26]` Timers that only refresh what is on screen (a chat's elapsed clock and context estimate, its next-wake read, watch countdowns, the Settings status polls, the limits clock, a runner's live log, the local-models monitor) run through one visible-interval hook: they pause while the window is hidden or the pane is parked behind another, and read once at once when shown again. The limits and countdown clocks share one ticker. The decorations' frames also hold in a parked pane, as they do in an unfocused window. A chat reads its next wake time when a watch is armed, cancelled or a turn ends, with a one-minute fallback, instead of after every tool result. The hardware meter polls every 3 seconds (the engine caches a GPU reading for 1 second, so a 2-second poll always spawned a probe).
- **Local state updates first; the engine catches up.** Sending, renaming, pinning, switching and closing take effect on screen immediately. If the engine later refuses, the change is rolled back and the reason is shown.
- **The first screen loads only what it shows.** `[implemented 2026-11-26]` The Agents view paints from the entry chunk; every other tab (Library, Skills, Training, Automations, Design, Models, Connectors, Memory, Settings) and the first-run setup are separate chunks (the Remotion player rides with Automations), and the QR code library loads when a code is first drawn. The tab chunks are fetched one per idle slice, starting 1.5 s after the page loads, so they never compete with the first paint and by the time anyone switches tabs the tab is already loaded and the switch is as instant as before. A tab opened before its chunk arrives shows an empty main area for the frame or two the local file read takes, never a spinner. Measured on the `startup` probe: the JavaScript loaded by the time the main view is interactive fell from 6475 KiB to 4332 KiB ([perf history](../../docs/perf-history.md)).

**Switching is instant, history may follow.** Switching chats, windows, workspaces or tabs changes the screen in the next frame. The chats used most recently stay warm: their transcripts are kept in a bounded in-memory cache and the last few chat windows stay mounted but hidden, so returning to one is a visibility flip rather than a rebuild. A chat that is not warm shows its frame (title, composer, controls) in the next frame and its history a moment later, newest messages first. The warm set has a fixed ceiling in both chats and memory, so the app does not grow without bound the longer it runs. `[implemented 2026-10-12]` On the Agents wall in Focus, the windows that are not shown stay laid out under the one that is, at its size, but are not drawn (`content-visibility: hidden`), so switching back reuses their styles and layout; the last four Focus chats also keep their composer mounted while hidden. Selecting a window restyles only its frame, never its transcript. Measured on the speed contract (CI runner), a warm switch went from a p95 of 24-30 ms to 13-17 ms.

**Budgets** (p95, headless, against the Local Web UI with a scripted model). The target is the product budget, measured on a desktop reference machine at 120 Hz, and `npm run perf:strict` holds a run to it. CI runs the same measurements on a 4-vCPU GitHub runner with no GPU and a 60 Hz display, where the same work takes about twice as long and varies about 30% run to run, so the `perf` job is a regression gate at two and a half times the target (three times for the composer keypress and the cold-switch frame, which the runner had at 100-110% of the 2.5x gate on every attempt by 2026-10-03 while a desktop measured them at 8 and 12 ms). `[changed 2026-10-15, Philip]` Two gates were raised by about 4%: the streaming frame from 10 to 10.4 ms, because an unchanged `main` failed it at random at 10.1-10.4 ms (issue #544), and the cold-switch frame from 25 to 26 ms. The product targets are unchanged. The report prints the raw p95 next to both numbers. `[changed 2026-10-17, Philip]` The gates were recalibrated from 115 runner reports, closing issue #544: 45 of them, nearly all from PRs that did not touch the renderer, had failed after three attempts. Each gate is now the worst healthy best-of-three p95 plus about 10% (table below); replayed on the same reports, none fail. A gate at roughly a third above today's median still catches a real regression; finer trends are tracked in `docs/perf-history.md`. `[updated 2026-10-12]` The latency figures measure the app, not the headless display's frame clock: the browser they run in has its frame-rate limiter off, and the harness keeps its frames flowing with a 1 px compositor animation of its own, because Chromium otherwise holds the frame after one that drew nothing to a 60 Hz tick. Before that, a keypress or switch measured up to a frame slower whenever nothing on the page happened to be animating (a chat switch read 18-19 ms instead of 10-13 ms on the runner with the app doing the same work). The report prints this frame wake next to the budgets.

`[changed 2026-11-06, Philip]` **Where the gate runs.** The speed contract runs on every pull request that changes what it measures (renderer, web server, packages, daemon, harness), and the required `gate` waits for it, so a regression is stopped before it reaches `main` ([decision 0059](../../docs/decisions/0059-speed-contract-and-itests-run-on-every-pr.md)). There is no merge queue any more ([decision 0056](../../docs/decisions/0056-no-merge-queue-speed-contract-and-itests-run-nightly.md)), so the PR is the last place to stop one. (From 2026-10-17 to 2026-11-06 it ran in the merge queue for every group that changed what it measures, and for a few hours on 2026-11-06 only nightly.) The `ci:perf` label forces it on a PR that touches none of those paths; a hand dispatch (`gh workflow run ci.yml --ref <branch>`) runs everything. It also runs in the nightly full run, which opens the `ci-scheduled` issue on a failure. `[changed 2026-11-06, Philip explicitly approved 48 ms]` The cold-switch frame gate is 48 ms, up from 33 ms. Since #1521 the harness measures the real six-zone board, where a cold switch remounts a chat into the active zone, and unchanged `main` failed the 33 ms gate, set on the old two-zone board, in about two runs out of three (issue #712). 48 ms is about a third above the median best-of-three p95 of 778 runner reports from 2026-11-03 to 06, the same sensitivity as the 2026-10-17 calibration. The product target (8.3 ms) is unchanged; making that remount cheaper, and lowering the gate again, is issue #1998. macOS daemon and capture jobs run only in the 6-hourly run (or with `ci:macos`): GitHub's Team plan runs five macOS jobs at once across every workflow, and per-PR macOS jobs had queued 50-100 minutes. See [Contributing: how changes land](#contributing-how-changes-land-2026-10-17).

**The memory contract.** `[added 2026-10-10]` A long session must not slow the app, or the rest of the desktop, down. A wall of busy agents once held ~70 MB of GPU tiles per window for a decorative beam, filled Chromium's 512 MB tile budget ("tile memory limits exceeded") and starved Windows' own compositor. So:

- **No animated layer is bigger than what it shows.** A decoration that runs an animation or carries `will-change` is rastered whole, so it is drawn at the size of its own box, never as an oversized surface clipped down to a ring or a glow.
- **Nothing a chat switch builds is kept.** Switching round the chats again and again leaves the heap, the DOM and the event listeners where the first lap left them.
- **Helpers end what they start.** Every browser, server or child process the app or its tooling spawns is ended with its whole process tree, and its scratch profile deleted. The tooling uses Chromium (Playwright's or Chrome), never the user's own Edge.

The same `perf` job measures these, on a Grid wall of six agents streaming at 2x scale, with a software GPU (SwiftShader) so a CI runner and a desktop count tiles the same way (`node scripts/perf/run.mjs --only memory`; budgets in `scripts/perf/budgets.mjs`):

| Check | CI gate |
| --- | --- |
| Worst animated compositor layer against the box that clips it | 2x |
| Compositor tile memory | 320 MB |
| JS heap kept per lap of chat switches, after warm-up | 2 MB |
| DOM nodes kept per lap | 50 |
| Event listeners kept per lap | 20 |

**Report-only probes.** `[added 2026-11-26, #3374; measured and printed, not gating]` The `perf` job also measures four things that no budget covers yet, so the renderer and daemon optimizations that target them have before/after numbers. They print in the job summary under "Report-only probes (not gating)" and in `perf-report.json` (`reportOnly`), they cannot fail a run, and their definitions live in `REPORT_ONLY_PROBES` in `scripts/perf/budgets.mjs`. Run one with `node scripts/perf/run.mjs --only <probe>` (`long-stream`, `concurrent`, `startup`, `idle`, or `extras` for all four).

| Probe | What it measures |
| --- | --- |
| `long-stream` | Main-thread work per frame (p50, p95, and p95 of the last third of the frames) while a 16 KB reply of mixed markdown (headings, lists, a code fence) streams at 300 tokens/s, traced until the reply ends. The gate's 6 s trace never reaches the large-reply part. |
| `concurrent` | Frame work in chat A while it streams the gate's 28 KB reply and chat B, another seeded chat, finishes a short turn every second (each `done` refreshes the session list). |
| `startup` | Cold profile (a new browser with an empty profile per load): first contentful paint and time until the main view is interactive (rail and a board window on screen, a frame and a task later), from navigation start; the renderer production build's total JavaScript (raw and gzip), the JavaScript loaded by then, and a per-chunk size listing so code splitting can be judged. |
| `idle` | CPU as a share of one core with the window hidden (a second tab in front; the result says if the page did not report `hidden`): the whole Chromium process tree with its renderer, GPU and browser processes (read per process from `ps` or `/proc`, counting only processes alive at both ends of the window), and the Local Web UI server with its children (nekkod, standing in for the desktop's main process), first with no agent and then with one scripted agent streaming. |

A probe becomes a budget only by the recalibration rule above: from real runner samples, with Philip's approval, recorded in `docs/perf-history.md`. The first baselines are recorded there.

**The engine can fail without taking the window with it.** `[shipped 2026-09-30, desktop]` The desktop window no longer runs the engine: a separate engine daemon (`nekkod`, in Rust) owns the terminals and supervises the rest of the engine as its own process. If either crashes it is restarted and the UI reconnects; the window, drafts and scroll positions survive. If the daemon binary is missing, the app still starts, running the rest of the engine directly with its older terminals.

**The terminal keeps up with any output.** `[shipped 2026-09-30, desktop]` Terminals render on the GPU with xterm.js on WebGL by default. Ghostty's terminal core compiled to WebAssembly is offered in Settings as an experimental renderer: it draws correctly, but under a 40 MB flood it held the UI thread 20-30 ms a frame where xterm stayed inside one, so it is not the default until that changes. Output is delivered at most once per frame rather than once per chunk, and a flood of output (a large `cat`, a runaway build log) slows the program producing it instead of freezing the app. Measured on the desktop app: a keypress in another input while a visible terminal prints 40 MB reaches the screen in 7.1 ms p95 (7.6 ms before), and the longest frame dropped from 20.9 ms to 4.4 ms. Keystroke echo through the engine takes under 1 ms on its own; PowerShell adds about 15 ms of its own before it echoes, which no terminal can remove (Command Prompt and Git Bash echo in under 1 ms). Prompt themes built on Nerd Fonts render when one is installed.

**Terminal copy, paste and right-click menu.** `[implemented; key-mapping unit tests, desktop suite and typecheck pass; renderer verification recorded in the PR; native OS clipboard in the packaged app not checked]` Users could not copy terminal output: the app has no Edit menu on Windows/Linux and the terminal had no context menu. Right-clicking a terminal (both renderers) opens a menu with **Copy** (disabled without a selection), **Paste** (disabled on read-only Agent commands logs), **Select all** and **Clear terminal** (clears the visible screen and scrollback in the pane only; the shell process and backend snapshot are untouched). Keys follow Windows Terminal and VS Code: on Windows/Linux Ctrl+C copies when text is selected and otherwise still sends the ^C interrupt; Ctrl+Shift+C and Ctrl+Insert copy; Ctrl+V, Ctrl+Shift+V and Shift+Insert paste. On macOS Ctrl+C always interrupts and Cmd+C/V are unchanged. Paste goes through the renderer's paste path, so programs that enable bracketed paste receive it bracketed. Clipboard access stays local (`navigator.clipboard`); failures show an error toast and nothing is sent to the shell.
