# Distribution & platforms

- **Supported platforms** `[decided 2026-10-13]`: Windows (x64, arm64), Linux (x64, arm64) and macOS on Apple silicon. **Intel Macs are not supported** (Philip, 2026-10-13: add them back when there is demand). The engine daemon cannot be built for them (ONNX Runtime has no prebuilt x86_64 macOS library) and the desktop app already shipped arm64 only, so on an Intel Mac the Local Web UI, `npx nekko-agent` and the CLI's local mode refuse to start with a message saying so; the CLI can still drive Nekko Agent running on another machine (`--url`). The model catalog offers no Intel Mac llama.cpp build.
- **Marketing website** `[shipped]`, static site (nekkoagent.com) rebuilt in an immersive deep-space style inspired by liquidink.design's GitHub concept: drifting starfield canvas, nebula gradients, an **Nekko Agent** display hero (leading with what it does for you, "AI help on your computer", rather than with the technology, see AN10b), glass panels, numbered chapters with scroll reveals, the astronaut Aphelion drifting in zero-g with a spark lapping it in the hero, plus the app-window mock, positioning cards, and edition cards. Dark-only by design; reduced-motion safe; still no-framework hand-crafted HTML/CSS/JS. The narrative leads with the **local-models spotlight** (chapter 01), then **"The harness is the other half of the model"** (chapter 02): the argument that a model you run yourself competes on real work through the scaffolding around it, laid out as a three-group spec-sheet manifest (what it sees / what it can reach / when it's wrong) rather than a card grid. The download chapter is a **smart download button**: it detects the visitor's OS and architecture, resolves the real asset URL from the GitHub Releases API (with the releases page as the offline/rate-limited fallback), and a caret opens a menu of every other platform and format (installer, portable, distro package), keyboard navigable and marking the build we picked for you. The **hero CTA is that same button**, so the first click downloads instead of scrolling to a second button, and the GitHub link beside it is a quiet outline pill. Both share **one button shape with hypergate.app**, the sibling product: a fully rounded single-line pill, dark ink on the brand gradient, the version in a mono chip behind a hairline divider, and an equal-height outline pill next to it (format and architecture move to the link's tooltip and the caption under the button). Below the download button, terminal people get the **same build as a one-liner in their own shell's syntax** (PowerShell `iwr`, `curl` + `open` on macOS, `curl` + `chmod` on Linux) with a copy button; it appears only once the real asset URL resolves, so the command is never a guess.
- **Documentation hub** `[implemented 2026-10-12]`, nekkoagent.com/docs, laid out like svelte.dev/docs: the page list on the left grouped into Introduction, Using Nekko Agent, Contributing and For AI agents; the article in the middle; "On this page" on the right with the section being read highlighted; previous/next links and an "Edit this page on GitHub" link at the foot; Ctrl/Cmd+K (or `/`) search over every section; copy buttons on code blocks; and a drawer for the page list on phones. `/docs` opens on **Getting started**: who we are and what we care about, a few bullets on what the app does, then installing it (the installer, or from source: the Git, Node 22.12+ and Rust prerequisites with each platform's C/C++ toolchain, clone, `npm install`, `npm run dev`). Every page renders from one Markdown file in the repo (`docs/hub/nav.json` maps them; the existing guides in `docs/` are reused, not copied), so a doc is edited once. For agents, each page is also served as Markdown at `/docs/<page>.md`, `/llms-full.txt` holds every page in one file, and `llms.txt` and `sitemap.xml` list the pages. Vercel builds the site on every deploy: its build command is `npm run docs`'s `node scripts/build-docs.mjs`, which writes the pages, `search.json` and `llms-full.txt` into `apps/website`. Those outputs are gitignored, never committed, so docs PRs do not conflict with each other on them in the merge queue (they used to, every round). Only the generated docs list in `llms.txt` and the docs URLs in `sitemap.xml` stay committed, since they change only with `nav.json`. The **Docs site** workflow (`.github/workflows/docs-site.yml`) keeps those two current without anyone remembering to: on a pull request that touches a docs source it rebuilds and, only if they changed, commits them to the PR branch with the repository App token (so CI re-runs on that commit); on main (push, a six-hourly schedule, or dispatch) it opens a `docs-site/regenerate` PR instead, since main only changes through PRs. A fork PR cannot be pushed to, so there it fails and asks for `npm run docs`. `npm test` checks that every docs link and heading anchor resolves and that the workflow watches every page source. A PR that changes user-facing behaviour updates the page describing it (AGENTS.md). Dark-only, matching the marketing site. The homepage nav and footer link to it.
- **Desktop packaging & release** `[shipped]`, electron-builder (win/mac/linux), GitHub Actions release workflow, branded NSIS installer + Windows uninstaller, **macOS Developer ID signing + Apple notarization** (hardened runtime, entitlements, stapled ticket, and a `codesign`/`stapler`/`spctl` check that fails the release rather than the user's machine; ad-hoc signing survives only as the fallback that keeps unsigned local builds launchable), and a self-updater against published GitHub releases (`[changed 2026-10-17]` run by the engine daemon instead of Electron's electron-updater, over the same `latest*.yml` feeds with SHA-512 checks, so existing installs update across the change; the Windows install path is verified with a stand-in installer, the macOS bundle swap and Linux AppImage/deb paths are implemented but not yet verified on hardware; see "Native dialogs, the OS shell and updates" under the engine). The desktop title bar's version pill is the complete update experience: it becomes **Check for updates** on hover or keyboard focus, keeps fast checks legible for at least 500 ms, confirms `latest`, offers **Download & install**, **Download only**, or **Skip** for a newer version, shows real download progress, stages **Install & restart**, stays visible while restarting, reports **Updated to vX.Y.Z** on the next launch, and exposes retry/details on failure. Skipping suppresses only that release and a manual check restores it. Settings uses the same live state and actions, while the existing first-run auto-check consent remains in place. Web keeps the same-build comparison and refresh fallback instead of desktop-only install controls. `[updated 2026-10-02]` Settings → Updates is now **per-check**, one toggle each: **App updates** (the version check above), **Provider model lists** (a background re-read of every configured provider's catalog, on by default, which is how a new ChatGPT model shows up in the picker without an app release), and **Skills catalog** (a background refresh of the skills marketplace shelf, opt-in). A **Refresh catalogs now** button runs the metadata checks on demand; they only swap lists, nothing is downloaded or installed. Released through v0.6.0, which is the first build actually signed with the Nekko Labs Developer ID certificate and notarized by Apple.
- **Self-hosted Local Web UI** `[shipped]`, `npm run web` / `npx nekko-agent` serves the same UI; localhost bind by default, token to expose.
- **Docker edition** `[shipped]`, multi-stage image, compose with volume workspaces + `host.docker.internal`, non-root, GHCR publish.
- **Native Android app** `[implemented 2026-10-11; device verification pending]`, Kotlin / Jetpack Compose in `apps/android`: pairing, the computer's chats, live streamed replies, queue/stop, approvals and questions over the E2E relay. Phone-side models, push and Play distribution are planned. See "Native Android app (2026-10-11)".
- **Retired Expo app** `[removed]`, the Expo/React Native implementation and its dedicated CI have been removed. Phone clients are the native SwiftUI (`apps/ios`) and Kotlin/Jetpack Compose (`apps/android`) apps. Their remaining feature and release gaps are tracked in the native phone specifications. Shared relay, push infrastructure, Local Web UI and native CI remain supported.
- **Remote push (relay-mediated)** `[shipped]`, APNs + FCM, dependency-free, content-free "a run finished" notifications, tokens registered **per device** and dropped on revocation; real delivery pending creds + device.
- **Phone remote control** `[shipped]`, run and manage chats, training, and goals from a paired phone. Relay v2 (per-device connections, unicast routing, rate/size limits), agent-side **device registry** with 10-minute single-use pairing codes, rename/revoke (live kick), and secret rotation; Remote access settings card (device list, expiring pair QR); phone **bottom tab bar**; remote access persists across restarts. Managed relay live at `wss://nekko-agent-relay.fly.dev` (free during beta; entitlement gate built for the Cloud launch); self-hosting is one Docker command (`ghcr.io/nekko-labs/nekko-agent-relay`, Compose/Coolify/Fly documented). Verified end to end through the live managed relay (enrollment, single-use codes, remote device management, revocation). See [docs/REMOTE.md](docs/REMOTE.md).
- **Messaging channels** `[shipped 2026-09-30]`, drive a chat from a messaging app, Telegram first. A long-poll bridge (in the engine daemon `nekkod` wherever it runs with a data directory, since 2026-10-16; in the TS host otherwise) binds each allowlisted chat id to one session, streams replies into one self-editing message, and turns approvals and `ask_user` questions into inline buttons; off by default and default-deny, configured on the Connectors page. Slack and WhatsApp adapters follow the same seam later.
