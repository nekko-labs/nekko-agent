# Beta signups and website analytics (2026-10-17)

**Beta signups.** People will join the beta from a form on nekkoagent.com with their email and, optionally, their name. The form on the home page's beta section posts to the live API (`https://nekko-agent-api.fly.dev/v1/signups`) with the email, `list: "beta"`, the page path, any `utm_*` tags from the URL, a hidden `website` honeypot field, `marketing: true|false` and `policyVersion: "2026-11-26"`. It wakes the API's machine with `/healthz` the first time someone focuses the email field, never on page load. `[changed 2026-11-03]` `[changed 2026-11-08]` The section opens with just **More is coming.** and "Want to get exclusive early features? Join our beta testers list." Signing up is two steps: the email (and the other fields) is saved the moment the button is pressed, then the card asks **What's your name?** with Save and Skip. Save re-sends the same signup with the name, which the API adds to the existing row only if it has none; leaving, skipping or a failed name post loses nothing, and the confirmation email has already gone out without the name. The privacy note mentions the name. It shows a thank-you on success, a try-again-later message on 429 (5 sign-ups per IP per hour), and a retry message on any other failure. The button reads **Get beta invites**. Under the email field, an unticked **Also send me product updates** box is a separate choice: without it the signup is for beta invites only (`marketing: false`), so consent to marketing is never bundled with the beta request. The form says **You must be 16 or older to sign up.** A privacy note under the form says the email is used only for beta invites, and for product updates only if the box is ticked, never shared, and removed on request to hello@nekkoagent.com. `[changed 2026-11-03: GDPR audit GD3; storing the two fields is the API's half, unverified here]` The API accepts browser calls only from nekkoagent.com, so the form can't be tested from a local copy of the site. `[Implemented, unverified until deployed]` Joining twice is harmless and looks the same as joining once, so the form never reveals whether an address is already on the list. We keep only what the form asks for, plus the page path and `utm_*` tags that brought someone there, never a full URL or IP. Sign-ups are double opt-in: a new signup stays pending and gets one "Confirm you want to join the Nekko Agent beta" email from hello@mail.nekkoagent.com (at most one per address per day) whose single-use link, valid 7 days, marks it confirmed and shows a thank-you page; every email has a one-click unsubscribe link. Unsubscribing deletes the sign-up and keeps only a hashed opt-out record so that address is never emailed again; a sign-up not confirmed within 30 days of its confirmation email is deleted (one never emailed is kept). Without the Resend key the signup still saves and no email goes out. `[Implemented, unverified until Resend and DNS are set up]` Each signup moves `pending → confirmed → invited → joined`, or to `unsubscribed`; signing up again after unsubscribing puts the address back to pending. The same table serves later waitlists under another list name.

**Users.** A signup is a request, not an account. Someone let into the beta becomes a **user**, the long-term account record that Cloud accounts will grow from; the signup row links to it. Nothing creates users yet.

**Where it runs.** A small API (`apps/nekko-agent-api`) on one small Fly.io machine, paid from Fly credits, with Postgres on Neon's free plan. Supabase was ruled out on cost, because its two free projects are already in use. Spending stays far under $100 a month. Fly can't cap a bill, so the limit is built into the app's config: one small machine that stops when idle and never scales out, at about $2 a month if it ran nonstop. The signup form wakes the machine when someone first focuses its email field.

**Website analytics (consent-first, 2026-11-26).** `[implemented and locally verified; not deployed]` Every public nekkoagent.com surface (home, beta, status, pricing, privacy, direct download, generated docs, What's new and the design-system page) offers one shared analytics choice. Before a person chooses, the browser does not request the PostHog SDK and sends no PostHog event. **Reject analytics** and **Allow analytics** use the same control shape, size, weight and colour and remain keyboard/focus accessible. The first-visit banner body says only “We never sell or share this data for advertising.” The **Privacy details** link explains what accepting or rejecting means. The stored choice can be reopened from **Privacy choices** on every page. Rejecting or withdrawing stops capture, clears the local analytics identity, and keeps the site functional. Global Privacy Control and Do Not Track override a prior acceptance while the signal is present and suppress SDK loading. The former unconditional Vercel Web Analytics integration is removed, so there is one analytics choice rather than two collectors with different controls.

After explicit acceptance, the website initializes the Nekko Agent PostHog project (project 686111, US cloud) from an `analytics-config.js` generated at build time from the public write-only `PROJECT_KEY` and `HOST` constants already shipped in `crates/nekkod/src/telemetry.rs`; production needs no additional Vercel environment variables and no private key. The client is opted out by default before its loaded callback opts the accepted visitor in. It captures one `$pageview` per load, the existing named `cta_click` and consented direct-download events, and the four `$web_vitals` metrics (CLS, FCP, INP and LCP). General autocapture, rage/dead clicks, heatmaps, errors, console logs, surveys, feature-flag requests and person profiles stay off. Query strings and fragments are removed from captured current/referrer/session URLs, including nested Core Web Vitals attribution URLs; GeoIP enrichment is disabled, and the project discards client IP before storage. Every accepted event carries `analytics_consent: "accepted"` and `analytics_schema_version: 2`, and the final `before_send` check drops an event if consent has since been withdrawn. Withdrawal propagates to other open tabs, while allowing analytics again on the same page safely reactivates the already-loaded SDK without duplicate navigation pageviews. Analytics events are configured for 84 months. Every CTA listed in the previous implementation remains covered through the delegated `data-cta` listener, but calls made before or after consent are dropped by the shared controller.

A first-party random identity and PostHog session id persist across page navigations so bounce and multi-page visits can be measured without identifying a person. Session recording is explicitly disabled in the SDK and is not part of website analytics. Web-vitals project capture is already on. Verification uses isolated local pages with the production hostname and intercepted PostHog ingestion so no production event is emitted. `[changed 2026-11-26: #3362 website slice]`

**Nothing third-party for analytics before consent (2026-11-26).** Opening a public page loads self-hosted site files only for analytics; PostHog's loader is requested only after **Allow analytics**. The status/pricing API requests and Vercel hosting logs remain the separately disclosed operational exceptions. The webfonts (Inter Tight, JetBrains Mono, Handjet, Space Mono; OFL-1.1, credited on the credits page) are self-hosted latin subsets in `apps/website/fonts/`, loaded by `fonts.css`, instead of Google Fonts. The download buttons' release info is fetched from GitHub at build time by `scripts/build-docs.mjs` (the build Vercel runs) into a gitignored `release.json`; without it the buttons link to the releases page. The API warm-up waits for the form (above). Known limit: `release.json` is as fresh as the last website deploy, so a release published without a website deploy after it leaves the buttons on the previous build's files until the next one.

**Privacy policy (2026-11-26).** `/privacy` (version date 26 November 2026; the beta form sends `policyVersion: "2026-11-26"`) covers the beta form, website analytics and Nekko Cloud accounts. Its analytics section matches the controller and verified project settings: no PostHog before consent; equal accept/reject; local choice storage; GPC/Do Not Track; visits, named CTA clicks, browser/device fields, path-only URLs, Core Web Vitals and first-party PostHog identity/session storage after acceptance; session recording disabled; withdrawal and erasure; US processing with IP discarded; 84-month event retention; and no sale, cross-context advertising share or advertising use. It names every other recipient and region, lists the GDPR rights, sets a minimum age of 16, preserves separate product-update consent and sign-up/account deletion disclosures, and explains the encrypted Relay's notification exception. Vendor DPAs remain an owner task.
