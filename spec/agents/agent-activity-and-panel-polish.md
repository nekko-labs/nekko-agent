## Quota read reasons, unavailable models and kept reply stats (2026-10-08)

Implemented; focused host/renderer tests and isolated renderer captures verified. Live provider behaviour (a real 429, a real token-endpoint rejection) is exercised only through mocked responses.

- **Why a quota is missing.** A failed subscription quota read records a reason (`LimitsProblem`): not signed in, sign-in expired (401/403, a rejected token refresh, or a ChatGPT sign-in without an account id), rate limited (429, honouring Retry-After), another HTTP status, unreachable, or an unreadable answer. The Utilization panel says so ("Sign-in expired. Sign in again in Settings.", "Rate limited by the provider. Retrying at 14:05.") with a Manage providers link for sign-in problems, instead of "Quota unavailable." The reason is read over `limits:problem` only after an empty answer. Codes and counts only: no token, URL or response body is stored or shown.
- **Backoff.** After a failure the host waits 1 minute, doubling per consecutive failure up to 30 minutes, or longer when Retry-After says so; the existing 30 second per-account throttle still applies on top. An expired or missing sign-in stops quota requests entirely until the stored token changes (a new sign-in, or a chat's own refresh succeeding). A success clears the reason. Polling cadence (60 s idle, 30 s while a subscription chat runs) is unchanged.
- **Unavailable model.** When a chat's saved model is not in its provider's list (for example a signed-out subscription), the model chip keeps naming it, struck through and marked "unavailable" in the warning colour, instead of a floating "Choose a model" popup. The floating popup is removed everywhere. A one-line note ("gpt-6.1-sol is not available right now. Select a model again.") shows in the chat's own actions row only in the selected Agents wall window or a full chat pane; other wall windows only mark the chip. Picking a model clears it. The saved model on the session is not changed until the user picks.
- **Reply stats kept in the chat.** When a reply finishes, the host attaches `turnStats` to the reply's last assistant message before saving: provider, model, effort sent, input/output/cache tokens summed over every model call in the reply, decode time, wall time, model calls, tool steps and how it ended. The transcript shows them under the reply ("GPT Sol · ChatGPT · High effort · 14k in · 640 out · 80 tok/s · 21s", exact counts on hover), so a long chat shows which stretch ran on which model and where the tokens went. A reply that ended on tool calls gets its own stats row after its working steps. The floating status row keeps the live readout while streaming and the sleeping/blocked states, but no longer repeats finished numbers once they are on the reply, and the "Reply stats" placeholder is gone. The same totals and effort are added to `replies.jsonl` (counts only, no text) for later analysis. Daemon-driven runs keep the stats across transcript checkpoints. Incognito chats keep stats on their in-memory messages and write nothing to the reply log, as before. Replies from before this change have no stats and show none; nothing is backfilled or estimated.

## Primary folder defaults and saved access revocation

Implemented, with focused automated regression coverage. Desktop interaction and visual evidence remain unverified in this batch.

- The last explicitly chosen primary folder is the default for new chats and is persisted locally across restarts. Explicit No folder is persisted too, including when a chat already has no primary. Supporting folders are not inherited by new chats.
- Refreshing settings or the folder list never replaces the current selection with the first saved folder. A saved default that is no longer registered does not grant access when creating a chat. Explicit No folder also prevents first-prompt auto-filing.
- Each saved folder in the composer picker has a separate X action labeled Revoke access. This removes saved workspace access and detaches that folder from saved chats, without deleting the directory, files, or chat worktrees. Removing a primary does not silently promote a supporting folder.
- The host rejects revocation while a running chat uses that folder as primary or supporting, and rejects primary/supporting selection mutations while the affected chat is running. Folder selection rejects IDs that are no longer registered. Revocation is not a filesystem permission boundary: independently attached paths and general tool permissions are unchanged.
