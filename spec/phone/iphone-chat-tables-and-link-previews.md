# iPhone chat: tables, and previews of files and local pages the agent links (2026-10-26)

**User intent (issue #1095):** Philip sent a screenshot of an iPhone chat where a Markdown table showed as raw `| a | b |` text, and two links did nothing useful: "Open the interactive design examples" (an HTML prototype the agent wrote, linked by its absolute path on the computer) and "Browser preview" (`http://localhost:PORT` on the computer). He wants tables to render, and links like these to open on the phone: the prototype interactive, the dev server's page live, served by the computer through the relay. The desktop's rules for which links count are the model (`apps/desktop/src/renderer/chatArtifacts.ts`, [Rich replies](../code/rich-responses-reports-and-design-workspace.md)).

**Status `[implemented 2026-10-26; the package logic is unit-tested on Linux (MarkdownBlocksTests, ChatLinksTests, PreviewsTests, PreviewLoaderTests); the SwiftUI and WebKit code is compiled and tested only on macOS CI; not yet run in the simulator or on a device]`.** The computer side (`artifact:read`, `preview:fetch`, and the "linked in this chat" check) is a separate change on the same issue; until it ships, a tap shows the computer's refusal ("Update Nekko on it").

## What the user gets

- **Tables.** A GitHub pipe table in a reply is a grid: the header semibold on a faint fill, hairlines between rows, each column aligned as its `:---`, `:---:` or `---:` says. Cells keep inline Markdown (bold, code, links). Outer pipes are optional, `\|` is a literal pipe, a short row is padded and a long one cut to the header's width, and a table inside a code fence stays code. A wide table scrolls sideways in its own rounded frame; a long cell wraps at a width cap (it grows with Dynamic Type). Touch and hold offers *Copy table* (tab-separated). VoiceOver reads each cell as "Row 2, Name: Nekko" and the header cells as "Column header: Name".
- **Which links are previews.** In an assistant reply, a link to an absolute path (`/Users/…`, `C:/…`, `C:\…`) or a `file://` URL (percent-decoded; `file:///C:/x` is `C:/x`; another host is ignored) whose file is HTML, SVG, PNG, JPEG, GIF, WebP, Markdown, text, JSON, CSV or PDF opens the preview window. So does an `http(s)` link to `localhost`, `127.0.0.1`, `[::1]` or `0.0.0.0` with a port. Other web and `mailto:` links open in Safari or Mail. Anything else (a relative path, `javascript:`, a loopback address with no port) does nothing. A path Markdown can't read as a URL (backslashes, spaces) is rewritten to a `file:` link before rendering, so it is tappable too.
- **Preview cards.** Under each finished reply, one card per distinct file or loopback page it links (in reading order; code fences and inline code skipped, as on the desktop; bare `http://localhost:NNNN` and `<http://…>` autolinks count too). The title is the link's label, or for a generic label (`index.html`, `README`, the file name) a name made from the folder or file (`design-examples/index.html` → *Design examples*); under it the file name or `host:port`, and an open arrow. HTML pages and loopback pages show a picture of the page: it renders at a phone's width (390 pt) in the isolated web view, without touches, scaled into a 160 pt card, and is then kept as a snapshot. Images show a thumbnail; other files an extension chip. Thumbnails load only when the card is on screen and the reply has finished streaming, two at a time.
- **The preview window** opens full screen from a card or a link. An HTML prototype runs with JavaScript and can be clicked through, and its relative CSS, scripts, images and pages load beside it. A loopback page loads with everything it asks for from the same origin. SVG renders in the same web view; images zoom (pinch, double-tap); Markdown is formatted; text, JSON and CSV are monospaced and selectable; a PDF opens in PDFKit. A text file the computer cut at 1 MiB says only the start is shown; an HTML page or binary file that is too large says so instead of opening half. The toolbar has the title and file name, **Done**, **Reload** (reads the page and everything it uses again) and a menu with **Copy path** / **Copy address** and **Share**. While it loads it shows progress; a failure shows a plain reason and **Try again**: "This file wasn't linked in this chat", "The preview server on your computer isn't running", "The preview server on your computer didn't answer", "This file may hold secrets, so it never leaves your computer", "Your computer can't open previews for a phone yet. Update Nekko on it." The window uses the app's palette and Dynamic Type, and its controls have VoiceOver labels.

## How it works

- **Package logic, unit-tested on Linux** (`apps/ios/Protocol`): `MarkdownBlocks` (the block parser, moved out of the app, now with tables), `ChatLinks` (classify a link, rewrite unreadable destinations, extract the cards with their titles), `Previews.swift` (the two requests, decoding their replies, the custom schemes' URL mapping, the content rule list, plain error messages) and `NekkoKit/PreviewLoader` (the calls, an in-memory cache per chat and path or URL, 32 MB at most, oldest dropped first, so a card's thumbnail and the window read the computer once; the two thumbnail slots).
- **Two read-class phone channels** on the computer: `artifact:read [sessionId, path]` → `{ path, name, mime, size, mtime, kind, content | base64, truncated }`, allowed for a file the agent linked in that chat and for files in the folder of a linked `.html`/`.htm`; `preview:fetch [sessionId, url, { method: "GET" }]` → `{ url, status, contentType, headers, base64, truncated }`, allowed only for a loopback origin the agent linked in that chat. The phone sends absolute `/`-separated paths. A 3xx from the server is shown as "sent somewhere else", never followed by the phone.
- **The web view's schemes.** A file loads as `nekko-artifact://local/<absolute path>`, so relative links resolve beside it, and every request under that scheme is an `artifact:read`. A loopback page loads as `nekko-preview://<host>:<port>/<path>?<query>`, and each request is a `preview:fetch` of the same path on the linked link's scheme, host and port; a request for another port is refused on the phone.

## Boundaries (isolation)

- The web view has a non-persistent data store, JavaScript on (prototypes are interactive) but no script message handlers and no bridge to the app, link previews off, no file access, no pop-up windows, and media that only plays when tapped.
- **No network.** A `WKContentRuleList` blocks every URL, then allows only the two app schemes, `about:`, `data:` and `blob:`; the view is not created until that list has compiled, and a failed compile refuses to open the preview. The navigation delegate cancels any navigation off the app schemes; only a link the user tapped to an ordinary web or mail address leaves, to Safari or Mail. `target=_blank` opens in the same view.
- The phone never reaches the computer's files or ports: the computer reads them and only for what the agent linked in that chat. The bytes stay in memory on the phone (no disk cache), and Reload forgets them.

## Acceptance

- Unit tests (Linux, `swift test` in `apps/ios/Protocol`): table parsing (alignment, optional outer pipes, escaped pipes, ragged rows, fences, no delimiter, VoiceOver labels); link classification for each path and URL shape above; card extraction and titles; scheme round trips including Windows drives, spaces and `#`; origin pinning for loopback requests; decoding both replies; error wording; the loader's cache, reload, per-chat forgetting, byte limit, cut text and slot limit.
- App test (`apps/ios/Tests/AppTests.swift`): a table through `MarkdownText.parse`, and a Windows path with a space rendered as a link that routes back to the same path.
- Not yet: a simulator or device run of the preview window and cards, screenshots in light, dark and the largest text size, and a VoiceOver pass. Status stays *implemented, unverified* until then.
