# Native iOS app (2026-10-16)

**User intent:** Philip asked (2026-10-16) to finish the native SwiftUI iPhone app using Orca's mobile app as the competitive reference, **Tailscale first** and on the Nekko relay, following the Android app's connection approach. It replaces the read-only direct-HTTPS foundation, which never shipped: one transport, the end-to-end encrypted relay, as on Android. Competitive notes: [reports/ios-native-competitive-2026-10-16.md](reports/ios-native-competitive-2026-10-16.md).

**Availability** `[limited beta, 2026-10-24]`: in a limited beta through TestFlight. Builds upload to App Store Connect from `main` (`.github/workflows/ios-testflight.yml`). Not yet released on the App Store (#615). Before that release, the App Store privacy labels need a review against the privacy manifest (`apps/ios/App/PrivacyInfo.xcprivacy`).

**Scope `[shipped 2026-10-16 (#630, #631); verified on Linux (50 protocol tests + live relay itest) and on macOS CI in the simulator (build with the widget extension, unit and UI tests, the live journey in light and dark, deep-link pairing, the largest text size); no physical iPhone yet]`:**

- **Wire and crypto** (`apps/ios/Protocol`, package `NekkoProtocol`): PBKDF2-HMAC-SHA256 (CommonCrypto) → AES-256-GCM (CryptoKit), byte-identical to the agent's WebCrypto through the shared `e2e-vector.json`; pairing links; the relay v2 client with Android's state machine (sealed HELLO, one-time code dropped after the first welcome and never resent, kick 4001 and bad key terminal, offline computer polled every 15 s, agent-online re-HELLO, network-change reconnect); `URLSessionWebSocketTask` transport with 25 s pings. Channel names are pinned to the computer's `PHONE_CHANNELS` by a test.
- **Transport rule (TASKS PH1, phone side):** `wss://` anywhere; plain `ws://` only toward Tailscale (`*.ts.net`, 100.64.0.0/10, fd7a:115c:a1e0::/48), the LAN (RFC 1918, link-local, `.local`, ULA) or loopback in the simulator. A plaintext link to anything else is refused before it is dialed, with the reason. ATS matches: `NSAllowsLocalNetworking` plus an insecure-loads exception for `ts.net` only.
- **Tailscale first:** the pairing screen leads with the Tailscale route (private relay on the computer via `npm run relay:tailscale`) and shows whether Tailscale is connected on this iPhone, read from its interface addresses (no VPN entitlement or Tailscale API). When a tailnet relay can't be reached the banner says why: Tailscale off on the phone, or on but the computer not answering. When Tailscale is off on the phone, the banner and *Settings → Connection* offer **Open Tailscale** `[2026-10-19, TASKS IO-19 TS-4]`. It opens the Tailscale app (`tailscale://`, listed in `LSApplicationQueriesSchemes`), or its App Store page when the app isn't installed. iOS doesn't let another app turn a VPN on, so this is as close as the app can get.
- **App:** pairing by QR, paste or deep link (`nekko-agent-pair:`, with a confirmation sheet naming the relay and route); several computers, one connection at a time; chats grouped as on the desktop with Working / Needs you, a Needs you section, search, complete / restore / delete (following the computer's main action and delete confirmation), pin, rename; the chat with streamed Markdown, reasoning, tool steps and output, the approval card with the exact input and severity, questions with multi-select and Something else, queue while running, Stop, the computer's skills, up to four photos (scaled JPEG data URLs, `images` in `chat:send`), dictation (Whisper on the computer when Nekko Voice is installed, else on-device iOS speech; `[updated 2026-10-27]` always-on, cut into segments at each pause (30 s at most): the words go into the message box, and only an explicit "Nekko, send it" sends; speech on the phone stays on the device; see *Always-on dictation*), per-chat model and tool policy; new chat with model (every enabled provider, starred first), folder and tool policy; the computer's phone-settable settings; theme that follows the computer (light/dark and accent) or the phone.
- **iOS surfaces (beyond Android and Orca):** a **Live Activity** per running chat on the Lock Screen and in the Dynamic Island (step, elapsed time) with **Allow / Deny** for a waiting tool and **Stop**, as App Intents that run in the app's process; local notifications while backgrounded with Allow (requires unlocking) / Deny actions; haptics for approvals and questions. `[updated 2026-10-27]` The activity's icon (Dynamic Island compact and minimal, the expanded island and the Lock Screen) is the pixel cat face from the chats screen instead of a system symbol, filled in the run's color (violet working, orange waiting on an approval or a question, green finished, red failed) with a small drawn badge bottom right: an ellipsis while working, "!" when it needs you, a check when done, an x when it failed. It hops when the phase changes and on every third step, blinking on alternate hops while working, and smiles when done. A Live Activity can't run its own clock, so the hops ride the updates the app and relay already send (at most one every 2 s while running). Colors and badge are checked by a render test; the hop on a real Dynamic Island is unverified.
- **Security:** pairing material in the Keychain (`AfterFirstUnlockThisDeviceOnly`, never synced); Face ID / passcode app lock on by default, on every open and return, covering the app-switcher snapshot, required to turn it off (`[updated 2026-10-23]` the cover is a window of its own above the app's, so it hides open sheets such as Terminals and Files too, which a view in the app's screen was drawn under; it shows the app icon tile on the app's background, edge to edge, and the old outline cat is gone from the app; `[updated 2026-10-24]` the tile is gone too: the cover, first run and pairing show the borderless brand mark in lavender, as the desktop, Android and the opening animation do. The tiled square is only the Home Screen icon); with the lock on, notifications and Live Activities omit chat titles and tool details. Allowing a tool from outside the app needs an unlocked phone; denying does not. Provider keys never reach the phone (the computer strips them; a live test checks the raw reply).
- **Live Activities while suspended** `[implemented 2026-10-16; APNs delivery unverified until the relay has the key and a device runs it]`: each activity's ActivityKit push token is registered with the relay under a hash of the session id. The computer sends the relay content-free phase changes (started, waiting on an approval or a question, running again, finished, failed; for an approval the opaque call id and risk level, so the buttons work), and the relay pushes the update or the end. The relay learns neither the chat nor any text.
- **Push:** the APNs token is registered with the relay on every connect, with the kinds of push this phone wants (see *Notification controls*). Content-free, using the shared relay push boundary. Needs the APNs key on the relay and a signed build.
- **iPad and Shortcuts:** a split view (computers and chats beside the open chat) on regular width; an "Ask my computer" App Shortcut that starts a chat from Siri, Spotlight or the Shortcuts app; and "What needs me?" `[2026-10-17]`, which answers from the widget's counts-only snapshot without opening the app ("2 chats need you on Studio, and 1 is working.", with the numbers' age once they're over five minutes old).
- **Home Screen and Lock Screen widget** `[2026-10-16]`: "Needs you" shows how many chats wait on you and how many are working, the computer's name and whether it is online, and how old the numbers are. It shows counts only, never titles or tool details, so it is safe on a Lock Screen. It comes in small, rectangular and circular sizes. The app writes the snapshot to the App Group `group.dev.nekkolabs.nekkoagent` and reloads the widget only when the counts change; the widget never connects to anything. **Apple Watch:** approvals reach a paired Watch through the actionable notifications iOS mirrors there (Allow / Deny included), with no watchOS app; a dedicated Watch glance stays a follow-up.
- **Store readiness** `[2026-10-16]`: the app icon is the desktop cat mark, full-bleed and opaque (`apps/ios/scripts/render-icon.sh` renders it from `icon.svg`). `PrivacyInfo.xcprivacy` declares no tracking and no collected data, since chats go end-to-end encrypted to the user's own computer, and the one required-reason API (UserDefaults, CA92.1). CI checks that both are in the built bundle. The export-compliance answer is left to the owner.
- **Accessibility** `[2026-10-16; green in the simulator, run 38970247435, light and dark; VoiceOver on a device not yet]`: the UI tests run iOS 17's accessibility audit (`performAccessibilityAudit`) on welcome, pairing, chats, new chat, an approval and a question, in light and dark, and fail on any contrast, clipping, hit-region, label or trait finding (`apps/ios/UITests/AccessibilityAudit.swift`; every finding, blocking or not, is attached as `a11y-<screen>`). Not blocking: the audit's Dynamic Type heuristic (the largest accessibility text size is driven for real by `testLargestTextSizesStillFit`), disabled controls (exempt under WCAG 1.4.3), elements not fully on screen, the system search field's placeholder, and findings the audit can't attach to an element. Two exclusions are named at their call sites: on welcome, the Get Tailscale link (it sits under the translucent Pair bar at first launch, and is audited on the pairing screen), and on the approval and question screens, the transcript's tool step. That step is reported clipped or low-contrast though the capture shows it whole; four fixes didn't change it, so it is left for a device check. The first audit found low contrast in the light theme, so the palette changed: accent `#5A4AE8`, faint ink `#6A6A76` (dark `#8E8E9B`), and darker danger, warning, running and success colours. Every text colour now meets WCAG AA (4.5:1) on paper, surface and surface2 in both themes, held by `PaletteTests`. Button text on the accent is whichever of white or near-black reads better, so dark-theme prominent buttons use dark text. Form section headers are in sentence case and full ink, and footers use the app's ink, rather than the system's small grey capitals. Links are at least 44 pt tall. When an approval or question card appears, the transcript scrolls so its latest step stays above the card; it used to sit hidden behind it. The approval buttons are large, and Deny uses ink. The empty chat list is a plain view, not `ContentUnavailableView`, which clipped. The Folder and Tools pickers open as lists, and the computer's default mode is named in the footer rather than in a truncated menu label. A keyboard Done key on pairing and new chat lets the keyboard be put away. `[updated 2026-10-23]` Not in a chat: on iOS 26 that key floats as a glass button over the composer's send button. There, scrolling or tapping the transcript puts the keyboard away, and the message box has a *Hide keyboard* VoiceOver action.
- **Share to Nekko** `[2026-10-16; unit-tested on Linux, simulator journey in CI; the share sheet itself not yet driven on a device]`: "Nekko Agent" appears in the share sheet for text and a single web link, like Android's AN-11. The extension (`apps/ios/Share`, `com.apple.share-services`) cleans the text with the same rules as Android (`SharedText`: page title above the link unless the text already has it, CRLF to LF, control characters dropped, cut at 20,000 characters with a note, never splitting a character). It leaves the text in the App Group's defaults (`ShareInbox`) and shows it with "Open Nekko Agent and New chat starts with this". iOS doesn't let a share extension open its app, so the next time the app comes to the front with a computer paired, New chat opens with the text in the message box, editable, and **nothing is sent until Start**. The text waits at most 10 minutes. It is removed as soon as the app reads it, or with **Don't keep**, and the extension never connects to the computer. With the app lock on, New chat opens behind the lock. The app, the widget and the share extension each ship a privacy manifest that declares App Group defaults (`1C8F.1`). - **Chat list when offline** `[2026-10-17; unit-tested on Linux (NekkoKit) and in the app tests; on by default since 2026-10-20 (OF-9); not yet on a device]`: **on by default** (decided 2026-10-19). A new install, and one that never touched the switch, gets it on; a deliberate off stays off (the setting is written only when the switch is flipped, so its presence is the user's choice; `OfflineSetting`). *Settings → Offline → Keep the chat list when offline* keeps each paired computer's chat list on the iPhone, as last read from it, so opening the app away from the computer (no tailnet, relay down, computer asleep) still shows the chats grouped as usual, under a line "Saved list from 10:42. It updates when Mac answers." It is replaced the moment the computer answers. What is kept (`SavedChatList`, versioned): each visible chat's id, title, updated and completed times, folder, pin and manual order, plus the folder names and optional absolute host paths. Never replies, first messages, models, transcripts or anything a chat contains. One JSON file per computer in Application Support, data protection *until first unlock* (so a launch from a notification can read it), excluded from backups. Forgetting a computer deletes its file; turning the setting off or *Forget everything* deletes them all. The app lock still covers the list. A chat opened from it shows its saved copy when there is one (below).

- **Changes, read only** `[2026-10-17; projection and gate unit-tested in TS and Rust and held equal by the phone golden; decoder unit-tested on Linux; a real file write read over the live relay, with accepting refused (Swift and Kotlin itests); both sheets opened in the simulator and emulator journeys, the iOS one through the accessibility audit; not yet on a device]`: a chat's **More → Changes** (on Android, the **Changes** button in the chat's top bar) shows what the agent changed in that chat, as Orca's mobile app does, but read only. It is **off unless the computer allows it**: *Settings → Remote access → Let phones see changes* on the desktop (`phoneChanges`, which a phone can't set). The computer computes the diff and sends only that (`changes:list` through `phoneChangesView` in `packages/shared/src/phone-changes.ts`, the same projection in the daemon's `crates/nekko-remote/src/phone_changes.rs`):
  - paths cut to their last two parts, never the full path on the computer;
  - a unified diff with 3 lines of context; at most 50 files, 400 lines and 64 KB a file, 512 KB in all; past that a file says how many lines changed, and the rest are counted;
  - files that may hold secrets (`.env*`, keys and certificates, `.ssh/`, `.aws/`, `.gnupg/`, `.npmrc`, `.netrc`, `credentials`) counted but never shown; binary files named only.
  - **Ask about a change:** touch and hold a change (a hunk) for *Ask about this change*, or a file's header for *Ask about this file*. The sheet closes and the message box gets the file, the line range and the changed lines quoted as a diff (at most 12), after anything already typed, unsent, like Orca's diff comments. A hunk rather than a single line, so the target is big enough to hit (the accessibility audit flagged single lines). VoiceOver offers the file action; TalkBack offers both.
  - Accepting or reverting changes, reading other files and listing folders stay refused (`PHONE_ALWAYS_DENIED`). With the switch off the computer refuses `changes:list` and the phone hides the menu item.

- **Notification controls** `[2026-10-19, IO-30; computer frames in nekko-remote, held to the agent golden (recorded from the TS agent before it was deleted) and the nekkod itest; relay unit-tested; NekkoKit on Linux; Settings, the test and its banner in the simulator journey against the real relay, light and dark; Apple push itself not yet, the relays have no key]`: *Settings → Notify me about* has a switch per kind: **Approvals and questions**, **Finished replies**, **Failed replies** (each starts as the old single switch was). They govern the notifications the app shows while backgrounded, and the phone registers its push token with the kinds switched on, so the relay pushes only those (a phone that sends no kinds, as legacy clients do, still gets every kind). The computer now asks the relay for a push when a tool waits for approval or the agent asks (needs you), when a reply finishes, and when one fails, each with only its kind and the chat's opaque tag (the same hash the Live Activity uses), never text. **Send a test notification** goes from the phone to the computer (`push:test`, answered by the relay agent itself, not through the phone allowlist), which asks the relay to push to that one phone even while it is connected. The relay tells the phone when it registers whether it holds an Apple push key; without one (a relay on the computer or the tailnet) the app shows the notification itself and says so under the button, naming the relay. **Dismissal sync:** when an approval or a question is answered anywhere (the desktop, another phone, this one) or its run ends, the computer sends the relay a content-free `dismiss` with the chat's tag; the relay forwards it to connected phones and sends iPhones a silent push, and the app removes that chat's needs-you notifications, pushed or local (`removeDeliveredNotifications`).

- **Hold to talk** `[2026-10-19, IO-28; press and release logic unit-tested on Linux; the setting in the simulator journey; not yet held on a device]`: *Settings → Dictation → Microphone* chooses **Tap to start and stop** (the default; `[updated 2026-10-27]` now **Tap to keep listening**, see *Always-on dictation*) or **Hold to talk**: press the microphone to record and let go to stop. A hold too short to say anything is thrown away with a hint, a release before the recorder started stops it as soon as it does, and the first press only asks for the microphone. - **Always-on dictation** `[2026-10-27, IO-28 follow-up; the command runner, the order of segments, the WAV writer and the on-device-only refusal unit-tested in the simulator (NekkoNativeTests); listening itself not yet verified: the simulator here could not open the microphone (its audio server timed out), and no device yet; needs a device check: the screen staying on through Auto-Lock, command haptics while recording, echo cancellation (voice processing) and AirPods]`: User intent: dictation on the phone should work like the desktop's Nekko Voice: keep listening, type what is said, and act on "Nekko, ..." commands, without ever sending speech to a server. *Settings → Dictation → Microphone* now reads **Tap to keep listening** (the default) or **Hold to talk**.
  - **Listening.** A tap on the microphone keeps it open (an `AVAudioEngine` input tap, converted to 16 kHz mono; other audio keeps playing, not ducked, while a hold still ducks it) and cuts what is said into segments at each 1.2 s pause, at most 30 s each, with the shared segmenter (`VoiceSegmenter`, the desktop's rules). Silence never stops it. While it listens the screen stays on (`isIdleTimerDisabled`, put back as it was on stop), since speech does not reset Auto-Lock and a lock would end listening. Echo cancellation (voice processing on the input) is on while it listens, so VoiceOver and what the speaker plays are not transcribed; other audio is not ducked by it. Command haptics play while recording. AirPods' microphone works (Bluetooth HFP), so AirPods use call-quality audio while listening. The app has one microphone: starting to listen in one chat (two chats in panes on iPad or landscape) stops the other's. Between the tap and the microphone opening (permissions, asking the computer) the button shows a progress and a second tap does nothing; if the app went to the background (a lock, an app switch) or the chat closed meanwhile, the microphone does not open. The microphone and speech permission prompts only make the app inactive, so they do not cancel it: the first tap opens the microphone once they are answered. The microphone shows whenever dictation is available, also with text in the box, so listening can be started again after a stop. It stops on the stop button, when the app leaves the screen (lock, app switch, Control Center), when the chat closes (also when a voice command opens another chat, New chat or Settings, and then the rest of that segment's words go to this chat's draft too), on an audio route change, an interruption (a call, an alarm, Siri) and a media services reset; it never starts again by itself. A stop the person did not ask for (lock, an interruption, a route change, a media reset, the Face ID sheet of a voice merge, the other pane starting) shows "Stopped listening" under the box and VoiceOver says it; a tap on stop or leaving the chat says nothing. On stop the words said last are still transcribed. Words that finish transcribing after the chat closed go into that chat's saved draft as plain text, and no command in them runs; the draft is in the box when the chat opens again. When the app leaves the screen the last words, and any segment already on its way to be transcribed, are finished only in the short background time iOS gives (asked for whenever anything is left, ended once the queue is empty), else dropped. When the phone will do the transcribing, speech permission is asked and on-device support is checked when listening starts, so a phone that can't refuses before anything is said; when the phone is already allowed and recognizes on the device, nothing is asked of the computer first and the microphone opens at once. Hold to talk is unchanged: one segment per hold.
  - **Transcription.** Segments are transcribed one at a time, in spoken order (the computer refuses a second `voice:transcribe` while one runs): Whisper on the computer when Nekko Voice is installed there (a failed call is tried once more, and while the computer is still online its failure is said rather than handed to the phone), else this iPhone's recognizer with `requiresOnDeviceRecognition` always set. A phone that can't recognize its language on the device refuses with "This phone can't turn speech into text on the phone for <language>, so dictation is off. Turn on Nekko Voice on your computer to dictate.", stops listening, and sends nothing (before this, such a phone fell back to Apple's servers).   - **Where.** A computer's page: **Add a provider** under Providers, and a switch on each provider row. Android: Settings → Providers (AN-36, [native-android-app.md](native-android-app.md)).
  - **The sheet.** A grid of kinds (Anthropic, OpenAI, OpenRouter, Ollama, LM Studio, vLLM, OpenAI-compatible), a key field for the cloud kinds, an address for the local ones (as the computer reaches it: *localhost* means the computer itself), a name, and *Save to <computer>*.   - **How the key travels.** The phone reads the computer's sealing key (`providers:sealKey`: a P-256 public key, X9.63, base64url, and the context `nekko-provider-key-v1`), seals the key the user typed to it with the same sealed box Nekko Cloud sync uses (`SyncCrypto.seal`), and sends `{id, kind, label, baseUrl?, sealedKey}` on `providers:saveSealed`. ## Saved computer folders from iOS (2026-10-25)

**Intent:** manage the computer's saved project folders without returning to the
computer, and distinguish folders with identical names by their absolute paths.

**Implemented; focused Swift tests, native simulator build, and isolated fixture-backed
UI interactions verified. Hardware and live-host verification remain untested:**

- Chats keeps unassigned chats visible without a **General** heading or collapse
  control. Named project headings show their absolute host path when available.
  The new-chat Folder chooser shows names and paths, with **No folder** for an
  unassigned chat. Older hosts and saved lists without paths still work.
- **Chats → Computers and settings → Files** opens saved folders and their files.
  **Add computer folder** accepts a typed absolute path on the active computer
  (POSIX, Windows drive-rooted, or UNC), never a phone document picker. The host
  stores the supplied path without validating directory existence; the phone does not resolve it locally.
- A folder's swipe/context action **Remove saved folder** requires confirmation
  that only the saved entry is removed: the folder and files stay on disk.
  Add/remove controls are disabled offline and during an in-flight operation;
  validation, signing, access refusals and host errors are presented to the owner.
- Both mutations use the signed `ComputersStore.call(change:)` flow:
  `workspace:addByPath [path]` and `workspace:remove [id]`. Each response replaces
  the full workspace array. Removal also reloads chat summaries so reassigned
  chats appear in the right group. Results from a replaced connection are ignored.
- Optional absolute paths are retained alongside folder names in the existing
  protected, backup-excluded offline list when keeping that list is enabled.
  This deliberately exposes saved folder roots to the paired phone, not arbitrary
  file access; file browsing continues to use checked workspace/session ids.
  No folder mutation is queued for offline delivery and neither action deletes
  disk contents.

**Verification:** workspace decoding/legacy initializer and cache round trips,
POSIX/Windows/UNC path validation, signed exact mutation arguments, full-array
replacement, refreshed unassigned summaries, Change-off refusal and offline
no-send behavior are covered by focused Swift package tests. Isolated native UI
tests verify unassigned chats retained without General, path labels in Chats, Files
and New Chat, absolute-path validation, add, removal dismissal and confirmation.
Matching native screenshots were captured and visually inspected. Live host,
hardware authentication, iPad and VoiceOver remain unverified.
