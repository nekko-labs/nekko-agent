# Native Android app (2026-10-11)

**User intent:** use the phone to run chats on the models that live on the user's computer, from a real Kotlin / Jetpack Compose app (applicationId `com.nekko.native.android`, minSdk 28, targetSdk 36), not a web wrapper and not the Expo app. Started in parallel with the iOS migration because the Android client was assigned separately; it talks to the same relay and host as every other client, so nothing on the computer changes.

**Availability** `[limited beta, 2026-10-24]`: in a limited beta. Not yet published on Google Play.

**Scope of this version `[implemented; JVM, integration and build checks verified; not yet run on an emulator or device]`:**

- **Pairing:** scan the computer's pairing QR with the Google code scanner (runs inside Play services, so the app never asks for the camera permission), paste the link, or open a `nekko-agent-pair:` link from the system camera. The phone enrolls with the one-time code, which it forgets as soon as the computer welcomes it. Several computers can be paired; one is connected at a time; rename, switch and forget are on the Computers screen.
- **Remote chat, end to end:** the computer's chat list (top-level chats, active and completed, grouped as below) with Running / Needs you badges; new chats on any enabled provider, model and folder of the computer; replies streamed live; Stop; prompts sent mid-run are queued like on the desktop; the exact tool call behind an approval (command or input) with Allow / Deny; the agent's `ask_user` questions as tap-to-answer choices with a free-text "Something else". Transcripts are re-read after each turn and after a reconnect, so a phone that slept catches up.
- **Model choice comes from the computer** `[implemented 2026-10-13; verified on an emulator against a sandbox agent; not yet against the desktop daemon or the managed relay]`: the phone has no models of its own. *New chat* asks every enabled provider on the computer for its models in parallel (`models:list`, 6 s per provider like the desktop picker) and shows them in one list grouped by provider, the computer's starred models first, with search once the list is long. It opens on the computer's default model, else the model of its most recent chat, else a starred one; `Auto` is never offered. A provider that fails or times out shows *Couldn't list its models* with Retry, and one that answers with nothing says so, instead of the whole screen reading "No models found". Nothing about the models is stored on the phone.
- **Theme follows the computer** `[implemented 2026-10-13; verified on an emulator against a sandbox nekkod: live light/dark/accent changes and the phone-side override; not yet against the TS-only editions on a device, nor the managed relay]`: user intent is "settings in sync with the PC, starting from dark mode", step 1. *Settings → Appearance* on the phone offers **Same as computer** (default), **Phone setting**, **Light**, **Dark**, stored on the phone only. With *Same as computer* the app uses the computer's mode (a computer on System, or one not heard from yet, falls back to the phone's setting) and its accent for buttons, selection and, in light mode, the user's bubble. The computer announces changes live with the relayed `appearance:updated` event (`appearanceOf` in packages/shared/src/themes.ts, `appearance_of` in crates/nekkod/src/settings.rs, held equal by the relay golden): only `theme`, `themePreset` (shape-checked id) and the two accents (`#rrggbb`) leave the computer, never any other setting; the phone also reads the same fields from `settings:get` when it connects. Planned next: other shared settings both ways (default model, chat mode, effort), each opted in explicitly; preset surface colours (Nebula, Terminal and so on) are not drawn on the phone yet, only their mode and accent.
- **Readable colours** `[implemented 2026-10-16; JVM-tested; emulator captures in CI]`: the same palette change as the iOS app. Light theme: accent `#5A4AE8`, faint ink `#6A6A76`, danger `#B42318`, warning `#8F5C0A`, running `#1D4ED8`, success `#1E7A4A`. Dark theme: faint ink `#8E8E9B`. Every text colour meets WCAG AA (4.5:1) on paper, surface and surface2 in both themes, and the ink on a computer-supplied accent is whichever of white or near-black reads better, by contrast ratio rather than a luminance cut-off (`PaletteContrastTest`). Before this, faint text was 3.3:1 and the light accent 4.4:1 on paper.
- **Is Tailscale on?** `[implemented 2026-10-16; JVM-tested; emulator journey unaffected (it pairs over adb reverse)]`: like the iPhone app, the phone reads its interface addresses (a tailnet address in 100.64.0.0/10 or fd7a:115c:a1e0::/48, no permission). When the computer's relay is on the tailnet (a `*.ts.net` name or a tailnet address) and Tailscale is off on this phone, the connection banner says so instead of "Connecting…", and so does the pair-confirm card: "Tailscale is off on this phone. Open the Tailscale app and connect to your tailnet to reach …". If the addresses can't be read it claims nothing (`protocol/…/Tailnet.kt`, `connection/TailnetStatus.kt`).
- **App lock** `[implemented 2026-10-14; verified on an API 37 emulator with a screen-lock PIN (lock on open and on return, PIN unlock, cancel, turn-off confirmation, private recents, no-screen-lock fallback); fingerprint/face, Android 9–12 and physical devices not yet verified]`: user intent is "someone who finds the phone must not be able to use it to cause trouble; ask every time the app opens". The app is locked on every cold start and every time it comes back to the foreground (ProcessLifecycleOwner ON_STOP, which already ignores rotations). Unlocking uses the system prompt only (`BiometricPrompt`, strong biometrics or the screen lock PIN/pattern/password; weak biometrics or the screen lock on Android 9–10); Nekko never sees or stores a credential. While locked: a full-screen lock screen covers the app, the content underneath is hidden from accessibility and gets no touches or focus, so nothing can be read, answered or approved; after a cold start the relay connection does not start until the first unlock. Deep links still route underneath and show after unlocking. The setting (*Settings → Security → App lock*, its own section file after Appearance) is on by default and stored on the phone in `PhonePrefs` (`app_lock`); turning it off requires the same authentication. Screenshots and screen recording of the app are never blocked (user decision 2026-10-16: chats must be screenshot-able; this replaced the earlier `FLAG_SECURE`, which also blocked them). While the lock is on, the recent-apps preview is kept private another way `[implemented 2026-10-16; verified on an API 37 emulator; Android 9–12 not verified]`: on API 33+ `setRecentsScreenshotEnabled(false)`, and on every API a plain privacy cover (the app's paper colour and lock mark, no content) replaces the content whenever the activity is paused or its window loses focus to something outside the app (`AppLock.covered`, drawn by `LockGate`; on API 37 opening the overview from inside the app does not pause the activity, so focus loss is the trigger there, and the app's own dialogs and menus are excluded on API 29+; below API 29 only a pause covers), so the overview shows the cover both when opened from inside the app (where `setRecentsScreenshotEnabled(false)` alone still showed the live window on API 37) and after leaving. Side effect: the notification shade or a system dialog over the app also shows the cover while the lock is on. The cover is never drawn while the app is in front, so in-app screenshots show the chat. Screenshot toolbar `[implemented 2026-10-18; JVM-tested; reported on a Samsung phone, fix not yet checked on one]`: on Samsung (One UI) the floating toolbar shown after a screenshot takes focus, so the cover replaced the chat until the user tapped it (user report 2026-10-18: "after a screenshot I get a lock I have to tap"). On API 34+ the activity registers `Activity.ScreenCaptureCallback` (`DETECT_SCREEN_CAPTURE`, install-time, no prompt) and calls `AppLock.onScreenshot()`; a focus loss starting within 2 s of a screenshot (either order) does not cover. A pause still covers (leaving from the toolbar keeps the overview private), and the next focus loss is judged on its own. Below API 34 the toolbar still shows the cover. The QR scanner and the system security settings are announced as short trips out (2 min) and do not lock on return. A phone with no screen lock cannot be locked: the app opens normally and Settings shows a warning with a link to the system security settings. Not a defense against a compromised/rooted phone, or against someone who knows the screen lock; revoking the phone on the computer remains the response to a lost phone. Limits to the computer side (what a paired phone may call) are a separate change.
- **New chat defaults on the phone** `[implemented 2026-10-14; verified on an API 37 emulator against two sandbox agents (default computer at start, phone model preselected over the computer's default, missing model falls back with a notice, forgetting a computer clears its defaults); not yet on a physical device]`: user intent is "default computer and model for new chats", chosen on the phone. *Settings → New chats* has **Computer** (the paired computer the app connects to when it starts; default *The one used last*, the previous behaviour; only offered with two or more computers) and **Model on <active computer>** (a model from that computer's providers; default *Same as the computer's default*). Both are stored on the phone in `PhonePrefs` (`newChat.computer`, `newChat.models`, one model per computer, keyed by the phone's computer id); nothing is written to the computer, whose own default model is unchanged. New chat opens on the phone's model for the active computer when that computer still offers it, else on the computer's default, else its latest chat's model, as before. When the phone's model is no longer offered (provider off, model removed), and only once every provider has answered, New chat says so and uses the computer's default; Settings shows the same note. Forgetting a computer drops its phone defaults. A share into Nekko (Share to Nekko) uses the same defaults.
- **Share to Nekko** `[implemented 2026-10-14; verified on an API 37 emulator against a sandbox agent (share sheet entry, lock first, editable text on New chat, text in the new chat's composer and not sent, Back/remove/blank/cold start/rotation); not yet on a physical device]`: user intent is "send text or a link from another app to open a new chat". Nekko Agent appears in Android's share sheet for `text/plain` (`ACTION_SEND`); browsers' page title (subject) is kept above the link unless the text already contains it. Choosing it opens **New chat** on the active computer with a *Shared with Nekko* card: the text is editable there and can be removed. After *Start on …* the text is in the new chat's message box and the user presses Send; **Nekko never sends shared text by itself**. The app lock applies first (a share while locked shows the lock, then New chat). Shared text is held in memory only (never written to disk, gone if the process dies before the chat starts), Back or removing it drops it, a newer share replaces an unused one. Limits: text only (files and images are not accepted, so no URI read permission is involved; attachments are AN-8), cut at 20,000 characters with a visible note, control characters removed; the computer and model come from the existing New chat defaults (A5 will add phone-side defaults).
- **Vibration on agent events** `[implemented 2026-10-15; verified on an API 37 emulator against a sandbox agent through the system vibrator log (approval pattern, preview, finished on/off, silent, Do Not Disturb, background); not felt on a physical device]`: user intent is "vibrate on events, for example when the agent asks something". *Settings → Vibration* has one switch per `PhoneEvent`: **Needs your approval** (on by default, two firm pulses), **Asks you a question** (on, one long pulse), **Reply finished** (off, one short tap), **Reply failed** (off, three short taps); switching one on plays its pattern once. It vibrates only while the app is in the foreground (`ProcessLifecycleOwner` STARTED) for the active computer's agent events, never in silent mode or Do Not Disturb, and with notification usage so the system's own vibration setting also applies. In the background the planned push notifications own sound and vibration (AN-6), so an event never buzzes twice. A sub-agent's chat finishing or failing does not buzz; its approvals and questions do. At most one vibration per 1.5 s. Adds the install-time `VIBRATE` permission (no prompt). Stored on the phone in `PhonePrefs` (`haptics.*`).
- **Full chat history, grouped like the desktop sidebar** `[implemented 2026-10-16; verified on an API 37 emulator against a sandbox headless agent with seeded folders and chats (groups, Show/Hide completed, open completed chat, Restore and long-press Complete read back from the computer's session files, a chat completed on the computer appearing after returning to the app), light and dark; not yet on a physical device or against the desktop daemon]`: user intent is "the phone shows every chat, the completed ones too, grouped exactly like the desktop: General, then one section per loaded folder, each with its active agents and Show completed; truly in sync, the whole history and not only the active chats". The list reads every top-level chat from `sessions:summaries` (sub-agents, task and training-run chats stay hidden, as before) and splits it with `ChatGroup.of` (apps/android protocol, mirroring `WorkspacesView.tsx` and `completedChats.ts`): **General** for chats with no folder or a folder the computer no longer lists (shown only when it has chats), then one group per `workspace:list` folder in the computer's order, shown even when empty ("No active agents"). Active chats sort by the desktop's manual drag `order` first, then most recent; completed ones (`archivedAt` set) by completion time, newest first, under a per-group **Show completed (N)** / **Hide completed** toggle. Tapping a group header folds it (count badge when folded); fold and show-completed state survive navigating into a chat. Completed rows are struck through behind a check and dated by completion. Opening a completed chat shows its transcript with a **Restore** bar instead of the message box; a long-press on a completed row offers Restore or Delete (Delete confirms unless the computer skips confirmation). Restore is `session:setOptions` with `archivedAt: null`, already allowed to phones by `PHONE_SESSION_OPTION_KEYS`; Complete now keeps the chat in the list under Completed instead of dropping it. **Sync:** the list is re-read on connect, pull-to-refresh, after every turn's `done`/`session_meta`, and now also when the app returns to the foreground. Limits: the computer sends no event when a chat is completed, restored or re-filed on the desktop while the phone is open in the foreground and idle, so that change appears at the next refresh trigger, not instantly; the phone cannot drag chats between groups or reorder them; the desktop's 60-day purge of completed chats applies unchanged.
- **The computer's settings from the phone** `[implemented 2026-10-15; verified on an API 37 emulator against a sandbox agent running the #529 phone policy (each change read back from the computer's settings.json, provider keys untouched; complete and delete on the computer's session files; offline state); not yet on a physical device or against the desktop daemon]`: user intent is "set the PC's default chat mode, the chat action and delete confirmation from the phone", with YOLO allowed. *Settings → On <computer>* shows and changes three of the computer's own settings (the same ones as in its Settings, not copies): **Chat mode for new chats** (Ask / Guardrails / YOLO), **Long-press a chat to** (Complete, the desktop's archive, or Delete), and **Confirm before deleting**. Each change is one `settings:update` with only that key; the screen shows the computer's reply, so it reflects what was saved there. **YOLO is allowed from a phone** by the owner's decision, already enforced on the computer since #529 (`PHONE_CHAT_MODES` in packages/shared/src/phone-access.ts and `chat_modes` in crates/nekko-remote/src/phone.rs, both tested); the phone asks once ("Use YOLO for new chats?") before switching to it. Nothing is shown until the computer has answered, so its values are never guessed (offline: a line saying so). In the chat list, a long-press offers the computer's action for that chat: Complete sets `archivedAt` (`session:setOptions`, nothing is deleted), Delete calls `session:delete`, after a "Delete this chat?" confirmation unless the computer is set not to ask. A protocol test checks every channel, setting key and chat mode the phone uses against the computer's phone policy file, so a phone feature the computer would refuse fails the build.
- **Confirming changes with the fingerprint or screen lock** `[implemented 2026-10-26 (AN-32); JVM tests against the computer's Change proof vector and a software key; verified on an API 37 emulator with a PIN against a sandbox relay, headless agent and nekkod (raise to YOLO: prompt, PIN, saved on the computer; cancel: nothing changed; a raise within 5 minutes: no second prompt); not yet on a physical device, with a fingerprint, or StrongBox]`: user intent is "the Android app does what the iPhone does": a Change on the computer (raising a chat mode now; editing files, Git, terminals and provider keys as those screens arrive) needs the owner at the phone, not just the app open. The phone keeps a P-256 key in the Android Keystore (StrongBox where the phone has one) that only signs within 5 minutes of the fingerprint, face or screen lock; the app asks itself, so one check covers 5 minutes and a recent unlock of the phone doesn't count, as on the iPhone. The key never leaves the Keystore and is not lost when a finger is enrolled; the computer learns its public half over `device:registerKey` on the first Change of each connection (trust on first use) and checks every proof (`nekko-change-v1`, 5 minutes old at most, never twice). **Raising the default chat mode** (Settings → On <computer> → Guardrails or YOLO) is sent plain; when the computer answers `proof-required` it is sent again signed, and with the computer's step-up (security key or code) beside the proof when it asks for one. Lowering it never asks. Cancelling the prompt changes nothing ("Not confirmed, so nothing changed on your computer."); a phone without a screen lock is told to set one. Forgetting the last computer deletes the key; the next pairing makes a new one. Before this, Android said "Switching to Guardrails or YOLO needs a confirmation this phone can't give yet".
- **Git on a chat's folder** `[implemented 2026-10-27 (AN-30, first half); JVM tests against the computer's phone-git golden; verified on an API 37 emulator against nekkod and a scratch repository (stage with the PIN prompt, a second stage within 5 minutes without one, Write message, commit, push publishing a new branch, history and a commit's files, switch and create a branch, compare, a merge conflict and Abort merge), phone width and an unfolded 841 dp window; not yet on a physical phone]`: user intent is the iPhone's *More → Git* on Android. **⋮ → Git** in a chat opens a full-screen Git view with its own back stack (so it works the same over an open folding phone's two panes, where its content stays at most 720 dp wide): the branch (or *detached at*), how far it is ahead or behind, its worktree, **Push** and, while a merge stopped on a conflict, **Abort merge** (confirmed first); staged and unstaged files with their status letter and line counts, each opening its diff drawn like the Changes sheet, **Stage** / **Unstage** per file and for all; a commit box with **Write message** (the computer's model, its tokens; a note when the diff was cut for it) and **Commit**; **History** fifty commits at a time with each commit's message and files; **Branches** on the computer and on the remote only, tap to switch (confirmed), **+** to create and switch; **Compare** two branches' commits and files. A phone names the chat, never a folder; a secret-looking file is listed with an eye-off mark and never shown; every change is signed (AN-32) and git's own words say how it went. A chat isolated in a worktree has no folder until its first turn makes one, and Git says so.
- **Pull requests** `[implemented 2026-10-27 (AN-30, second half); JVM tests against the computer's phone-git golden; verified on an API 37 emulator against nekkod with a loopback stand-in for GitHub's REST API (open a PR with the PIN prompt, the chat's chip and sheet, checks failing first, files and a file's diff, Approve then Merge within 5 minutes without a second prompt, the chip reading Merged, an *Ask the agent* prompt reaching the chat), phone width and an unfolded 841 dp window; not against real GitHub, not Close / Reopen on the emulator (same path, JVM-tested)]`: Git's **Open a pull request** takes a title, a description, a base branch (the repository's default when empty) and Draft, opened from the chat's branch (which must already be on GitHub); then *Open on GitHub*. A chat that opened pull requests shows a chip above the message box (`#7 Open · checks failing`, coloured by state and checks; read when the chat opens, after each turn, and when Git or its sheet closes). The chip's sheet lists them with their line and file counts and review decision, *Open on GitHub*, **Checks, files and actions** (the checks failing first, each opening its run; the files with their diffs; **Approve**, **Merge**, **Close** for an open one, **Reopen** for a closed one, each confirmed and signed, GitHub's own rules still applying), **Git: status, commit, push**, and **Ask the agent**: *Commit these changes*, *Open a PR* when none is open, *Fix the failing checks* when one fails, sent to the chat as prompts so its approvals apply.
- **Terminals and SSH in a chat** `[implemented 2026-10-27 (AN-31); JVM tests (the iPhone's VT screen, wire and session cases, the computer's phone-terminal golden and phone-access limits); verified on an API 37 emulator against nekkod with a scratch HOME and ~/.ssh/config (new terminal with the PIN prompt, commands with colours, ^C and history, reattaching without a second prompt within 5 minutes, the size following the screen, unfolding and folding again with the terminal open, Close, an SSH session that exits 255 with ssh's own message); not yet on a physical phone or with a reachable SSH host]`: user intent is the iPhone's *More → Terminals* on Android. **⋮ → Terminals** opens a full-screen list: the chat's terminals (a phone mark when a phone is attached) and the agent's command log, **New terminal** (in the chat's folder, the computer's shell), and the SSH hosts from the computer's `~/.ssh/config` (alias and where it goes, never the user). Opening a terminal is a signed Change (the fingerprint, face or screen lock once per 5 minutes) that hands the phone a token for typing; typing and resizing carry it, in order, and an expired token opens the terminal again once. The terminal screen draws the output with ANSI colours, bold, underline and the cursor (the iPhone's VT parser, by code point), with a key row (esc, tab, a Ctrl toggle that sends the next key as Ctrl+key, ^C, arrows, backspace, return, paste with bracketed paste when the program asks) and a command line for typing or dictating a whole line. Its columns and rows follow the space it has; leaving restores the size the desktop had; the agent's log is only read. **Read again** re-reads the tail; **Close terminal** (confirmed) stops it on the computer. Git and the Terminals open over a chat live by chat id in the app, not the screen, so opening or folding a folding phone keeps them open and the terminal attached.
- **The queue, fork, saved prompts and search** `[implemented 2026-10-27 (AN-29, chat half); JVM tests with the iPhone's BeyondTests data; verified on an API 37 emulator against nekkod (a saved prompt from `/` armed as a chip and sent as its text then the typed words; two prompts queued during a long reply, one edited and one removed, the computer's queue matching; *Edit in a new chat* forking before the prompt with it in the new chat's box; search across chats); the saved prompts under **+** added after that run, build-checked only; not yet on a physical phone]`: user intent is the iPhone's IO-22 to IO-25 on Android. **Queue:** prompts sent while a reply runs show under the message box, each with **Edit** (not a skill's, whose text is its instructions) and ✕ to remove it; an edit lands only while that prompt still reads what the phone showed (`chat:editQueued` with `expect`), is refused while offline, and the queue is read again either way. **Fork:** a long press on a saved message offers Copy and, on a prompt, **Edit in a new chat** (the chat up to it, the prompt waiting in the new chat's box) or, on a reply, **Fork from here** (everything up to the next prompt); a reply still streaming offers Copy only. **Saved prompts** (the computer's `prompts`) show in `/` above its skills and under **+**; picked alone one becomes a chip and sends its text then what is typed; picked after words its text replaces the `/query`; `/name rest` typed in full works too. **Search chats** at the top of the list matches every word, any case or accent, in a chat's title, first prompt or last reply, completed chats included.
- **Automations and usage and limits** `[implemented 2026-10-27 (AN-29, second half); JVM tests with the iPhone's BeyondTests data; verified on an API 37 emulator against nekkod (the stack's nightly task listed with its cadence, Run now marked Started and its result read back, the screen at phone width and unfolded); usage read from the computer but the fake model reports no tokens and its provider no limits, so the limit bars and per-model rows are covered by the tests only; not yet on a physical phone]`: user intent is the iPhone's IO-26 and IO-29 on Android. **Settings → On <computer> → Automations** lists the computer's tasks (with their cadence: *Once*, *Every day*, *Until it's done*) and workflows (category, steps, Off), how each last went and when, and **Run now** (refused while offline, never sent later; the list is read again a few times so the run's result shows). A banner says when automations are paused on the computer. Making, changing, pausing or deleting them stays on the computer. **Usage and limits** shows each enabled provider's plan windows (a bar coloured at 80 % and when rate limited, when it resets), then all-time tokens and estimated spend, recent days and tokens by model (*plan* for a subscription). Limits are asked by provider id; the phone never holds a key.
- **Files in a chat's or saved folder** `[implemented 2026-10-27 (AN-33); JVM tests against the computer's phone-files golden and with the iPhone's FilesModelTests cases; verified on an API 37 emulator against nekkod (a saved folder added by path with the PIN prompt and removed again with its files left on disk, a folder listed with a file that may hold secrets counted, search, Markdown formatted, a PNG, line-numbered code, a save checked on the computer, *Changed on the computer* after an edit there and Save over it, an unsaved edit kept across unfolding and folding); not yet on a physical phone]`: user intent is the iPhone's IO-33 FA-1 on Android. **⋮ → Files** in a chat opens its folder (its worktree when isolated) and **Settings → Files** the computer's saved folders: add one by its absolute path on the computer, touch and hold one to remove it (never deleting files). Tap through folders or search by file name; a file opens with line numbers (Markdown formatted or not, images as pictures, at most 5000 lines, a note when cut short or read only). **Edit** a whole text file up to 256 KB and **Save** over the version read (its hash): a signed Change, so the fingerprint, face or screen lock is asked once per 5 minutes. When the file changed on the computer meanwhile, *Changed on the computer* offers **Reload, losing my edits**, **Save over it** (not when the file is gone) or **Keep editing**. The pages live in the repository, so folding the phone keeps them and the draft. A phone names a chat or a saved folder by id, never a path.
- **The computer's logs** `[implemented 2026-10-27 (AN-34); JVM tests against the computer's phone-files golden and its log-redact cases, the same cases again on the device (Android's regex is ICU, not the JVM's); verified on an API 37 emulator against nekkod (the desktop app's and the engine's logs listed, the engine's tail opened at its newest lines with a key already redacted by the computer, a search showing line numbers, Share sending the matching lines with the header); not yet on a physical phone]`: user intent is the iPhone's IO-33 FA-5 on Android. **Settings → Logs** lists the desktop app's log, the engine's and each chat's agent run log (size, when last written, or *Empty*). A log opens at its newest lines (the last 64 KB, a note when older lines stay on the computer); **Refresh** reads it again; *Find in this log* shows the matching lines with their numbers. **Share** sends what the screen shows as plain text with a header, redacted again on the phone with the computer's rules (`LogShare`), so a log from an older computer still doesn't leak a key. Read only.
- **Files and pages the agent linked** `[implemented 2026-10-27 (AN-35); JVM tests (the iPhone's ChatLinksTests, PreviewsTests and PreviewLoaderTests cases, and the computer's phone-artifacts golden: requests it accepts, views decoded, and no card for a file it would refuse); verified on an API 37 emulator against nekkod with a fake model reply and a local server (cards with pictures of a prototype and a dev server page, the prototype opened from its link with its CSS, script and image and its outside request blocked, a web link opening the browser, the window kept across unfolding, Markdown, CSV from a file: URL, a PDF, an image, a second page on the dev server, and a stopped server said plainly); not yet on a physical phone]`: user intent is the iPhone's #1095 on Android (decision 0025). Under a finished reply, a card for each file it links (HTML, SVG, images, Markdown, text, JSON, CSV, PDF, as an absolute path or `file:` URL) and each loopback page (`http://localhost:<port>`): a picture of the page or image (drawn once in the isolated web view at 390 dp, then kept), else the extension; title from the link or the file or folder name. Tapping a card or the link opens the preview window full screen: a page runs interactive, a picture pinches to zoom, Markdown is formatted, text is monospaced, a PDF shows up to 50 pages; **Reload**, **⋮ → Copy path / Copy address** and **Share**. Reads go through `artifact:read` and `preview:fetch` only, cached per chat (32 MB) with two thumbnails at a time. The web view has no JavaScript bridge, file or content access, cookies or new windows; every request is answered by the app on `https://artifact.nekko.invalid/<path>` (relative assets resolve beside the page) or `https://preview.nekko.invalid/…` for the one linked origin, anything else gets an empty 403, and every answer carries a Content-Security-Policy keeping the page's own connections on those hosts. A tapped web link in a page opens the browser. Computer recordings are 16 kHz mono 16-bit PCM WAV, in memory only, **capped at 30 s** with a visible clock and an automatic stop: the computer accepts 60 s, but the WAV travels as a JSON number array, sealed and base64'd (~150 KB/s), so 60 s (~9.1 MB) would sit at the relay's 10 MB frame limit; 30 s is ~4.6 MB. Recordings under 0.25 s are not sent; Whisper's non-speech tags (`[BLANK_AUDIO]`, `[Music]`, `(wind blowing)`) are dropped, and nothing heard says so instead of inserting them. The microphone permission is asked on the first tap; refusing it explains where to allow it. The phone's dictation setting is separate from the computer's `voice.enabled` (which means "Whisper installed and on there"); the phone only reads that, to decide and to say why. The computer uses the language set in its own Nekko Voice settings; the phone recognizer's language is set on the phone.
- **Plain `ws://` to the tailnet and the LAN, as on the iPhone** `[implemented 2026-10-31; JVM tests (RelayHintTest, OkHttpTransportTest, RouteSupervisorTest, NearbyComputerTest); verified on an API 37 emulator: pair, stream, deny and answer against a relay at the Mac's LAN IP (ws://10.0.0.55, no adb reverse), Connection status "Local network"; a ws://relay.example.com link shows the refusal on the pairing card and the chat list; aapt2 dump of the compiled config in the release and debug APKs; not yet on a physical phone over a real tailnet]`: user intent is "use the phone on 5G with the free private relay on my Mac", and at home over the LAN. The rule is the iPhone's (`RelayRoute.swift`, and the desktop's `relay-route.ts`): `wss://` anywhere; plain `ws://` to Tailscale (`*.ts.net`, `100.64.0.0/10`, `fd7a:115c:a1e0::/48`) and to the LAN (RFC 1918, link-local, `.local`, IPv6 ULA and link-local); never to the open internet. A loopback relay is the phone itself, so it is refused on release builds and allowed on debug builds for `adb reverse`. **Security boundary:** Android's network security config can't name IP ranges, so it permits cleartext app-wide (debug and release share one file) and the app is the barrier: `RelayRoute.publicCleartext` refuses public `ws://` in the WebSocket transport (before anything is sent) and in the `/healthz` probe. Every frame is end-to-end encrypted on every path; the rule keeps metadata off the open internet. The trade-off, chosen by the owner on 2026-10-31, is that the system no longer stops a future code path that skips the rule ([decision 0034](../../docs/decisions/0034-android-permits-cleartext-and-refuses-public-ws-in-the-app.md)). A relay the phone won't use (loopback on a release build, public `ws://`) is reported on the pairing confirmation and in the chat list's connection line (`RelayHint`), instead of an endless "Connecting…". Before 2026-10-31 Android allowed plain `ws://` only to `*.ts.net` names.
- **Large chats on the phone** `[implemented 2026-10-16; verified end to end on an API 37 emulator against a sandbox agent with a synthetic 10 MB chat (13.3 MB sealed); not yet on a physical device or against the desktop daemon]`: found on the first real-phone test, where a long agent chat (9.8 MB, 1,677 messages, 7.6 MB of it screenshots inside tool results) spun for two minutes and then showed `session:get: timed out`. Sealed, the whole session was over the relay's 10 MB frame, which the relay drops without a word. A phone now receives a **phone-sized view** of `session:get` (`PHONE_SESSION_VIEW` in packages/shared/src/phone-access.ts, applied in `redactPhoneResult` and its Rust twin in crates/nekko-remote/src/phone.rs, held equal by the golden replay): the newest 300 messages, with `omittedMessages` counting the rest; tool results without their images (`omittedImages`); tool output and long string tool arguments cut to 4,000 characters, with `truncated` and the original length. The computer's copy is untouched, and the full detail stays on the computer. The phone says so: "N earlier messages are on the computer." at the top of the chat, and "… (N more characters, on the computer)" / "N images, on the computer" under a tool's output. As a backstop, a reply that still seals above 9 MB (`PHONE_MAX_FRAME_BYTES`) is answered with an error the phone shows at once ("This reply is too large to send to a phone (X MB). Open it on the computer.") instead of silence; same in relay.ts and agent.rs. Older messages beyond the newest 300 cannot be loaded on the phone yet (planned: paging).
- **Route failover** `[implemented 2026-10-30 (AN-28); JVM tests (the iPhone's RouteSupervisorTests and failover cases, the shared relay-route golden); verified on an API 37 emulator against nekkod with the test stack's route proxy taken down and up; LAN routes dialed since 2026-10-31 (see below); not yet on a physical phone moving between networks]`: user intent is the iPhone's IO-20 on Android: a computer reachable at more than one address of its relay keeps working when one goes away. The pairing link's `alt` routes are kept with the computer (replaced when it is paired again). The phone dials the best route it may use (its own network, then the tailnet, then the internet; a LAN address only on Wi-Fi or Ethernet), leaves a route at once when it doesn't open (4 s while there is a fallback), drops or sends no handshake, and keeps that route out for 60 s. While on a worse route it asks the better one's `/healthz` every 10 s (nothing about the room or the phone is sent) and moves back after 3 good answers in a row and 30 s on the current route, never while a request is in flight, so a running turn is not cut. "Computer offline" is the relay answering, not a failed route. A network change starts again from the best route. *Settings → Connection status* shows the route in use, its relay and the other routes, and the chat list's banner names the relay in use. **LAN routes:** dialed and probed like the iPhone's since 2026-10-31 (the plain `ws://` rule above); only a public `ws://` route is kept but never dialed, listed as "not used on Android". No background grace like the iPhone's yet.
- **Relay security boundary:** every payload is E2E-sealed (PBKDF2-SHA256 100k → AES-256-GCM, salt `nekko-relay:<room>`), the relay sees only ciphertext, and the HELLO handshake is enforced by the computer's device registry (unknown devices denied, revoked devices kicked, spent codes refused). Pairing material (room, secret, derived key, device id) is encrypted at rest under a non-exportable Android Keystore AES-GCM key and excluded from backups and device transfer. Provider records and settings are reduced to ids, labels and the default model the moment they arrive: API keys never reach app state, storage or logs. Plain `ws://` only to the tailnet or the LAN, refused by the app toward the open internet (see above).

- **Background connection and local notifications** `[implemented 2026-10-14; verified on an API 37 emulator against a local relay and headless agent: reconnect after airplane mode, keep-alive service while a run streams with the app in the background, finished/failed notifications with and without the app lock, opening a chat through the lock; not verified on Android 9–13, physical devices, OEM battery managers, Wi-Fi↔cellular handover on real radios, or approval/question notifications live]`: user intent is "the phone stays in touch with a running chat when I put it in my pocket, and tells me when it's done or needs me". **Reconnect:** a `ConnectivityManager` default-network callback (`connection/NetworkChanges.kt`, JVM-tested) restarts the relay socket as soon as the phone moves to another network or a network comes back after none; `RelayClient.reconnect()` drops the old socket, fails in-flight calls and dials at once (no-op once closed or denied); the backoff otherwise stays as it was. Measured on the emulator with 40 s of airplane mode: back online after 21.5 s and 26.6 s before, 4.4–4.7 s after (see docs/perf-history.md). **Keep-alive:** *Settings → Connection → Stay connected while a chat runs* (`PhonePrefs` `keep_connected`, on by default) runs `KeepAliveService`, a foreground service of type `remoteMessaging` (no runtime permission and no daily cap, unlike `dataSync`, which Android 15 limits to 6 h a day), only while a chat on the active computer is running or waiting on the user, the relay is online or reconnecting, and an event arrived in the last 30 minutes (`connection/KeepAlive.kt`, JVM-tested). It is started when the app leaves the foreground (the moment Android allows it) and stops itself when the run ends; its notification is silent, low-importance and reads "Staying connected · N chat(s) running on <computer>". On Android 16+ that notification asks to be a **Live Update** `[2026-10-17; unit-tested; not yet seen on a device]` (`setRequestPromotedOngoing`, `POST_PROMOTED_NOTIFICATIONS`, a normal permission): a "Running" / "N running" chip in the status bar and a place at the top of the lock screen, the counterpart of the iPhone's Live Activity. Counts only, never chat content; the user can turn Live Updates off for the app, and older Android shows the same ordinary ongoing notification. It holds no connection of its own and is not sticky. `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is deliberately not used (Play restricts it); when the app is *Restricted* in battery settings, Settings warns and opens the app's system page. **Notifications:** *Notify me* (`notify_events`, on by default; `[updated 2026-10-31]` now one switch per kind, see *Notification controls*; POST_NOTIFICATIONS is requested from Settings on Android 13+, never at launch) posts a local notification for `PhoneEvent`s (reply ready, reply failed, question waiting, approval needed) only while the app is out of sight and only for chats the phone lists. Two channels, *Approvals and questions* (high) and *Replies* (default), plus *Connection* for the keep-alive. Text never carries the reply, command or question: only the event, the chat title and the computer; with the app lock on, not even the title ("Open Nekko to see it."), and visibility is PRIVATE on the lock screen. One notification per chat (tag `chat:<sessionId>`), replaced by newer events and cleared when the chat is opened; push (AN-6) must reuse the same tag so a push and a local notice never show twice. Tapping opens the chat through `nekko-agent://chat/<id>`, so it passes the app lock. An approval notification also has **Deny** `[2026-10-17; unit-tested; not yet tapped on a device]`, which answers that tool call with `tool:approve(…, false)` over the live connection without opening the app (`DenyReceiver`, not exported, 8 s limit; the notification is cleared once the computer has the answer, and stays if the phone is offline). Deny skips the app lock because nothing runs. There is deliberately no Allow on Android's notification: its text never shows the command, so approving stays in the chat where the exact input is on screen (the iPhone's Allow shows the tool's label and asks for Face ID). Without push these only arrive while Android keeps the app alive. Found on the way: both loops report a stop between steps as `error "Aborted"` (not only `"Stopped"`), so `PhoneEvent` now treats both as a user stop, not a failure.

- **Settings layout** `[implemented 2026-10-14; checked on a headless emulator, light and dark]`: the phone's Settings screen is an ordered list of sections, one file each in `ui/settings/` (Appearance, Security, Computers, About), so later phone settings each add a section instead of editing one screen. *Computers* opens the existing paired-computers screen; *About* shows the installed version (read from the package) and the open-source licenses: the app's MIT license and the Apache 2.0 text bundled with the app, and the Google Play services / ML Kit terms for the code scanner, which is not open source. The list of libraries is kept by hand from the release runtime classpath (no license-plugin dependency). No new functional setting is in this change. Groundwork for later settings, not visible yet: `PhonePrefs`, a store for the phone's non-secret settings (a `StateFlow` per key, its own preferences file `nekko_phone`, excluded from backup and device transfer like everything else in the app; the appearance choice stays where it was, in `ThemePrefs`), and `PhoneEvent` (finished, failed, needs input, approval), a pure mapping from the agent events the chat already receives, not yet wired to any notification or vibration. A stopped turn (`error` "Stopped") is not a failure.

- **Markdown in replies** `[implemented 2026-10-17; parser unit-tested; not yet inspected on a device]`: AN-8's first half. Replies render the same subset as the iPhone app (`Markdown.parse` in the protocol module mirrors `MarkdownText.parse`): fenced code blocks that scroll sideways with a monospace face and a **Copy code** button (48 dp), headings (announced as headings to TalkBack), bullet, task and numbered lists, quotes, rules, and inline bold, italic, code and links. - **Photos in a prompt, from the message box's + menu** `[implemented 2026-10-17; JVM tests (PhotoTray limits, scaling, chat:send and chat:queue payloads, the phone allowlist) pass; verified on an API 37 emulator against an isolated sandbox headless agent (TS relay agent, fake model): + menu light/dark, a gallery photo through the system photo picker, a shot from the emulator's virtual camera, thumbnails, a sent turn saved on the computer with both JPEGs (a 1280×820 photo kept at its size), "2 images" on the bubble, the camera's cache file deleted after reading, Dictate from the menu; not yet on a physical device, a real vision model or the desktop daemon edition]`: AN-8's attachments, as on the iPhone app. User intent (2026-10-17): "Android has only Send and a microphone; the structure should be Send and a **+** that holds audio, an image from files, and take a photo". Photos are held by the chat's view model until the prompt goes, so a rotation keeps them. `[updated 2026-10-30, offline drafts]` They are also kept in the chat's saved draft, as the already-scaled JPEGs the computer would receive (see *Offline: drafts and prompt ids*); before that they were never written to disk apart from the camera's transient file. The sent bubble shows the photos `[implemented 2026-10-18; TS/Rust/Android unit- and golden-tested, the bubble rendered on an API 37 emulator in light/dark; not yet checked end to end on a physical phone or against the daemon edition]` (user report 2026-10-18: "photos I upload from the phone show in the computer's chat but not in the phone's"; until then the phone showed only "N images"). In `session:get` a phone receives each user message's `images` as small thumbnails instead of the originals (`PHONE_SESSION_VIEW`: the newest 40 photos of the messages it gets, JPEG quality 70, long side 384 px, never enlarged, each data URL at most 96 KB, so at most about 4 MB per reply, under the 9 MB frame limit). The empty box's placeholder is one line ("Message, / for skills" when the computer has skills, ellipsized if needed), so the empty box is as tall as one with a line typed (2026-10-18: the longer "Message your computer, / for skills" wrapped to two lines on a phone; checked by `ComposerHeightTest` at 360 dp and 1.3× font scale on an API 37 emulator). - **On this network** `[2026-10-17; unit-tested; not yet run against a real network]`: Pair a computer has an *On this network* card. **Look on this network** browses `_nekko-agent._tcp` with the system's NSD service for 30 seconds (no multicast lock, no permission) and lists computers whose desktop has *Visible on this network* on: the name and, when the computer runs its own relay and Android would accept it (`wss://`, or `ws://` to the tailnet or the LAN), that relay's host. **Not in this version `[planned]`:** models running on the phone (previously available in the removed Expo app; on Android this needs a llama.cpp JNI/NDK bridge), push notifications (FCM token registration to the relay), files other than photos, and the public Google Play release (signing key, listing, Data safety form). **Host fix found by this work `[implemented, tested]`:** the relay agent sealed each outgoing frame independently with async WebCrypto, so a streamed reply could reach a phone out of order ("from your Hello computer."). Outgoing sealed frames now go through one ordered queue in `packages/host/src/relay.ts` (covered by `relay.test.ts`); this affects every relay client, including the native apps and the Local Web UI.
