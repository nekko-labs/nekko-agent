## Telling subscription accounts apart by email

`[implemented 2026-10-14; unit, golden and isolated renderer checks; live vendor sign-in unverified]` User intent: someone holding two plans on one vendor (for example a personal Claude Pro plan and a work one) sees two identical "Anthropic (Claude)" entries and cannot tell which account a model or a quota bar belongs to. Each signed-in provider now shows the email it is signed in as next to its name: `Anthropic (Claude) · davide@example.com`.

- **Where:** model picker (provider group headings, the provider tag on Recent/Starred/Default rows, and the chip's tooltip), the Agent board Utilization panel, and the sidebar Capacity list. Same for ChatGPT and any other sign-in that reports an email.
- **Source:** read once at sign-in from what the vendor already returns: Claude's token response `account.email_address`, ChatGPT's `id_token` `email` claim (the sign-in already asks for the `email` scope), and the Codex CLI import's `id_token`. Kept across token refreshes unless the vendor reports a new one. No extra request to the vendor.
- **Privacy boundary:** the email lives only in the host's `tokens.json` (mode 0600) next to the token, reaches the window only through the sanitized sign-in status (never with the token), and is not written to provider settings, so it never enters a settings export. Display only; it is never used to authorize anything. Values that do not look like an email are dropped.
- **Not covered:** API-key providers and OpenRouter carry no email and keep the bare label. Plans signed in before this change show no email until signed in again. A user-chosen account name is not offered yet (decided 2026-10-14: email only for now).
- **Verification:** TS and Rust token parsing held equal by the OAuth golden set (Claude with and without a valid email, ChatGPT `id_token` email, refresh keeping or replacing it, status, Codex import); render tests for the picker and Utilization. Whether Anthropic's live token response still includes `account.email_address` has not been checked against a real sign-in.

## One gap between the Agents view's panels

`[implemented 2026-10-27; hidden renderer captures at 1280, 1600 and 2000px wide in Dynamic and Focused, Windows chrome]` User intent: on a wide Windows screen the wall composer cut into the bottom of the agent windows (their footers ran into its header strip), the agent panel's toolbar sat right under the "Agents" heading, and the space between panels varied (3, 6, 7, 16 and 26px).

- **One gap:** the agent panel, the wall's windows, the composer below them and the Monitors dock are `--wall-gap` (8px) apart, the same 8px the wall puts between its own windows. The add-zone rails along the wall's right and bottom edges are that gap (their plus buttons overhang it), so a dock on the right adds no second gap, and a zoned board clips instead of scrolling so no scrollbar gutter widens it.
- **Composer:** windows always stop one gap above a composer docked below them, with or without rails; the composer's resize handle lives in that gap and never covers a window's footer.
- **Agent panel:** a vertical agent panel spans exactly the wall's windows: its top lines up with the top of their panels (below a zone's name bar) and its bottom with their bottom, in Dynamic and Focused, at every window size. The Agents view measures those offsets from the wall, so the composer's height and the rails are accounted for.
- **Not covered:** a horizontal agent panel above the wall, and a composer docked above the windows (it keeps the wall's 14px top inset). At widths where the wall stacks its windows and scrolls, the panel ends at the composer's gap rather than at the last window.
