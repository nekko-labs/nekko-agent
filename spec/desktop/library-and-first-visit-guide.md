# Library and its first-visit guide

## Intent

The rail destination formerly called Artifacts is **Library**. Someone opening it for the first time should understand what appears there without knowing the term artifact. This completes the introduction requested in issue #1272 and applies the Library name to the rail, page title, command palette and voice navigation.

## Implemented

- Library keeps the existing `artifacts` route, file index and preview behavior. Files are not moved or copied by this rename. Chat artifact cards, the Agent Monitor's Artifacts disclosure, and the separate Nekko Artifacts publishing server keep their existing names.
- The first visit opens an illustrated, static guide in both Simple and Detailed output modes. Three short explanations cover creating files in a chat, finding and previewing them, returning to the source chat, and keeping or sharing a file through its usual app. A sample request ends the guide with something to try.
- **Explore Library**, the close control, Escape and the scrim dismiss the guide. Dismissal is saved in this renderer profile's local storage; returning to Library or reloading does not reopen it. **Library guide** always reopens it. Clearing browser/app profile storage resets the first-visit state. If storage is blocked the guide still closes, but dismissal cannot survive remounting.
- On narrow shared-web/desktop windows the list uses the available width. Selecting a file switches to its preview, with the back button returning to the list. Wide windows retain the list and preview side by side.
- The existing index reads up to the 60 most recent eligible top-level chats. It is not a scan of every file on the computer or a backup. A file a chat named that is no longer on disk drops out once its folder has been listed (see [below](#designs-first-real-previews-and-a-design-you-can-click-2026-11-13-2723)).

## Designs from every agent, and the designs folder

Requested 2026-11-12 (#2677): designs made in Claude Code chats were missing from Library; design canvases should show whoever made them, and agents should be able to find and use them. Checked against 299 saved chats on one Mac: Claude Code chats record the files they write as `Write` with a `file_path` (33 calls in 39 chats, two of them HTML designs) and name them in code formatting, so neither half of the index saw them. (#2675 has since made a page, image or PDF named in code formatting count as a link, which lists those; a design the reply never names, and every other kind of file, still depends on the `Write` call.)

Implemented, not yet released:

- **Files Claude Code wrote.** A `Write` call in a Claude Code chat counts as a written file, the same as Nekko's own `write_file`, with the same rules for what is an output (no source folders, no project housekeeping files). Reading or editing a file does not list it. An agent's own notes under `.claude/` (Claude Code's memory and plans) are never listed.
- **Designs by name.** An HTML page or image is filed under **Designs** when its own file name says so: `design`, `mockup` (or `mock-up`, `mock`), `prototype`, `wireframe`, `concept`, `canvas`, `artboard` or their plurals, as a whole word (`checkout-design.html`, `pricing_wireframe.png`, `prototype.html`). The folder rule is unchanged: anything under `nekko-designs/`, `design(s)/`, `mockup(s)/` or `prototype(s)/`. Other kinds keep their kind (`ci-runners-design.md` stays a document).
- **The designs folder.** Library also lists the pages and images in each saved project's `nekko-designs/` folder and one level of subfolders (`nekko-designs/login/index.html`), whoever put them there: an agent on any provider, the Design tab, a person, or a tool outside Nekko Agent. Up to 40 subfolders and 300 files per project are read. A design a chat also produced keeps its chat; one no chat mentions shows "<project> designs folder" where the chat title would be, has no date, sorts after the chat-made designs, and offers **Open file** as its main action, with no **Open chat**. The folder is listed again whenever a chat changes.
- **Agents know the folder.** The shared prompt tells Nekko's own agents what a design is, that it goes in the project's `nekko-designs/` folder and never in `reports/`, to look there before designing or building an interface, and to version a design as files. The rules, and how Claude Code chats are told, are in [Rich responses, reports, and design workspace](../code/rich-responses-reports-and-design-workspace.md#a-report-and-a-design-are-different-outputs-2026-11-13). See [decision 0089](../../docs/decisions/0089-designs-are-files-in-the-projects-designs-folder.md) and the options in [the report](../../reports/design-canvases-for-agents-2026-11-12.md).

Not done: on a Claude plan, Claude Code chats are not told by Nekko (the Claude policy's `context_note` row is off there), so they follow the project's `AGENTS.md` or `CLAUDE.md`; files Claude Code changes with `Edit` are not listed; a design in a chat's own worktree is found through its chat, not the folder listing. The Design board follows the same folder: see [the Design tab](../code/designing-draw-it-or-describe-it-design-tab.md#the-board-follows-the-designs-folder-2026-11-12-2680).

Verified in the hidden, isolated full-App Electron journey (`library-designs-sandbox.cjs`, 9 checks, matched captures on unchanged `main`) and focused unit tests. Packaged builds, Windows paths in a running app and the Local Web UI in other browsers were not checked.

## Browsing: kinds, groups and layouts

Requested 2026-11-09: a slider at the top for All and then each kind; collapsible groups under All; groups with their headings and the files as large square previews without a card box; the setup answer's group first (a Developer sees theirs first); previews of the newest files of each kind in the empty space beside the list; a layout slider of icons in the top right (list, small icons, large icons, full cards) with smooth transitions, keeping the list on the left in every layout except List, where the list sweeps across the full width.

Implemented, not yet released:

- **Kind slider.** A sliding segmented control at the top: **All**, then one segment per kind that has files, each with its count. The highlight slides between segments; arrow keys, Home and End move the choice (one tab stop). Picking a kind shows only that kind, in the list and the previews, with every file. If a kind's last file leaves (for example after hiding completed chats), the slider returns to All. The kind shown is not saved; Library opens on All.
- **Groups.** Under All every kind is a group with its heading and count. Clicking a heading folds or unfolds that group, in the list and the previews together, with a short height animation; folded content leaves the tab order. Every group starts expanded; the folded set is saved in this profile's local storage.
- **Designs, then the setup answer.** Designs always come first in the slider, the list and the previews (changed 2026-11-13, #2723). The kind matching the setup answer to "What do you mostly do?" comes next: Developer, Web pages; Writer or researcher and Student, Documents; Product or business, Office files (a Designer's kind is already first). Just exploring, no answer, or a lead kind with no files keeps the usual order after Designs (Documents, Web pages, Diagrams, Data, Office files, Images).
- **Layout slider.** An icon slider in the top right picks **List**, **Small icons**, **Large icons** (the default) or **Full cards**, saved in local storage. In the three preview layouts the list stays on the left and the space beside it shows each kind's newest files: 16 small icons, 8 large icons or 4 full cards per kind under All, with **See all N** switching the kind slider to that kind. Small and large icons are a square picture with the name under it and no card background or border; full cards add the source chat, date, **Open chat** and **Open file**. **List** spreads the list across the page with file name, source chat and date columns; picking a file there narrows the list back to the left for the preview, and closing the preview widens it again. The layout slider is hidden on narrow windows, where the list keeps the full width as before.
- **Previews.** An HTML page or an image shows as itself on its tile (changed 2026-11-13, #2723; see below). Markdown and plain-text documents show their first-page text; images use small cached still pictures (see below). Unsupported or unreadable files keep original line art drawn from their kind, with the extension in the corner. List rows use compact shared file-type symbols, tinted per kind, without reading files.
- **HTML pages run live.** Picking an `.html` design serves it with its folder so its own stylesheets, scripts and images load, offline unless **Load from internet** is switched on: see [HTML previews run with their folder](html-previews-run-with-their-folder.md).
- **Back to Library** (2026-11-14, #2754; replaced the close control on the right of wide windows and the narrow-only **Back to Library** button). Every open file has a back button, a left chevron and "Library", at the top left of its header on every window width. It, Escape (outside a text field, and not while a dialog or menu is open) and the mouse's back button return to the previews or the full-width list, keeping the kind, layout and folded groups. Verified in the hidden, isolated `library-layouts` journey (21 checks, including where the button sits and Escape) and the `library-intro`, `library-designs` and `design-canvas` journeys.
- **No files yet.** Requested 2026-11-09: keep the placeholder illustration for someone with no artifacts. Once every candidate chat has been read and none produced a file, the original Library illustration fills the page in every layout (including List and narrow windows) with "What your agents made", a line on how files arrive and a request to try. The kind and layout sliders hide, since there is nothing to sort. If **Include completed chats** is off, the placeholder offers to turn it on. While chats are still being read the usual list and right-hand illustration show, so the placeholder never flashes before older chats are checked. A filter that matches nothing still says "Nothing matches." in the list.
- **Motion.** Layout and kind changes run as view transitions (340 ms, ease-out): on-screen previews morph from their old place and size to the new one, labels and group headings glide without stretching, and items leaving or arriving fade quickly. When the list itself changes it plays as a panel sweeping to its new width rather than a crossfade. Only items on screen get transition names. With the OS reduced-motion setting, or a browser without view transitions, changes are instant; the slider highlight and folds also stop animating.

Verified in the hidden, isolated full-App Electron journey (`library-layouts-sandbox.cjs`, 16 checks) and the existing first-visit journey (18 checks), plus focused unit tests. Packaged builds, the Local Web UI in other browsers, and light-theme captures of the new layouts were not checked. Diagram files linked in a reply are not indexed by the existing artifact index (separate, unchanged behavior), so the Diagrams group appears only for diagrams the agent wrote.

## Designs open on a canvas, with their versions

Requested 2026-11-13 (#2696): treat a design as a canvas with controls, play and pause where the design moves, and versions.

Implemented, not yet released:

- **Versions are one design.** The numbered files of a design (`checkout-design.html`, `checkout-design-v2.html`, `-v3`; also `_v2`, `.v2` and ` v2`) are one Library entry, in the list and the previews. It stands for the newest version (highest number; a file with no number is version 1), is named without the number, keeps the newest version's chat, and says "3 versions". Only designs are grouped, and only files in the same folder. A design saved once is unchanged, whatever its name.
- **The canvas.** Picking an HTML design opens it on a dotted canvas in place of the file pane. The page is laid out at a desktop width (1440) and at its own full size, up to 8000 by 12000, so a row of screens is seen whole instead of through a narrow frame. It opens fitted to the width, never above 100%.
- **Moving and zooming.** Drag, or scroll, to move. Pinch, or Ctrl/Cmd+scroll, zooms at the pointer; **−** and **+** zoom in steps between 10% and 400%; the percentage is a button that fits the design again. A fitted design stays fitted when the window changes size, until it is moved.
- **Play and Pause** appear only when the design is moving: a CSS animation or transition, a Web Animation, a `requestAnimationFrame` loop, a video or a sound. Pause holds all of them where they are, and Play resumes them (media that was not playing stays stopped). A still design shows neither. Motion driven by timers alone is not detected or held.
- **Versions.** A design with more than one version shows a slider of them (v1, v2, v3); the newest is open first. The path under the title and **Open file** follow the version shown.
- **Always interactive** (changed 2026-11-13, #2723; this replaced an **Interact** switch). The design takes clicks and hover from the start. The canvas moves by dragging the space around the design, or by holding Space and dragging anywhere, over the design too; a quiet "Hold Space to drag over the design" sits by the controls on wide windows. Scrolling over the design moves the canvas and pinching or Ctrl/Cmd+scroll zooms it, unless the spot under the pointer is inside the design's own scrolling list or panel that can still scroll that way, which scrolls instead. Space in a field or on a button inside the design types or presses as usual. Why: [decision 0094](../../docs/decisions/0094-library-tiles-show-the-file-and-a-design-is-always-interactive.md).
- **Source** opens the file itself in the usual pane (source, viewport sizes, Load from internet, Add to design board); **Canvas** in the header returns. A design that is an image, and any design the host cannot serve (a page directly in a disk root or the home folder, a host with no preview server), opens in the file pane as before.

Boundaries: the design runs where every served page does, in a frame with an opaque origin, offline, with no app bridge ([HTML previews run with their folder](html-previews-run-with-their-folder.md)). For the canvas the server adds one small script to the page (`controls`), through which the canvas asks for the page's size and what is moving and tells it to pause or play, over `postMessage`. The script answers only the frame above it, and also passes up a scroll or pinch the page has no use for and whether Space is held. The canvas reads only numbers and flags, and only from its own frame: a scroll step is capped at 400 pixels and its pointer held inside the frame, so a hostile design can at most misreport its size, show a Play button that does nothing, nudge or zoom the view within its limits, or hold the canvas in drag mode until Space is pressed and let go in the app. Pages opened in the file pane do not get the script. Why this and not the alternatives: [decision 0091](../../docs/decisions/0091-the-design-canvas-controls-a-served-design-over-postmessage.md).

Verified in the hidden, isolated full-App Electron journey against the real preview server (`design-canvas-sandbox.cjs`, 24 checks, including the animation's and the frame loop's actual state inside the sandboxed frame) and focused unit tests. Not done or not checked: frame-by-frame stepping or a timeline; jumping to a named frame; the phone apps; the Design board, which still shows each version file as a card; packaged builds, Windows, the Local Web UI in other browsers, light theme, touch gestures on a real trackpad or screen.

## Smoother canvas, keyboard, and what can be clicked (2026-11-14, #2756)

Requested 2026-11-14: better design canvas controls, smoother and faster panning, highlight the interactive areas.

Implemented, not yet released:

- **Smoother moving.** Dragging, scrolling and pinching paint the design's new place straight onto it once per frame instead of re-rendering the canvas for every pointer event; the zoom figure and buttons catch up when the gesture pauses (120 ms). Measured: script time over a 120-move drag fell from about 113 ms to about 22 ms ([perf history](../../docs/perf-history.md)).
- **The dots move with the design.** The dotted surface pans with the design and its spacing follows the zoom, kept between 12 and 36 pixels, so the canvas reads as one surface being moved.
- **Keyboard.** With the keyboard in the app (not in a field, a button or the design itself): the arrows move the canvas 60 pixels, 300 with Shift; `+` and `-` zoom at the middle; `1` shows 100%; `0` fits. With Ctrl, Cmd or Alt held the keys stay the app's.
- **Double-click** the space around the design to zoom in there; Shift and double-click zooms out.
- **Highlight clickable** (a toggle in the controls, off by default, remembered in this profile): outlines the design's links, buttons, form fields, elements with a click handler attribute or a button-like role, and anything with a pointer cursor (counted once, not again for the text inside it). The outlines are drawn by the canvas over the design and let the pointer through, so the design still takes clicks; they follow the design when it changes (a quarter-second after the change) and keep the same width at every zoom.

Boundaries: the control script's two new words, `targets` and `untargets`, start and stop the report; until asked, the page measures nothing. It reports at most 400 boxes as numbers; the canvas cuts each to the design's frame and drops anything malformed, so a hostile design can at most draw outlines over itself. Nothing else crosses: no element text, attributes or selectors.

Verified in the hidden, isolated `design-canvas-sandbox.cjs` journey (43 checks: the three clickable parts of a login design outlined and placed with it, a new button outlined after it appears, arrows, `1`, `0`, double-click, the dots following, and every earlier canvas check) and unit tests for the box reader, the keys and the dot spacing. Not checked: a real trackpad, a visible window, Windows, the Local Web UI in other browsers, light theme.

## Designs first, real previews, and a design you can click (2026-11-13, #2723)

Requested 2026-11-13: move designs to the top; previews still did not show; some designs, such as `checkout-design-v2.html`, did not render; the Interact switch was not obvious, so interaction should always be on with the canvas still showing and draggable.

Why `checkout-design-v2.html` did not render: on the Mac where it was reported, no such file existed. The only mentions were fixture paths inside the chat that built the design canvas, and Library listed every path a chat named or wrote, whether or not it was ever on disk. Such an entry failed to open, and a phantom newer version could stand in for a design's real newest one.

Implemented, not yet released:

- **Designs lead.** See Browsing above.
- **Real previews.** On the Small icons, Large icons and Full cards tiles, an HTML page (a design or a web page) runs, laid out at 1440 wide, shrunk from its top-left corner to the tile, and held still once it has settled (its motion is paused after about a second, through the same control script as the canvas). It is served only when its tile comes within 200 pixels of the screen, released when the tile goes, offline, in the same opaque-origin sandbox as every served page, and cannot be clicked, focused or reached by the keyboard. Until it has settled, and if it cannot be served, the kind's drawing shows. An image (PNG, JPEG, GIF, WebP, SVG) shows as a cached still picture, cropped to the tile, read only when its tile is near the screen. Markdown and plain text now show document content, as described below. Unsupported files keep their drawing.
- **Files that are not there drop out.** Each chat file's folder is listed once (names only, eight folders at a time) whenever the set of paths changes, and a file its folder lists without is left out, along with its versions. A folder that cannot be listed keeps its files, so a refused or failed read never hides anything. Until a folder has been listed its files show. Designs found by listing the designs folder are not checked again.
- **Always interactive** canvas: see the canvas section above.

Verified in the hidden, isolated full-App Electron journeys: `design-canvas-sandbox.cjs` against the real preview server (33 checks: Designs lead, both design tiles show their pages, sandboxed, inert and held still, a chat's never-written fourth version is left out, the design is under the pointer and takes it with no Interact switch, a real drag on the space around the design and a scroll over it move the canvas, Space held in the design turns the pointer into a handle and letting go hands it back, plus the earlier canvas checks); `library-layouts` (19), `library-designs` (9), `library-html-preview` (19) and `library-intro` (18). A real click into the design could not be driven in a hidden window: with nothing painted the browser has no hit-test data for the design's own process and routes the click to the page around it, so the journey checks the hit test on both sides instead. Not checked: an on-screen click and hover in a visible window, a real trackpad pinch, packaged builds, Windows, light theme, the Local Web UI in other browsers, and the cost of many live tiles on a slow machine.

## Document thumbnails and fast repeat visits (#2747)

Implemented, not yet released:

- **Documents show content.** `.md`, `.markdown` and `.txt` tiles show the start of the actual file on a neutral paper background, not a generic document illustration. The compact first-page renderer preserves headings, text, lists and code/table text; it is not the full Markdown viewer. It drops frontmatter, links and media. Work is bounded to the first 24,000 characters, 160 source lines and one page. Truncated text reads may still supply that first page; binary, empty or refused reads keep the drawing. PDF and Office content thumbnails remain unsupported.
- **Small row icons.** Every left-hand row uses the app's shared 24-unit file-type symbol instead of shrinking a large tile illustration. Kind tint, row size, click target, source-chat label and keyboard behavior are unchanged. Icons perform no file reads.
- **Lazy, shared cache.** Supported document/image files are read only once their tile comes within 200 pixels of the viewport. A renderer-local LRU shares both pending and completed work across tiles, layout changes and visits to Library. It holds at most 80 entries and 8 MiB of encoded strings (estimated at two bytes per UTF-16 code unit), and runs at most three read/decode jobs at once. The cache key includes the exact path and source chat's revision. Successes expire after 60 seconds and failures after five seconds, checked on the next request; an already mounted tile is not polled. Cache contents are not written to disk and disappear on app reload. External edits without a chat revision are picked up on a later request after expiry.
- **Images are sized for tiles.** PNG/JPEG/GIF/WebP and inert SVG images are decoded once and reduced to at most 640 pixels on the longest edge, encoded as WebP at 0.8 quality (browser fallback encoding if unsupported). The original large data URL is not kept in the cache; animated images become still thumbnails. Unsupported, truncated or failed images retain the drawing. Images over 40 megapixels are refused after decoding. HTML tiles keep their existing offline, sandboxed live-page lifecycle, not this document/image cache.
- **No embedded resource fetches.** Document text is XML-escaped into a small inert SVG image: no HTML, foreign objects, scripts, network links, fonts or document images are embedded. Source images use the existing local-image validation and are rasterized before display. Clicking a tile or row still opens the original file, never the reduced picture.

Verification: focused unit tests cover escaped/bounded document output, supported formats, pending-read deduplication, concurrency, byte/count eviction, revision keys and failure/success expiry. The isolated full-App `library-thumbnails-sandbox.cjs` journey checks document content, fallbacks, no live document frames, read counts across layouts and return visits, lazy image reads, image downsampling and original-file opening. Matching desktop dark/light and narrow screenshots use unchanged `main` and the implementation with the same synthetic data. Verification results and limitations are recorded in the PR; packaged builds, Windows/Linux desktop and other Local Web UI browsers are not claimed.

## Privacy and boundaries

The guide uses original inline artwork and reads no files or external resources. Dismissal saves only a boolean in local storage. Listing a project's designs folder reads file and folder names only, in folders the person already saved as projects. To leave out files that are gone, Library also lists the folder of each file a chat named (names only). An HTML page or image on a tile is read or served when its tile nears the screen, offline and sandboxed as above; Markdown and plain-text thumbnails also read the file when its tile nears the screen; unsupported files are not read until picked. File previews retain their existing isolation and permission boundaries. Files remain in their original folders; nothing is published automatically. Hosted publishing remains separate planned work, not a Library action added here. The native phone apps do not have this page and are unchanged.

## Acceptance and verification

- First visit shows the guide, dismissal persists across leaving/re-entering and reload, and the page control reopens it.
- Modal keyboard dismissal, file opening, source-chat navigation, filtering and narrow-screen return behavior remain usable.
- Focused tests cover copy, storage failure/persistence, static artwork, voice navigation and the unchanged artifact index. The full-App isolated Electron journey records desktop/narrow screenshots in default dark and light themes and checks actual interactions.
- Visual and packaged-platform verification status is recorded in the implementing PR; code existence is not proof of shipped or verified behavior.
