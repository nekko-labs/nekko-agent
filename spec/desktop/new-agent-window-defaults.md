# New agent window defaults

Implemented; 67 focused tests, 1,145 desktop tests, desktop typecheck, isolated production build and five docs tests pass: an explicit model choice in a chat (including its expanded picker) or Add window becomes the next agent window's saved provider/model pair. Auto is saved as Auto, not the model it later resolves to. Browsing providers, loading catalogs and switching existing chats do not rewrite defaults or other chats' choices. New chats prefer the saved pair over a transient active catalog; startup restores settings before loading that catalog. A successful permission-mode change saves Ask, Guardrails or YOLO as the default for new chats; failed or missing-session updates do not. Mode choices now follow the settings-inheritance behavior below, including per-chat effort and privacy choices. No new network calls beyond existing settings/session APIs, permissions or telemetry. Acceptance: exact provider/model pairs, Auto, saved-default startup ordering, session-choice precedence, failed permission updates, and effort/execution/privacy regressions. Isolated visual interaction and packaged-app verification remain pending with the parent task.

## Latest Mode choices for new chats (issue #1106)

Implemented: 28 focused desktop helper/ModePanel tests, 31 Rust settings/store tests, desktop typecheck and daemon compilation pass. Live multi-window interaction and packaged verification remain unverified. A successful Mode change, including the composer effort slider or applying a saved mode, saves the changed choices for subsequent chats and agent windows. This covers execution/worktrees, approvals, effort, internet, Incognito, model scope/Auto switching, disabled tools/MCP/connectors, work mode, memory, guidance and tool approach. Each newly created top-level chat snapshots those choices, including fallback effort and approvals, so later defaults do not retune it. Existing explicitly saved chat choices are untouched. Older chats with no saved effort or approvals retain their legacy app-default fallback; this change does not migrate historical records.

The daemon is the authoritative cross-window store. Windows send only changed fields after a successful session write. The settings store merges them under its write lock, so two windows changing different fields do not erase each other's defaults. Creation reads current daemon settings, not the creating window's cached settings. The last completed settings write wins for the same field. A rejected or missing chat never changes defaults. Session and settings writes are separate: if saving defaults fails, the chat update may already have succeeded and the caller receives the persistence error; creating a chat while an update is still in flight need not observe it.

An explicit star/unstar action clears last-used overrides and uses the selected saved mode or baseline defaults; later manual changes override individual fields again. Sandbox still forces Ask and disables Git isolation. Sub-agents retain their existing inheritance path. No folders, task titles, transcripts, provider credentials or attachments enter the mode defaults. Incognito and Offline are now inherited choices for *new* chats, not switches on existing chats; they do not grant access or enable globally disabled services. No new network endpoints, permissions or telemetry are added. The Local Web UI uses the same transport behavior; direct API/phone session-option writes do not implicitly save desktop defaults.

Acceptance: independent-window field merging and restart persistence; latest effort and the full mode whitelist on new-chat creation; old chat records unchanged; missing/rejected updates excluded; normalized and cleared values; no task-data inheritance; sandbox constraints; unchanged existing store golden fixtures. Live multi-window interaction and packaged-build verification remain unverified; the daemon settings/store tests cover independent-window field merging and restart persistence without launching user profiles.
