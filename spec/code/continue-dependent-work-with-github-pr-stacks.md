# Continue dependent work with GitHub PR stacks

Successful linking explicitly refreshes the existing PR list read in both the daemon and host fallback. The updated membership replaces the cached result, so the following ordinary poll keeps the GitHub stack label and merge control instead of resurrecting the old Link stack action. Background polling continues to use cached reads.

Implemented 2026-10-12. Ordinary new chats keep their existing worktree defaults. On an open PR's action panel, **Continue as stacked PR** starts a new chat in a separate worktree from that PR's committed head, retaining the selected model and tool/privacy preferences. It requires a selected local project with a matching GitHub remote and a PR whose head and base are in the same repository. An existing stack can be continued from its top PR. Closed/merged PRs, fork PRs, offline/incognito and sandbox sessions cannot start this flow. It never switches the user's branch or copies their uncommitted edits into the dependent branch.

The checkout records its parent PR, parent branch and commit, and configures the parent as the default base for PR creation. After the agent publishes the dependent PR, **Link stack** creates a native GitHub stack or appends it to its parent's existing stack. The parent must still be open, the new PR must belong to this chat's branch and target the parent, and an existing parent must be the top layer. Failures leave both PRs and local work intact and explain the recovery. Stack merges open GitHub's stack review screen because merging an upper layer can include every layer below it. Rebasing active worktrees after parent edits or remote merges stays explicit; no automatic reset, force push or deletion is performed. GitHub stack support is a public preview, requires GitHub authentication with PR write permission for publication, and is optional for users of other Git providers. Desktop and shared web UI are in scope; native mobile entry points are not part of this first version.

Both the local engine and host fallback provision pinned dependent checkouts. Restoring a removed checkout retains its parent instructions and branch. If its dependent branch was deleted, resuming fails with a recovery message rather than creating unrelated work from main; the user starts a new stacked chat explicitly.

Verified locally: matching parent code appears in the new checkout; source edits survive; normal worktree creation is unchanged; PR base is inherited; native linking supports retries and rejects unrelated branches, forks and wrong dependency order; stack merges cannot accidentally use the ordinary synchronous merge path. Focused tests cover real Git isolation and mocked native API creation, appending, authentication fallback and merge guards. Hidden full-renderer interaction checks and inspected screenshots cover 1200px/390px in light/dark, including error recovery, continuation, linking and privacy restrictions. A real continuation from PR #482 verified authentication, fetching, parent HEAD equality, a separate checkout, inherited default PR base and preservation of the source checkout in an isolated profile; its empty test checkout and profile were removed afterward. The native stack listing endpoint was also read successfully. Automated tests do not execute live GitHub stack mutations or merges. Native mobile entry points and automatic local restacking are deliberately outside this scope.

Implemented in the pure state/settings layer: persisted wall layout (`grid`, `focus`, or `fixed`, integer columns/rows clamped to 1–6), dock placement/visibility and six panel flags, independent monitor minimization (`dock.minimized: Record<MonitorKey, boolean>`), nullable hero session ID, and per-session companion-folded flags (`folded` never folds whole chats). Defaults are grid 3×2, right dock shown with every panel unminimized, all dock panels enabled except insights, no hero, and no folded companions. Minimization accepts only booleans for known panel keys; missing/invalid entries (including a global boolean) default to false without changing other panels. Fresh trees contain only chats and terminals. Legacy automations/insights leaves enable the corresponding dock flags and are removed while retaining surviving IDs, split directions, and relative sizes; legacy grid visibility is carried into those flags. Invalid persisted values fall back to safe defaults.

An optional finite non-negative `monthlyBudgetUsd` setting is an advisory USD budget, not a spending limit; invalid/unset values mean no budget. These preferences are local persisted data and introduce no network requests or new resource sampling. Acceptance is covered by pure migration/settings tests. The working implementation now includes Grid/Focus/Fixed controls, geometry transitions with reduced-motion support, a pinned existing composer without its tether, four-side dock controls, individual panel minimization, and spend/savings presentation using existing usage/resource APIs. Grid mode renders the Add cell at the same split-tree leaf where `addPane` will insert the next window, so the preview and actual placement match. The Hardware dock reads existing runtime status only: resident local-model count, reported resident memory, placement and last-used summaries come from `RuntimeStatus.resident`; last tokens/sec remains unavailable until a runtime status field reports throughput. Chat and composer contents are retained. Companions read and close through the existing workspace tree. Release acceptance remains unverified: actual-window before/after and motion evidence, independent horizontal Focus-deck scrolling, exact companion ownership in multi-chat workspaces, terminal deck output/model details, full performance regression checks, and whether local-runtime throughput should become a first-class reported field. Full terminal emulation and per-tool/per-pane provenance remain planned non-goals for this PR, not shipped claims.
