## What it is for `[planned]`

One button turns a Mac running Nekko Agent into a CI runner. The provider's own job queue hands it `runs-on` jobs, and every job runs in a throwaway macOS VM that is deleted when the job ends. Job code never runs on the host.

- **The problem.** A public repo gets free hosted macOS minutes, but the capacity is small: a few macOS jobs at once, and per-PR macOS jobs can queue for an hour or more. So macOS checks run rarely or behind a label, and a macOS break shows up hours after the change that caused it.
- **The opportunity.** Teams that ship Mac or iOS software already own fast Apple Silicon Macs that sit idle at night and between builds. Doing this by hand means building VM images, scripts and launchd jobs, then hoping nothing on the host gets touched. Nekko Agent already has a daemon, an Automations tab, a scheduler and a phone app.

**Relation to the "Local CI runner" template.** [`docs/git-runner.md`](../../docs/git-runner.md) documents a workflow template that runs shell steps on the host and posts a commit status. That template stays, as the lightweight option. It is not a self-hosted runner: it does not speak the runner protocol, never picks up `runs-on: self-hosted` jobs, and runs on the host. This feature is the real runner: it takes jobs from the provider's queue, and the job runs only inside a VM.

## Principles `[planned]`

- **A job can only hurt itself.** Fresh VM, own kernel and disk, no host folders (except that scope's own cache volume, for trusted runs), no host credentials, public-internet-only networking, deleted afterward.
- **Your work comes first.** The default mode, Balanced, takes jobs while you work only when there is headroom, and steps aside for memory pressure, heat and busy apps; Do not disturb waits until the Mac is idle. Being a runner is opt-in and adjustable. (Until 2026-11-03 the default was Do not disturb; Philip changed it to Balanced, recommended.)
- **Apple's rules, enforced in code.** At most 2 macOS VMs per Mac, only for the owner's own development and testing. The settings cannot exceed it.
- **Local first.** One Mac works fully with no Nekko Cloud account.
- **Off means off.** The Off switch and "Pause all automations" stop every runner within seconds and delete its VMs. A menu bar indicator shows whenever a VM is running.
- **Never block a merge.** When no Mac is available, jobs fall back to hosted runners.

## Journeys `[planned]`

1. **One developer, one button.** Scheduled Tasks tab, CI runners section, Connect this Mac, pick GitHub. Install the Nekko GitHub App on one repo; Nekko creates a runner group limited to it. Nekko builds the pinned macOS image once (tens of GB) and shows the label to use. The user changes `runs-on` (or adds the picker job), and the next push runs on their Mac in a VM.
2. **A team pools several Macs.** Each person connects their Mac to the same GitHub org, each in their own priority mode. With a Cloud account the fleet view shows which are idle, busy or away, and the picker job falls back to a hosted runner when none is free.
3. **The lid closes mid-job.** macOS announces sleep; the runner marks the slot as leaving. The job is lost and GitHub fails it. An automatic re-run lands on another Mac or a hosted runner. On wake, leftover VMs and disk clones are deleted before anything new starts.
4. **The owner starts a heavy build.** In Do not disturb, local CPU above the threshold for 30 seconds stops new jobs at once. The running job keeps going for the grace period, then the VM is stopped and the job is re-run elsewhere. When the Mac is quiet again the slot comes back on its own.

## Scopes `[planned]`

Every runner is set up per repo or per org (a `Scope`): its own label, trust settings and cache volume. All scopes on a Mac share that Mac's slots, so the 2 macOS VM limit holds however many scopes are connected.

## Priority modes `[planned]`

Exact labels, in the order the app lists them. The default is the first, marked **Recommended**.

| Mode | Meaning | Grace for a running job when a gate fails | Warm VMs while idle | CPU per VM |
|---|---|---|---|---|
| **Balanced: in the background** (default) | Takes jobs while you work if there is headroom | 10 min | 1 | 6 |
| **Do not disturb: Only run when I'm idle** | Only when you are away and plugged in; steps aside the moment you need the Mac | 2 min | 0 (start on demand) | 4 |
| **Runner first** | For a docked Mac that mostly runs CI; jobs finish even when you are busy | until max job time | all slots | all but 2 |

The host always keeps at least 2 cores. A supervisor checks a chain of gates every 5 seconds (switched on, schedule, power, network, headroom, your activity); a slot takes a new job only when every gate passes, and the mode sets the thresholds. Signals come from public macOS APIs and are read on the device only. Input idle time and power come from the activity sampler; CPU and memory from the system stats, with the job VMs' own processes taken out; thermal state, Low Power Mode and memory pressure from the VM helper's `host` stream (ProcessInfo and a memory pressure source); a pending security update from `softwareupdate --list --no-scan` (an entry titled as a security update, or a macOS update for the running major version, so a declined upgrade to the next major release never blocks runners; when the version cannot be read every macOS update counts), where the 7 days count from the first time nekkod saw it listed; and a trusted network is identified by its router's hardware address (`route` and `arp`), which needs no Location access.

**Hard limits for every mode.** These stop a running VM at once: memory pressure critical, thermal state critical, free disk below the floor, Low Power Mode, Off, and Pause all automations. A macOS security update available for more than **7** days blocks new VMs until the Mac is updated.

### How a slot runs `[implemented; run against three real jobs 2026-11-02]`

Each slot runs one job in a throwaway VM and moves through five states: **starting** (the VM boots and its runner registers), **ready** (online, waiting for a job), **running**, **draining** (a gate failed and the job has its grace period) and **cleaning** (the VM is stopping; its clone and seed are deleted once the VM process has exited, and its registration is removed).

- **VMs kept ready** `[implemented 2026-11-03; unit and daemon tests, hidden renderer capture; not yet run against a live job]`. How many VMs stay booted while idle, 0, 1 or 2 (`readyVms`), set in **How should this Mac help?** (default 1) and in runner settings. Never more than the macOS slots, the memory limit or Apple's cap of 2 macOS VMs per Mac allow; picking 2 when connecting also sets 2 slots. Gates still decide whether a ready VM may boot, so Do not disturb with one ready VM boots it only while you are away. A runner saved before the setting existed has none and keeps its mode's count: **Do not disturb** boots a VM only when a job is queued, **Balanced** keeps one ready, **Runner first** keeps every slot ready.
- At most one VM starts per tick across all runners, never more than Apple's cap counting other apps' VMs, and none when the count cannot be read. A VM that fails to start is cleaned up, registration included; after 3 failures in a row the runner shows an error until its settings change or it is switched off and on. A passing GitHub error while registering does not count: the runner waits 30 seconds and tries again. A refused GitHub key shows an error at once, and a runner with no golden image shows "No VM image yet."
- A ready VM above what is wanted stops after 3 minutes idle; one that never comes online stops after 10 minutes.
- Memory headroom, an unknown host state and an overdue security update only stop a new VM from starting. A booted VM without a job stays through them (macOS counts the VM's own memory as used); the hard limits and the mode's soft gates still stop it. Until `softwareupdate` has been read once after nekkod starts, the host state counts as unknown, so new VMs hold; a failed read is retried within a minute.
- A VM we stop is checked once for a job GitHub gave it since the last status poll; such a job is audited as stopped and re-run like any other.
- A guest that powers itself off has run its one job, even if no poll saw it busy, unless no poll saw it online and the provider still lists its runner as offline. That runner never connected, so the VM is audited as a failed start, is not a job in Today, and counts toward the 3 failures in a row. Seeing a VM online or busy clears that count.
- Runners are named `nekko-<host>-<install>-<unix secs>-<n>`: `<host>` is the Mac's name lowercased to `[a-z0-9-]`, and `<install>` is 8 hex digits generated once per install and kept in `<data>/runners/install-id`. Sweeping stale registrations removes only offline ones named exactly that way for this install, never another Mac's, even one with the same name.
- The max job time counts from when GitHub first reports the runner busy. A job that reaches it is stopped and not re-run. In Runner first, the grace for a failing gate never runs past it.
- When the Mac wakes from sleep (the wall clock moved more than a minute further than the monotonic clock since the last tick, so a slow tick is not a sleep), every VM is killed, `vms/` is cleared, and each lost job is queued for a re-run before anything new starts. Lost or stopped jobs (when "Re-run lost jobs" is on) are re-run once, tried every minute for up to 30 minutes; the queue lives in memory, so a daemon restart forgets it.
- Every job and every failed start appends one line to `<data>/runners/audit.jsonl`: `ts`, `runnerId`, `repo`, `workflow`, `job`, `result` (`finished`, `stopped`, `lost`, `failedToStart` or `notRemoved`), `seconds` and `reason` (gate reasons, `maxJobTime`, `slept`, `removed`, or the error). `[implemented 2026-11-03]` A job's line also has `jobId`, `url` (the job's page), `pr` (`number` and `url` of the pull request a GitHub run lists; none for a fork's run or for GitLab) and `events` (each state the VM entered, with its time; the line's `ts` is when the VM was deleted). A VM that powered itself off with no job known is looked up once more by its runner name, among in-progress and then completed runs, so a job that started and ended between two status polls is still named (before, those lines read "A job"). A `notRemoved` line names a CI registration nekkod could not delete within an hour of its runner's removal (the runner id, its name, and the repo, org, project or group with GitLab's id and base URL) so the owner can delete it by hand. The runner's "today" totals count lines since local midnight, failed starts and `notRemoved` lines excluded. The file is not rotated yet.

### Suggested VM size `[planned; design awaiting Philip's check-in, T233 to T236]`

**Why.** A VM holds every gigabyte it is given from boot, whether the job needs it or not, and vCPUs it cannot use only take cores from the owner. Today the owner has to guess both numbers. The runner should say what size its jobs actually need, from what they used, and set it with one click. Measured on 2026-11-03 ([docs/ci-runner-performance.md](../../docs/ci-runner-performance.md)): Native iOS averaged 2.7 busy vCPUs out of 6 with bursts to all 6, and its memory use inside the guest is unknown because the host cannot see it.

**What the owner sees.** In runner settings, above **CPU per VM** and **Memory per VM**, one row: **Suggested for your jobs: 6 vCPUs, 8 GB**, the reason in one sentence (for example "The biggest job used 5.4 GB at most and never swapped; all 6 vCPUs were full for 14% of the time."), and **Apply**, which sets both fields through `runner:update` and takes effect from the next VM (a ready VM keeps its size until it has run its job). When the current size already matches, the row shrinks to a quiet "Fits your last N jobs". Before there is enough evidence it reads "Suggested size after 3 jobs (N so far)". The suggestion never changes settings by itself.

**One size per runner.** Every VM of a runner is the same size, and a ready VM boots before GitHub picks its job, so the suggestion sizes the runner for its most demanding job, not each job separately. It uses the runner's `finished` jobs from the last 30 days that carry usage (at least 3); jobs stopped, lost or killed at the max job time are left out.

**What is measured, per job.** A sampler in the guest (the boot script, as root, every 5 s from the job's start to its end) records busy vCPUs (from the guest's own CPU idle share times `hw.ncpu`), memory in use (wired plus app memory plus what the compressor occupies, from `vm_stat`; file cache is left out because macOS gives it back), the compressor's size, and swap-outs (`vm.swapusage` and `vm_stat`'s swapouts). nekkod reads the samples after the VM stops and adds a summary to the job's audit line as `usage`: the VM's `cpus` and `memoryMb`, `cpuP95` (busy vCPUs, 95th percentile), `cpuFullShare` (share of samples with every vCPU nearly full, busy at least `cpus - 0.5`), `memPeakMb`, `compressedPeakMb` and `swapOutMb`. Samples themselves are not kept. A job whose samples are missing or unreadable gets no `usage` and does not count.

**How samples leave the guest.** Through a fourth disk, not the clone. nekkod creates a 1 MiB raw image per VM with a header block naming it, attaches it read-write, and the boot script writes samples to the raw device, with no filesystem. After the VM process exits and before the clone is deleted, nekkod reads that file with plain file reads, at most 1 MiB, and parses it strictly (numbers only, one sample per line, anything else drops the job's usage). Rejected alternatives: mounting the job's clone on the host the way the image build reads its proof file would hand the host's APFS driver a filesystem an untrusted job has written; a serial console is a host channel `nekko-vm` leaves out on purpose. Only root in the guest can write the raw device (`runner` has no sudo and is not in `operator`). A job that gains root can only fake its own suggestion, which the owner still has to apply and which stays inside the limits below.

**The rules.** `N` is the current vCPUs per VM, `M` the current memory per VM.
- CPU up: when any job had every vCPU nearly full for at least 20% of its samples, suggest `N + 2`.
- CPU down: when every job's `cpuP95` is at most `N - 2`, suggest the largest `cpuP95` rounded up, plus 1.
- Memory up: when any job swapped out at all, or its compressor peaked at a quarter of `M` or more, suggest `M + 4 GB`, or the largest `memPeakMb` plus 2 GB rounded up to whole GB if that is more.
- Memory down: when the largest `memPeakMb` plus 2 GB headroom is at least 2 GB under `M`, suggest that figure rounded up to whole GB.
- Otherwise the current value stands. CPU and memory are judged separately.
- Never below the floor: GitHub's standard hosted Mac, 3 vCPUs and 7 GB, which passes the jobs this repo routes here. Never above the ceiling: `cpus_per_vm`'s (cores minus 2) for CPU; for memory, the 64 GB setting limit and the runner memory budget divided by the macOS slots the owner asked for, so applying it never costs a slot. A suggestion held down by a limit says so ("The jobs swapped; 8 GB is the most this Mac can give each of 2 VMs.").
- GPU is not part of it: a VM's paravirtualized GPU has no size setting.

Checked against the 2026-11-03 Native iOS run: all 6 vCPUs full for 14% (under 20%) and a 95th percentile of at least 5 (above 4) keeps 6 vCPUs, the answer the analysis reached by hand.

**Not in this version.** Per-step breakdowns (the analysis joined samples to step times by hand; the rules need only the job). A floor read from each job's hosted history through the Actions API (the app already has `actions: write`), which would raise the floor for jobs that run on `*-xlarge` (5 vCPUs, 14 GB) or `*-large` (12 vCPUs, 30 GB) hosted Macs. Resizing a ready VM when the size changes.

## Keep awake `[planned]`

Exact labels.

- **System default.** The Mac follows its own Energy settings. If it idles to sleep mid-job, the job is lost and re-run elsewhere.
- **While a runner is active** (default). Holds a sleep-prevention power assertion while any slot is Running or Draining and releases it when the last job ends. The display can still sleep.
- **Always.** Holds the assertion whenever the runner is on and its gates pass.

None can stop sleep when the lid closes on battery, when Low Power Mode turns on, or when the user chooses Sleep. The menu bar shows it `[implemented T213]`: the tray icon gets a green dot while any VM exists or a runner keeps the Mac awake, and its menu gains the information-only lines `CI runners: N VM(s) running` and `Keeping this Mac awake for CI`.

## Limits and defaults `[planned]`

- **macOS slots:** at most **2** VMs at once per Mac, counting macOS VMs started by other apps. Default 1.
- **Linux slots:** default 0, at most 8. Not counted against the macOS limit. See [Linux slots](#linux-slots).
- **Memory:** 8 GB per VM. Total runner memory is a setting. The default is a recommendation computed from the Mac's RAM and the owner's usual memory use (the owner keeps the larger of 8 GB and 1.25 times their usual use), shown in settings as "Recommended: N GB for this Mac". It is never above 75% of RAM, whatever the setting says. A VM starts only when macOS reports its memory plus 2 GB available right now; a running VM is not stopped by this check. Slots that do not fit are greyed out with the reason.
- **CPU per VM:** 4 / 6 / all but 2 by mode.
- **Disk:** image disk budget 150 GB; free disk floor 25 GB (below it no new VM starts and running ones stop).
- **Max job time:** 2 h. The VM is destroyed at the limit whatever the provider's timeout.
- **Only when:** on power, on trusted networks, never on hotspots, and not while a VPN carries all the Mac's traffic (a full-tunnel VPN or a Tailscale exit node). With **On power** off, a runner still waits on battery below its mode's floor: 80% for Balanced, 50% for Runner first, any charge for Do not disturb. An unread charge counts as below the floor; macOS reads it from IOKit's power sources (the internal battery's current of max capacity), and the card shows "On battery" with no figure when it is unknown. The setting **Let jobs use the internet directly while a VPN is on** (off by default) lifts the VPN pause; job traffic still leaves by the physical interface, never the tunnel. Like the other network gates, a VPN coming on drains a running job with the mode's grace (Runner first lets it finish).
- **Accepted ranges:** settings outside these are clamped when loaded: macOS slots 0 to 2, Linux slots 0 to 8, memory per VM 4 to 64 GB (0 means 8 GB), total runner memory at least 4 GB (below that, the recommendation), vCPUs per VM at least 2, image disk budget 50 to 4000 GB, free disk floor 10 to 1000 GB, max job time 10 to 1440 minutes. A hand-edited record that cannot be read is skipped, and a file that is not JSON is kept as `runners.json.bad`.
- **Trusted networks:** the networks you approved, recognised by the router's hardware address, which macOS records itself, so no Local Network permission is needed; connecting adds the current one. At most 32.
- **Unknown Mac state:** no new VM starts while the Mac's state, its egress interface or its addresses are unknown; a running job is not stopped by that alone.
- **Safety:** fork PRs off, re-run lost jobs on, build cache for trusted runs on.

## The sandbox `[planned]`

| Threat | Control |
|---|---|
| A job reads your files, keys or tokens | Separate VM with its own disk. No host folder, clipboard or keychain reaches it. The VM has a display device with no view and no input devices (a macOS guest needs one to boot), so nothing of its screen reaches the host. That display is a paravirtualized GPU (`VZMacGraphicsDeviceConfiguration`): the guest's GPU commands are processed in the host's VM process against the host GPU stack, an accepted risk because a macOS guest does not boot without it, and it supersedes the original "no graphics" constraint. The only secret inside is a single-use runner config. |
| A job attacks your LAN or other devices | The VM's only network is a userspace NAT inside `nekkod` that forwards to public unicast internet addresses only, judged after DNS resolution, and never to the Mac's own addresses or any network the Mac is on, even a public one. |
| A job reaches networks behind your VPN | Every host socket the NAT opens, DNS included, is bound to the Mac's physical interface (Wi-Fi, Ethernet or cellular), so no VPN route, split or full tunnel, ever carries job traffic. With no physical interface, or before it is known, every flow is refused. A full-tunnel VPN pauses the runner by default. Implemented; a check against a real tunnel (Tailscale exit node and subnet route, or a packet-tunnel VPN that enforces routes) is pending, owned by T212. Known risk: a packet-tunnel VPN with includeAllNetworks or enforceRoutes may capture or drop sockets bound to the physical interface (dropping is fail-safe). |
| A job reaches services on the host | There is no host-to-guest and no guest-to-host network. The NAT answers DHCP and DNS for the guest and forwards nothing to a host address. |
| Malware persists into the next job | Every job starts from a new copy-on-write clone of a read-only golden image; the clone is deleted after the job. |
| A job poisons the build cache | One cache volume per scope, attached only for trusted runs (never fork PRs), size-capped, wipeable from the runner card. |
| A job eats the Mac | Fixed vCPU, RAM and disk per VM, the disk floor, memory and thermal hard limits, max job time. |
| Stolen runner credentials | A JIT config works for one job and expires. The GitHub App private key lives in the macOS keychain and never reaches a guest. |
| Fork PRs run on your Mac | A PR runs its own workflow file, so the picker is no boundary. On a public repo: GitHub's approval for all external contributors, and the runner's org group restricted to selected workflows on trusted branches. The VM is the second layer. The connect sheet refuses public repos unless allowed. Through the click-through connect, a public repo's runner connects off and the daemon refuses to turn it on until GitHub holds outside contributors for approval: Nekko sets it (the repo's own app, or `gh` for an org), or the owner confirms it after following a link. Connecting by hand keeps the older behavior: it comes up on, with the approval callout. |
| A tampered image | Images are pinned by digest and checked before cloning. |

**Guest network, exactly.** Public unicast internet only. Never RFC 1918, loopback, link-local, 100.64.0.0/10, multicast, broadcast, 0.0.0.0/8, 240.0.0.0/4, 198.18.0.0/15, fc00::/7, fe80::/10, or any host address. "Host address" covers the Mac's own interface addresses, every on-link prefix of every host interface, and known WAN or gateway public addresses, because most LANs give devices global IPv6 addresses that the static list allows. The NAT refreshes that list whenever the Mac's network changes.

**Guest network, the P1 details.** Guests are IPv4 only: the guest is 10.233.0.2/24 behind gateway 10.233.0.1, and every IPv6 frame from the guest is dropped. DNS goes through the gateway: 53/udp and 53/tcp to the gateway are forwarded to the physical interface's own resolvers, keeping only ones a guest could connect to anyway (never loopback, link-local, 100.100.100.100 or anything on the LAN, such as the home router, because DNS over TCP is a raw pipe to the resolver); with none left, DNS goes to 1.1.1.1 and 8.8.8.8. Every other packet to the gateway is dropped or reset. The router's public address is learned from the router itself (NAT-PMP, else UPnP), never from an internet lookup, and is refused like the Mac's own addresses; when the router answers neither, a guest can reach that address, a known limit. Each VM holds at most 256 flows at once, a host connect gives up after 15 s, and a guest TCP connection that stops answering (keep-alive probes included) is reset after an idle timeout and frees its slot. The supervisor refuses to start a VM if it cannot read the host's addresses, rather than run with an empty list.

**Guest network and VPNs (T211).** `nekko-vm egress` streams the Mac's physical egress interface from `NWPathMonitor` (the first Wi-Fi, wired or cellular interface on a monitor that excludes tunnels) and whether a tunnel leads the default route. The NAT creates every host socket unconnected, binds it to that interface with `IP_BOUND_IF`, then connects, so split-tunnel routes (a corporate VPN's ranges, Tailscale subnet routes) and full tunnels (an exit node) never carry job traffic. With no physical interface, or before the helper's first report, every flow is refused: TCP gets a reset, UDP and DNS get nothing. `nekkod` restarts the helper if it exits and refuses flows until it reports again. The VPN pause is the `nekko-runner` gate described under Limits; the supervisor that feeds it the helper's report lands with T212. Implemented and unit-tested only (binding checked on lo0); a check against a real tunnel (Tailscale exit node and subnet route, or a packet-tunnel VPN that enforces routes) is pending, owned by T212. Known risk: a packet-tunnel VPN with includeAllNetworks or enforceRoutes may capture or drop sockets bound to the physical interface (dropping is fail-safe).

**Who holds the virtualization entitlement.** Only `nekko-vm` carries `com.apple.security.virtualization`; `nekkod` and the app do not. Dev builds ad-hoc sign it. Packaged builds stage it and sign it with its own entitlements file (the electron-builder `mac.sign` hook for Developer ID, after-pack for unsigned builds), and `scripts/check-mac-entitlements.sh` fails a macOS release or installer build if `nekko-vm` lacks the entitlement, anything else has it, or a file cannot be read. CI proves this with an ad-hoc signed dry-run through the real hook; a Developer ID signed and notarized release is still pending (T214).

**Golden image** `[implemented T214, boot-checked in a VM 2026-10-25, on macOS 26 with Xcode 27.1 2026-10-28]`. Jobs run in clones of an image you build and host yourself in P1, from a Cirrus `macos-tahoe-xcode` base (or Apple's restore image) with `scripts/runner-image/provision.sh`, following [docs/ci-runners-image.md](../../docs/ci-runners-image.md). Tart is used only to build the image, never at job time. In each clone, one root LaunchDaemon (`dev.nekkolabs.runner-boot`) runs the boot script: (1) wait until the `NEKKOSEED` volume shows a file (macOS makes its mount point seconds before mounting it, so an empty folder does not count); (2) accept exactly one regular file named `jit-config` (GitHub) or `gitlab-runner.toml` (GitLab), 1 byte to 64 KiB, else run nothing and power off; (3) copy it where only the job user can read it and unmount the seed; (4) wait for the auto-login session; (5) run one job as `runner` in that session with `launchctl asuser` (no LaunchAgent; GitLab's runner starts the same way, untested until T215); (6) power off whatever the outcome. With no seed at all, or an empty one, the guest stays up and starts nothing. provision.sh makes `runner` a standard user with a random password, logs it in automatically, installs the pinned GitHub Actions runner and gitlab-runner (each checked by SHA-256 from its official release), gives `runner` Homebrew without sudo, and locks the guest down: every admin account and root are disabled (FileVault must be off), no passwordless sudo, SSH, Screen Sharing, Remote Desktop and the Tart guest agent off or removed, and it fails unless `runner` has no sudo, is not an admin, and SSH and Screen Sharing are disabled. An image is rebuilt from the base, never patched. Still planned: pinning images by digest and checking them before cloning, and the image disk budget.

**Image builder** `[implemented T226; the setup screens are T227 below]`. On a macOS 27 Mac, one action builds the image with no terminal and no Tart ([decision 0038](../../docs/decisions/0038-image-builder-reaches-a-build-vm-over-ssh.md)). `runner:imageBuild({ kind, runnerId, priority })` starts a job in `nekkod` that works in `runners/images/default.new` and reports through `runner:imageStatus` and the `runner:imageChanged` push; `runner:imageResume` and `runner:imageCancel` pick it up or remove it. Seven stages: Check (macOS 27, VM support, 110 GB free, security updates, Xcode found), Download (Apple's newest restore image, resumable), Install (a 140 GB sparse disk, then a first boot with a random-password admin, auto-login and SSH, saved as a checkpoint; the build's copy of the restore image is then deleted), Xcode (the Mac's Xcode as a `tar` stream, first launch, the iOS simulator, Homebrew with `zstd` and `gnu-tar` so `actions/cache` compresses with zstd as on hosted Macs; `macosOnly` skips Xcode and the simulator), Lockdown (`provision.sh` as a one-off LaunchDaemon, then the proof file read from the stopped disk, where no proof file is a failure), Test (a clone must boot, reject a `not-a-config` seed and power off within 10 minutes, with its boot log showing the runner ran), Finish (swap the image in, write `image.json`, apply the chosen mode, turn the runner on). A failure names its stage and keeps what finished: Xcode and Lockdown restart from the checkpoint, so macOS is not reinstalled. Quitting pauses the job and the next launch offers to resume. Every guest command has a time limit. Between stages the job waits, with a reason, for a free VM slot, critical memory, serious heat, the disk floor, and from Install on, for power; idle and priority modes do not apply, because the owner started it. It holds the Mac awake, uses 8 GB and leaves 2 cores free. A running job's clones are unaffected, and `images/default` is untouched until the test boot passes. Below macOS 27 the build refuses with "Update this Mac to macOS 27 to set it up here.", and the manual guide stays.

**Keeping the macOS image** `[implemented]`. A downloaded restore image is also kept in `runners/images/cache/`, under the file name in Apple's URL (version and build), as a hard link, so deleting the build's copy does not delete it. Download asks Apple for the newest image every time and uses the kept one only when the names match; a newer one replaces it, so at most one is kept. When Check finds less than 110 GB free, the kept image counts as free space and is deleted to make it, instead of refusing the build. The setup sheet shows **Downloaded earlier** in place of the download size while one is kept (`ImagePlan.cachedMacos`).

**Update scripts** `[implemented; not yet run on a real image]`. For a change to Nekko's own guest scripts, the runner settings offer **Update scripts** beside **Rebuild image**: `runner:imageBuild({ kind: "refresh" })` runs Check (an image exists, the scripts are staged), Scripts, Test and Finish, in minutes instead of half an hour. Scripts clones `images/default`, mounts the clone's disk on the host, and overwrites `nekko-runner-boot.sh` and its LaunchDaemon plist in place (each keeps its owner and mode, because a host mount that ignores ownership could not set them on a new file). It replaces only those two files: one missing means an image older than them, which needs a rebuild. Lockdown is not rerun, and `image.json` carries over. A new macOS, Xcode or `provision.sh` change still needs **Rebuild image**. The progress sheet reads **Updating the image**, with its own three stages, and says the image in use keeps taking jobs until the updated one passes its test boot. Like a rebuild, it names no runner, so the runner keeps its mode and its on or off state.

**How the guest gets its config.** `nekkod` mints the single-use JIT runner config and puts it on a read-only seed disk attached to the VM. The host never connects into the guest: no SSH, no host-to-guest network.

### GitLab guest `[implemented in the Layer E image scripts; untested in a real guest]`

What the golden image must hold for a GitLab runner, read by the image work (T214, Layer E):

- `gitlab-runner` darwin-arm64, version 17.1 or later (`run-single -c` needs it), pinned and checked against the release's published checksum, at `/usr/local/bin/gitlab-runner`. `provision.sh` on the Layer E branch pins 19.5.1.
- The same auto-login `runner` user and LaunchAgent as the GitHub guest (GitLab supports only a user LaunchAgent, never a LaunchDaemon). The boot agent mounts `NEKKOSEED` read-only; when `gitlab-runner.toml` is present it copies it to `~/.nekko/gitlab-runner.toml` (0600), runs `gitlab-runner run-single -c ~/.nekko/gitlab-runner.toml -r nekko --max-builds 1` with no `--wait-timeout` (the supervisor owns idle time), and powers the VM off when the process exits, whatever its exit code. With `jit-config` it runs the GitHub runner as before. Layer E's `nekko-runner-boot.sh` already does all of this.
- `bash` present (the toml sets `shell = "bash"`). The shell executor creates `/Users/runner/builds` and `/Users/runner/cache` (the toml's `builds_dir` and `cache_dir`) under the runner-owned home; the first real guest run is the check.

**The honest limit.** No software promises zero risk. The target is that a job can only hurt its own VM. The remaining path is a VM-escape bug in macOS itself, the class of bug that affects every desktop virtualization product. The planned fork-code default and 7-day security-update gate reduce exposure. The network filter constrains traffic through the guest's virtual NIC, not code that has escaped into a host process; it cannot promise LAN isolation after a VM escape. The guest's paravirtualized GPU (needed for macOS guests to boot) is one more host surface of that kind: its commands run in the host's VM process against the host GPU stack.

## Linux slots

`[implemented 2026-11-05; the image built and a job VM booted to its runner on a real Mac, against fixtures in the supervisor and UI; a whole GitHub job on a Linux VM not yet seen]` Decision [0053](../../docs/decisions/0053-linux-runner-vms-boot-ubuntu-directly.md).

**Why.** Apple caps a Mac at two macOS VMs; Linux guests have no such cap. Lint, unit tests and server builds rarely need macOS, so Linux slots are how one Mac takes much more of a repo's CI.

**What the owner gets.**
- **Linux slots** in runner settings, 0 to 4 in the sheet (8 accepted from a hand-edited file). Each is an ARM64 Ubuntu 24.04 VM with Docker Engine (`services:` and `container:` work), git, build-essential, Python and the usual CLI tools, and a `runner` user with passwordless `sudo`, as on GitHub's hosted Ubuntu.
- A job lands on one when its `runs-on` is `[self-hosted, Linux, ARM64]` or names `<label>-linux` (GitLab: the `<label>-linux` tag, or `linux` and `arm64`). macOS VMs keep `[self-hosted, macOS, ARM64]` and the plain label, so neither kind takes the other's jobs. amd64 jobs (`X64`) never come here.
- **Linux image** row: **Set up Linux image** downloads Ubuntu (about 600 MB, from Canonical, each file checked against its published SHA-256) and builds `runners/images/linux` in a few minutes (151 s measured on an M-series Mac with the downloads cached). It shows the stage (Downloading, Unpacking, Installing, Test boot, Finishing) with a percentage while downloading, **Cancel**, the failure's sentence, and once ready the Ubuntu, runner and Docker versions with **Rebuild Linux image**. No Xcode is needed. A build never touches a working image until its test boot passes.
- Slot tiles: the Linux tiles follow the macOS ones, `Slot N · Linux`, "Starts a VM when a Linux job is queued", the job while one runs, or greyed with why ("No Linux image yet.", or that the memory macOS slots leave is used up).

**Rules.**
- Linux VMs boot only for a queued Linux job (polled every 30 s); none is kept warm, since one boots to its runner in about 5 s. An idle one with no job stops after 3 minutes, as a macOS one does.
- They share the runner memory budget and the per-VM size with macOS VMs, after the macOS slots that may run: `min(linux slots, budget / memory per VM - macOS slots available)`. A Linux VM never takes a macOS VM's place.
- Apple's cap counts every Virtualization.framework VM on the Mac except Nekko's own Linux ones. Another app's Linux VM (Docker Desktop, say) still counts, because nothing tells the kinds apart from outside.
- One VM starts per tick across all runners and kinds, macOS first.
- A runner with no macOS slots needs no macOS image; Linux slots without a Linux image show "No Linux image yet." and leave macOS alone.
- The same gates (priority, power, network, VPN, security update, memory headroom) and the same max job time, audit log, VM log and job log apply.

**Security.** Everything decision 0022 says holds: the filtered NAT is the only network, the JIT config arrives on a read-only ISO seed, nothing is shared from the host (no Rosetta share either, which is why there is no amd64), no SSH server in the image. cloud-init runs once, at build time, and is disabled after. The guest kernel and initrd come from the image; the kernel command line is fixed in `nekko-vm`.

**Channels** `[implemented 2026-11-05]`. `runner:linuxImageStatus()`, `runner:linuxImageBuild()` and `runner:linuxImageCancel()` return a `LinuxImageView` (`state` none, building, ready or failed; `stage`; `progress`; `message`; `proof`, what the build installed), and `runner:linuxImageChanged` pushes it. `RunnerView` gains `linuxAvailable` and `linuxError`; each `SlotView` carries `guest` (`macos` or `linux`). None reach a phone.

## Apple's license `[planned]`

This is a product reading of the macOS license, not legal advice; check the current license text for each supported macOS version before launch.

- Up to 2 additional macOS copies in VMs on each Apple-branded Mac already running macOS. Nekko stops at 2, counts macOS VMs other apps already run, and Virtualization.framework itself refuses a third.
- The purpose is software development and testing. Runners serve only the repos and orgs the owner connects.
- The Mac is one the user owns or controls.
- No service bureau, time-sharing or terminal sharing. Nekko never matches a Mac to accounts outside its owner's orgs: no marketplace and no donate-to-any-project mode.
- Renting whole Macs to a customer is out of scope; a paid runner offering would need legal review first.
- Linux guests are not covered by the macOS VM limit (Apple DTS on the developer forums, 2026), so Linux slots have no Apple cap.

## Providers `[planned]`

**GitHub Actions comes first**, then GitLab (T215). Buildkite is planned later, behind the same adapter shape (connect, mint a single-job credential, start the agent in the VM, read job status).

**Connecting GitHub** `[implemented T212]`. The owner makes a GitHub App, installs it on their org or repo, and gives this Mac its app id, installation id and private key (the PKCS#1 `.pem` GitHub downloads, under 16 KB). Before anything is saved, connect checks in order: the key mints an installation token (a refused key fails with "GitHub refused this app key. It may have been revoked; connect again with a new key."); the installation's account is the scope's org or owner, compared in any case, so only the owner's own accounts can be connected; every repo is reachable and private, and a public repo is refused unless the owner turns on public repos; for an org, the runner group `nekko-<label>` is created, or updated, limited to the chosen repos. An org that cannot create runner groups is refused ("This org cannot create runner groups. Connect a single repo instead."), never put in the Default group. Only then is the key stored in the keychain item `github-app-<appId>` of the runner vault, and the runner saved enabled (unless the request says `enabled: false`; reconnecting never turns a runner on, and turns it off only for an open fork approval), trusting the network the Mac is on. Any failure leaves nothing stored and nothing registered. Reconnecting a scope replaces its GitHub link and keeps its settings; if it moves to another app, the old app's key is deleted once no runner uses it. An org's runner group is shared by name: its repo list is whatever the last connect for that org and label set, so two Macs connected with the same label share one group. GitHub calls count as connector traffic, so turning connectors off in Settings > Connections also stops the runner from reaching GitHub. A runner whose key is later revoked or removed shows Error, not Waiting; a GitHub rate limit (a 403 whose message names a rate limit) is a passing error, not a revoked key. A repo runner's repo is checked again before each registration: if it became public and public repos are not allowed, the runner shows Error and registers nothing. Owner, org and repo names match in any case wherever scopes are compared.

**Connecting GitHub with clicks** `[implemented T225; run on real GitHub through the daemon 2026-11-02]`. Issue [#1467](https://github.com/nekko-labs/nekko-agent/issues/1467). The owner makes no app by hand and pastes nothing. The sheet asks which account; `nekkod` opens a loopback port for this attempt (127.0.0.1 and ::1, reached as `http://localhost:<port>`) and a one-use `/start` page that posts a GitHub App manifest to GitHub, because GitHub takes a manifest only as a browser form post. The app is private, its webhook is off, and it holds Actions (write) and Metadata (read), plus Self-hosted runners (write) for an org or repo Administration (write) for a personal account. An org app never gets repo Administration, except an org GitHub says cannot use runner groups, which is offered one repo instead, before anything is created. The owner clicks **Create**; GitHub redirects to `/created` with a one-hour code and the `state`. A wrong `state` (compared in constant time) converts nothing, and a good one works once, so a forged or replayed callback does nothing. `nekkod` swaps the code for the app's id, slug and key, stores the key in the vault at once and writes `runners/pending-app.json` (0600: app id, slug, owner, kind, no secret) before the browser moves on to the app's install page. The owner picks repos and clicks **Install**. `nekkod` polls `GET /app/installations` every 3 s with the app's JWT and matches the account in any case; the redirect only wakes the poll sooner, so a closed tab breaks nothing. It then lists the installation's repos (the first 100) and the sheet confirms. Confirm is an ordinary `runner:connect` with the key already stored, so every check above still runs, and it records the app's slug on the runner. Every Confirm connects with `enabled: false`, because the mode and the image come next; connecting again turns off a working runner only when it serves a public repo, whose approval every Confirm opens again until it is settled, and the mode step turns it back on. A runner on a public repo stays off until that is settled; see the Fork PRs row above.

Leaving is safe: because the key is kept from the moment GitHub hands it over, closing the tab, cancelling or quitting between Create and Install resumes at Install with the same app when the sheet opens again, never a second app. Pressing the button twice carries on the same attempt. A saved runner of the same owner with a known slug reuses its app and goes straight to Confirm, with a link to add repos on GitHub and a Check again that reads them afresh; a runner connected by hand has no slug, so its owner gets a new app. A pending app whose key cannot be read is not resumed, so a new one is created; its file stays, since a locked keychain reads the same. If GitHub says the app no longer exists, a pending app is forgotten, a saved runner keeps its record, and the start creates a new app; any other refusal keeps it. The port and the poll stop after an hour or on cancel, and the sheet then says so; the app stays pending. A failure in the callback names no code and no key, and repeats nothing GitHub said. Without `gh` the sheet asks for the account's name and kind. An org whose plan cannot be seen can ask for one repo up front (**On the Free plan? Connect one repo instead**); otherwise an org that cannot use runner groups is only found out at Confirm, which stops with the reason and a link to delete the app. `gh` is looked for in Homebrew's folders too, because an app started from the Dock gets a bare PATH. A runner left off with its approval unsettled (`forkApprovalOpen`) cannot be turned on from the card or settings; the refusal says what to do, and connecting again reaches the same step. After a restart, GitHub's last redirect lands on a dead local page, since the app's redirect names the old port; the sheet still moves on by itself. Connecting by hand (**Use an app I already have**) stays as it was.

## Laptops that come and go, and the offline fallback `[planned]`

A queued self-hosted job can wait a long time, and a job on a runner that vanishes fails only after the provider loses contact. So the provider is never left waiting on a Mac that may leave:

- **Pick before you queue.** A small job on a hosted runner asks which Mac is free and outputs `runs-on`; with none free it outputs the hosted runner. Without a Cloud account the picker calls the provider's runners API with a read-only token. On a fork PR the token is absent, the call fails and the job falls back to hosted.
- **The picker** `[implemented T214, off until the pilot]`. `scripts/pick-runner.mjs` behind `.github/actions/pick-runner` outputs `["self-hosted","<label>"]` when an online, idle runner has the label, else the fallback (`macos-latest` by default, `macos-14` in Native iOS). It never fails the workflow: no token, an API error, a timeout or a bad reply all give the fallback. It lists the repo's runners, or with an `org` input the org's (an org runner does not appear in the repo's list). In `ios-native.yml` it runs only when the repo variable `NEKKO_MAC_RUNNERS` is `on`, and only for the schedule and dispatches on `main` or `ci/ios-batch`, the refs the runner group allows; a labeled PR always runs hosted. It uses the org from `NEKKO_MAC_RUNNER_ORG` and the fine-grained token `MAC_RUNNER_STATUS_TOKEN` (organization Self-hosted runners: read). A job lost to sleep is re-run, and the re-run keeps the first attempt's answer, so it waits for the same Mac. On a public repo the picker is not a boundary against fork code, since a PR runs its own workflow file: fork PR approval for all external contributors and a runner group restricted to selected workflows on the default branch are, with the VM as the second layer (see the pilot runbook).
- **Announce leaving.** On sleep, lid close, leaving a trusted network or a failed gate, the runner stops being offered at once.
- **Re-run lost jobs.** A job lost because its runner vanished is re-run once automatically.
- **Clean up on wake or launch.** Leftover VMs, clones and runner registrations are removed before a slot opens.

**GitLab** `[implemented T215, unit-tested with scripted HTTP; never run against a live GitLab]`. A runner record holds a GitHub link or a GitLab link (never both); `runners.json` files written before T215 load unchanged, and GitLab records get ids `gl-<random>`. Instances are self-managed or gitlab.com, given as an https origin; no other scheme is accepted. Connect checks, in order, and stores nothing until all pass:

- The instance's host name must resolve only to public addresses, judged like guest traffic (not this Mac's networks, a LAN, Tailscale or loopback), because the guest must reach it. No request is sent otherwise. No request carrying the token ever follows a redirect; a 3xx is an error that names the redirect host.
- The project or group exists and the token's user can see it. A public project is refused unless the owner allows public projects. A group record lists 1 to 20 projects inside the group, because GitLab has no group-level pending jobs list; the list only drives start-on-demand, while the group runner still takes jobs from every project in the group.
- The token is active and has `create_runner` and `manage_runner` (`api` covers both), read from `/personal_access_tokens/self`, then a probe: a paused runner is created and deleted, which also proves the Owner role (GitLab refuses `POST /user/runners` otherwise). Only then is the token stored in the runner vault item `gitlab-token-<record id>`; it never reaches a guest.

Per VM, nekkod creates one runner with `POST /user/runners`: `locked`, `run_untagged` false, the tags above, `maximum_timeout` from the max job time, and `access_level` `ref_protected` unless the owner unticks "Protected branches and tags only" (default on). Its `glrt-` token goes into `gitlab-runner.toml` on the read-only seed, and the guest runs `gitlab-runner run-single --max-builds 1` from it. nekkod pauses the runner as soon as `GET /runners/:id/jobs?status=running` shows a job (pause fails closed), and deletes it when the VM ends. A failed delete is retried with backoff; auth failures hold a record's removals and show as its error. A removed record is kept up to 1 hour while removals are pending, then nekkod writes a `notRemoved` audit line naming the runner so the owner can delete it by hand. Start-up and a removed record's sweep delete every runner whose description has the exact name shape `nekko-<host>-<install>-<secs>-<n>`; a group sweep keeps any runner not owned by that group (GitLab lists ancestor groups' runners too), and two GitLab group records on one instance never sweep while the other has VMs.

Start-on-demand counts pending jobs per project (a group record counts its listed projects), only those whose tags are all ours and, under protected only, whose branch or tag is protected (looked up once and cached 10 minutes); merge request refs never count, so no VM boots for a job the runner would not take. Matching is provider-aware: a GitHub and a GitLab runner on the same path are separate records, and a GitHub connect never touches a GitLab record. Fork merge requests run on this Mac only when a member runs the pipeline in the parent project ([merge request pipelines](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/)); with protected only on, merge request pipelines do not run here at all.

**GitLab known limits.** GitLab has no single-use runner, so a job can read its own runner's `glrt-` token inside the guest; the runner is locked, protected-only by default, paused once busy and deleted after, so the token takes nothing after the first job. The access token (365 days by default) is not tracked for expiry; a lapsed token shows the runner as Error with a plain sentence. The desktop has no GitLab connect sheet yet (the channel and the TypeScript types accept it). Nothing has run against a live GitLab or a real guest.
