# Tooling & integrations

- **MCP client** `[shipped]`, connect stdio MCP servers **or streamable-HTTP endpoints** (a URL + optional bearer token, added via "+ Add URL" in Settings); their tools merge into the agent loop namespaced `mcp__<id>__<tool>`, with per-chat toggles and live status. A chat turn syncs and calls its MCP servers in the engine daemon, approvals included `[implemented 2026-10-12, PF14]`. Sub-agents (`spawn_agent`) are the daemon's too: it checks the delegation, creates and admits the child session, runs the child's turn, stops it with the parent, resumes it once after a transient failure and returns its answer `[implemented 2026-10-12, PF14; the delegation and the child chat moved from the TS host 2026-10-18]`. Verified against `@modelcontextprotocol/server-filesystem` (stdio) and a live Hypergate gateway (HTTP). An **MCP menu sits in the composer's instrument strip, just right of Tools**: it lists every configured server with a live status dot (connected / offline / checking), its name and transport, and an **enable/disable switch** (server enablement is global, so turning one on offers its tools to every chat); it probes live status on open, and offers **Add MCP server** (jumps to Settings) plus a recommendation to manage servers securely with the **Hypergate** app.
- **Hypergate integration** `[shipped]`, Nekko Agent pairs with [Hypergate](https://hypergate.app), the Nekko Labs MCP server runtime and manager, in one click from either side, and then runs it as a tab in this window.
  - **Detect.** Nekko Agent probes the local `hypergated` daemon at startup (in the engine daemon, so it works in every edition) and shows a card in Settings → MCP servers naming its version, its managed-server count, and its port. With no daemon running, a quiet **Get Hypergate** hint makes the companion discoverable without nagging.
  - **Connect (from Nekko Agent).** One click claims this install's own scoped agent token from the daemon, saves the aggregated gateway as a single MCP entry (every server Hypergate manages, one URL), brings its tools online in every chat, and opens the Hypergate tab. Re-connecting replaces that entry rather than adding a second.
  - **Connect (from Hypergate).** Hypergate's **Connect Nekko Agent** button opens `nekko-agent://hypergate/connect?port=N`, which brings Nekko Agent forward (launching it if it was closed) and runs the same flow. The link names a port and carries no credential: Nekko Agent reads the daemon's identity back over loopback and asks the user before connecting, because any local program can open a URL and a gateway's tools reach every chat.
  - **Scoped, not borrowed.** The token is Hypergate's own per-agent credential rather than the master gateway token, so the pairing is visible and governable from both sides: Hypergate's Agents list shows Nekko Agent online, with its own per-server permissions, usage history, and revocation.
  - **Hypergate as a window.** The manager's UI runs in a workspace window (`hypergate` pane kind) with the daemon's live version, server count, and connected agent in its header, so adding or auditing MCP servers never means leaving Nekko Agent. It says so and offers to reconnect when the daemon stops.
- **`nekko-agent` CLI + MCP server** `[shipped]`, run against a running server over HTTP+WS, or, with no app serving, on a private engine of their own (`[updated 2026-10-18]` nekkod on the data directory, started by the command and stopped when it ends, instead of the TS host in-process; it is found beside the installed app, in the npm package's platform dependency, or in a checkout's cargo build, and a machine without one is told why); `nekko-agent status|sessions|chat|mcp|watch`; `nekko-agent mcp` exposes Nekko Agent as an MCP *server* (chat/list/new/get/status) so other agents can trigger agents + swarms. Bundled into the npx package.
- **Local models from other agents** `[implemented 2026-10-15; unit-tested, end-to-end against a real llama-server on macOS arm64 (isolated data dir, in-process host); not yet exercised through the running app's API server, the engine daemon, Ollama/LM Studio providers, Windows or Linux]`, Claude Code, Codex or a script can ask Nekko to *run a model*, not only to answer with one already running. `nekko-agent mcp` adds `nekko-agent_local_status`, `nekko-agent_local_models`, `nekko-agent_model_search`, `nekko-agent_model_download`, `nekko-agent_downloads`, `nekko-agent_download_cancel`, `nekko-agent_model_load`, `nekko-agent_model_unload`, `nekko-agent_runtime_start` and `nekko-agent_runtime_stop`, and the CLI the matching `nekko-agent local status|list|search|download|downloads|cancel|load|unload|start|stop`.
  - **Acceptance:** from an MCP client, with nothing open but the engine binary installed, a caller can see the engine and its memory budget, download a catalog model (quantization `Q4_K_M` or the closest when none is named, an unknown one refused with the list of available ones), follow the download to done, load it (which starts the engine), get back the `provider`/`model` pair to pass to `nekko-agent_chat`, have that model answer, unload it and stop the engine.
  - **Boundaries:** these are the Model Server page's existing operations behind the same host channels, not a second implementation. They target the built-in engine unless a local runtime provider is named; a cloud provider is refused. Stopping a server Nekko Agent did not start returns `needsConfirmation` rather than killing it, and the caller must pass `force` after asking its user. Downloads come only from the Hugging Face catalog the app already uses. MCP callers are the user's own local agents with the same trust as the CLI, so there is no extra approval prompt for a download or load; the size is reported so the calling agent can ask first.
  - **Lifetime:** with the app serving, the CLI and MCP server are clients and the engine is the app's; a loaded model stays loaded after the caller exits. Without the app, `nekko-agent mcp` is the host: models it loads live for its session, and closing it (stdin end, SIGTERM/SIGINT/SIGHUP) stops the engine it ran so no llama-server is left holding memory. One-shot `nekko-agent local load|start` refuse without the app, because the model would stop when the command exits; one-shot commands also no longer auto-start the engine (`engine.autoStart`), which previously kept them from exiting once a model had been downloaded. An in-process `local download` waits for the download (and its companion files) to land.
  - **Known gaps:** an empty catalog search is indistinguishable from an unreachable Hugging Face in the host API, so the tool says both are possible and points to downloading by exact repo id. Engine install (`engine:install`) is not exposed: if no engine is installed, the status says why and the user installs it from the app.
- **Installed means set up** `[shipped 2026-09-28]`, installing the desktop app is enough for the CLI and MCP to work, with nothing to export or `npm install`. The **local API server is on by default** (loopback only, a token generated on first run). The app **ships the CLI inside itself** (one CommonJS file run by the app's own Electron, so no Node or npm is involved) and links an `nekko-agent` launcher onto PATH on first run (the user PATH on Windows, a marked shell-profile line elsewhere). The address and token go into a **link file** the CLI reads when no flag or env var says otherwise, stamped with the app's process id, so a terminal falls back to the local data directory the moment the app quits or crashes instead of dialling a dead port. **Onboarding pre-checks** every detected agent tool and adds Nekko Agent as an MCP server to the checked ones on Next (skip or uncheck to leave a config alone). Entries the app wrote are **kept current** when the port, address or token changes; entries written by hand are never touched. The **Server tab** owns the address, token and environment in one block: where it listens (this computer, the network, or a specific interface), the port, the **address clients are told to use** when that differs (a tunnel, a container port, a Tailscale name), the token, and copyable env lines for bash or PowerShell, masked on screen. The CLI tab shows whether the command is installed and on PATH, with Install/Reinstall, and the npm package stays the fallback for the web and self-hosted editions.
