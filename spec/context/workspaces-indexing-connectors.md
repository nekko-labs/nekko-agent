# Workspaces, indexing & connectors

- **Workspaces** `[shipped]`, multi-root folder add/remove/activate, chats bound to one primary workspace plus optional supporting workspaces so index + per-project memory engage across every selected folder while tools keep the primary as their working directory. The composer presents a chat's folders as its **Environment**, local folders plus repositories cloned from a connected GitHub or GitLab, and the agent asks when a project is missing `[implemented 2026-11-09]`: see [Chat environment](chat-environment-folders-and-repositories.md).
- **Indexer** `[shipped]`, workspace file tree, regex-based code outline, search; index-grounded context merged across a chat's selected primary and supporting folders.
- **Projects page** `[removed 2026-07-18]`, the dedicated Projects view (folder add/remove, index status, file browser) was retired to keep the rail focused. Folders are added from a chat's **+ → Folder** menu or the Context Inspector; files are browsed in the right panel's Folders accordions; the index keeps powering `@` file mentions and context under the hood.
- **Connectors** `[shipped]`, GitHub/Linear/Slack/Discord (token-based, real REST), Jira (site URL + email + API token) and Microsoft Teams (incoming webhook for posting, optional Graph token for reads) `[shipped]`, Gmail/Drive (paste an OAuth access token; one-click OAuth flow still pending Google client creds); connector snippets fed into context. **Official brand icons**: full-colour marks for multi-colour brands (GitLab, Slack, Jira, Teams' two-person mark, Gmail, Drive, Trello, Todoist, ClickUp, and Telegram on the messaging card); single-colour Simple Icons (CC0) for Discord and Asana; GitHub and Linear follow the theme ink so they stay visible in light mode `[updated 2026-10-17]`. **Layout** `[updated 2026-10-17]`: the Connectors tab fills the available width, with connector cards (and the Telegram messaging card) in a 1/2/3-column grid keyed to the view's own width (container queries, about 768px and 1152px); primary actions (Connect, Enable) sit at the card's right edge. Also **validate-on-connect**, Connect stores the token and immediately does a real fetch, surfacing a bad token as an inline error instead of silently "connecting"; each card links to where to get its token. **One-click setup** `[implemented 2026-11-10, #2492]`: each connector starts as one row with a single Connect button and no key field; pressing it opens the steps one at a time (1. a button that opens where to get the key, 2. the key field and any extra fields), and a key pasted in the shape the service uses (ghp_/github_pat_/gho_, glpat-, lin_api_, xoxb-/xoxp-, pk_, flp_) connects without another click. GitHub's step opens the new classic-token page with the name "Nekko Agent" and the repo + read:org scopes filled in; GitLab's opens its token page with the name and api scope filled in (on a self-managed instance's address when given). If the GitHub CLI is signed in on the computer, the GitHub row says so and Connect uses that sign-in in one click: the daemon runs `gh auth token` itself (`connectors:detect` returns only the account name, `connector:importCli` stores the token), so the token never reaches the UI; `connector:importCli` is never callable from a phone. Use a token switches to the token steps. Connected rows show a dot and the word Connected. Not yet: real OAuth one-click sign-in (it needs registered OAuth apps per service), prefilled pages for the other services, and reading a copied key from the clipboard without a paste. **Choosing repositories** `[implemented 2026-11-11, #2562]`: a connected GitHub or GitLab row shows a Repositories disclosure, closed by default, with the count it reaches ("4 of 7" once some are removed). Inside, repositories are grouped under their owner (a GitHub user or org, a GitLab top group), each group collapsible with its count (a single group opens by itself). Remove (on hover, always on touch) takes one repository out; Remove org takes a whole owner out; both move to a Removed group with Add back. The choice is what the app offers and reads, not what the token can reach: removed repositories are left out of Add repository (`repos:list`) and of the connector's chat context and sample fetch (GitHub's repository list and issue search, GitLab's project list), and a removed owner's future repositories stay out. Stored as lower-case lists `excludedRepos` / `excludedOwners` in the connector's `settings`, matched without case; `connector:exclude` writes only those two lists (never the token or the GitLab site), and `connector:repos` lists everything the token reaches, removed ones included, for the card. Neither channel is callable from a phone. A connected row's details stay collapsed: every connector's sample fetch (after connecting, or from Fetch sample) sits behind a Sample disclosure, closed by default with its count, and only a fetch error shows at once; GitHub and GitLab rows drop Fetch sample and leave repositories out of the sample, since the Repositories list already shows them. Acceptance: removing a repository or an org hides it from Add repository and context; Add back restores it; the token is untouched. Verified by unit tests (daemon filter, the save channel, grouping) and hidden-window captures against a stub bridge; not yet checked against a live GitHub or GitLab account. Not yet: the card lists one page of each provider (100 most recently updated), so an account with more sees only those; workflow listeners (`poll`) and actions are not filtered; Disconnect forgets the choice; GitHub's own fine-grained token access is not changed from here.
- **Nekko inside other agent tools** `[shipped]`, one-click install of the app as an MCP subagent into detected agent CLIs (Claude Code, Codex, Cursor, Windsurf): the app is already an MCP server (`nekko-agent mcp`), so connecting writes that server into the other tool's config (a backup is made first), and a copyable config snippet covers tools we can't write to. From then on Claude Code or Codex can hand Nekko scoped tasks, which run under this app's guardrails on this machine's models.
