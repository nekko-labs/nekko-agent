# Mode panel and saved modes (2026-10-17)

`[v1 implemented 2026-10-17: the panel, saved modes, a default mode for new chats, and every control backed by an existing setting. Phase 2 implemented 2026-10-17: per-chat effort, MCP servers and connectors in both engines. Skills per chat, system prompts, memory strategy and the model router are planned]` **User intent:** the composer's **Mode** button should open one panel that holds every setting that shapes how a chat runs, each with a line of explanation, and let the user save combinations as named modes, switch between them in one click, and pick one as the default for new chats. **What ships:** the button opens a panel with a rail of **saved modes** on the left and three columns of settings. *Environment*: Run on (Local machine or Sandbox, tiles) and Use worktrees (a switch, with a link to the git-worktree docs; off and explained in Sandbox). *Model*: Model router (coming soon) and Effort (tiles for the rungs the chat's model offers; sets this chat's `Session.effort`, with a link back to the app default). *Privacy*: Incognito, Internet access (locked on for a cloud model, as before), Folders (the chat's folders as chips with add and remove), Approvals (Ask, Guardrails, YOLO tiles; Sandbox always asks), Tools, MCP servers and Connectors (each opens a list out the panel's side). The MCP list switches each configured server on or off for this chat (`Session.disabledMcpServers`); a server off in Settings shows as off and cannot be switched on here, and the agent window's MCP menu still changes the app-wide enablement. The Connectors list shows the connected connectors with a per-chat switch (`Session.disabledConnectors`) and a link to the Connectors page. *Approach*: Skills (opens the work-mode list with the skills each applies; picking skills one by one is planned), System prompt and Memory (coming soon). Every setting and option has its own icon. **Saved modes:** a saved mode stores where the chat runs, worktrees, approvals, internet, incognito, disabled tools, work mode, effort, MCP servers switched off and connectors switched off (`SavedMode` in packages/shared/src/saved-modes.ts, kept in `AppSettings.savedModes`). Folders are never part of a mode. Until the user saves their own, the rail shows four starters (replaced 2026-10-22, see *Default modes: where the models run*): Cloud only, Fusion, Local only, Risky business. Clicking one applies all its per-chat settings, effort included, in a single `setSessionOptions` write; a mode saved before phase 2 that has no effort, MCP or connector fields leaves those as they are and matches any value for them; a mode that moves a chat into Sandbox opens the Sandbox setup dialog instead of moving it unasked. The header names the mode the chat matches, or *Custom*; a chat edited after applying a mode offers *Revert* and *Update "name"*, and any chat can be saved as a new mode. Starring a mode makes it the default: the host's `createSession` starts every new top-level chat in it (sub-agents keep inheriting their parent). With no starred mode, new chats keep the existing last-used defaults. **Per-chat effort, MCP servers and connectors (phase 2):** `Session.effort` wins over `AppSettings.effort` for that chat's turns (temperature, provider effort and the stats line); unset follows the app setting. `disabledMcpServers` drops those servers' `mcp__<id>__*` tools from the chat's tool list in `turnTools` / `turn_tools`; the servers keep running for other chats. `disabledConnectors` skips those connectors when a turn or the Context Inspector gathers connector context. The composer's Effort slider follows the chat too. All three are user fields a running turn does not overwrite, are copied by fork, and are inherited by `spawn_agent` children. The TS host and the Rust daemon share `chatEffort` / `chatMcpTools` / `chatConnectors` (shared/chat-scope.ts, nekko-turn scope.rs), held equal by the turn and store golden sets. **Boundary:** a saved mode is only a shortcut for settings that already exist; it grants nothing a user could not set by hand, per-chat switches only narrow what Settings allows (they never start a disabled server or reach a disconnected service), a cloud-model chat is never taken offline, and the Rust daemon's own session creation (automations) does not apply the default mode. **Not yet:** per-chat skill choice, a system-prompt library with view/edit links, memory strategies (incognito does not yet keep memory out of the prompt), the model router, and phone support. Design prototype: the Rail option chosen 2026-10-17.
