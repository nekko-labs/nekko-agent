# Context, guardrails & memory (the differentiators)

- **Context Inspector** `[shipped, restructured 2026-07-28]`, the right-hand panel, now **two stacked sections split by a draggable divider**, the way VS Code stacks its sidebar views:
  - **Folders** on top: each project folder is an accordion carrying what the agent may see (primary / supporting / excluded, promote-to-primary, remove) and expanding into that folder's **file tree**, so browsing and opening a file happens where you choose the context. Folders support one primary plus supporting roots, and the selection drives the chat's multi-root context.
  - **Context** below: Sources (attached files, SPEC.md, guideline/memory links) + Breakdown (live per-source token view, toggle/pin, headroom bar). The former Project context section is now **Guidelines**, above the Spec panel, with each guideline and memory entry individually enableable or disableable.
  - The split **gives and takes ground**: with every folder collapsed, Folders is content-height and Context owns the panel; opening a tree hands Folders the height you dragged it to, capped so Context always keeps a usable minimum, and the height you asked for is remembered rather than clamped away, so freeing space (collapsing the resource meters) returns it. The **Resources** dock at the foot is collapsible for the same reason, keeping its headline numbers in the header when closed.
  - The panel belongs to the **app**, not to any one window, so opening a file from the explorer doesn't take the explorer away with it; it follows the active chat and says so when there isn't one. Toggled from the workspaces sidebar or Ctrl/⌘+\. A workspace can also carry its own **file explorer as a window** (the `files` kind), rooted at a project folder and as many as the work needs, for when the folder belongs beside the work rather than on the far side of the screen.
  - Prefs persist per session and actually shape the prompt. **Both readouts move as you type**: the composer's context gauge and this panel's total, bar, and breakdown all count the unsent draft as a **Your message** source, so the cost of what you're about to send is visible before you send it rather than only after the reply lands.
- **Spec-driven development** `[shipped]`, first-class Kiro-style spec workflow built from the conversation. Pick a **methodology** (per-chat + global default): `spec-tasks` (**Spec → Tasks**, spec.md → tasks.md with no separate plan), `nekko-agent` (**Spec → Plan → Tasks**, spec.md → plan.md → tasks.md), `kiro` (requirements.md → design.md → tasks.md), or `lean` (single spec.md). Spec → Tasks is the default, while the other methodologies remain available. Each artifact has its own **Build/Update** button and is **chained** where the methodology provides earlier artifacts as context. When a chat has multiple context folders, the Spec panel **follows the primary folder** chosen in the Folders section right above it, and its own project select overrides that until the choice above moves again, so spec and tasks can be viewed, built, and toggled per workspace without ever showing one project's docs while the pane says another is primary. A "Build all from chat" button runs the whole pipeline. The **tasks artifact renders as an interactive checklist** whose toggles write `[ ]`/`[x]` back to the file, with a progress bar. Lives in the Context Inspector's Spec panel. A **Live** toggle keeps the primary spec rebuilt after every reply.
- **Guardrails** `[shipped; read-only allowlist implemented 2026-10-22, not yet released]`, the default permission mode. Since 2026-10-22 it auto-runs a shell command **only when every command in it is a known read-only one**; everything else asks. Before that it was a denylist (run anything no risky-command rule matched), and a review found that text the agent reads (a fetched page, a README, MCP output) could get `python3 -c "..."`, `curl -o /tmp/x https://...; sh /tmp/x`, `bash -c "$(curl ...)"`, `rm -r -f` or `cat .e''nv` run with no approval. **User intent (Philip, 2026-10-22):** guardrails must fail closed against prompt injection, so it moves from a denylist to an allowlist ([decision 0010](../../docs/decisions/0010-guardrails-mode-auto-runs-only-read-only-commands.md)).
  - **The read-only list:** `ls`, `pwd`, `cd`, `cat`, `head`, `tail`, `wc`, `file`, `stat`, `du`, `df`, `which`, `echo`, `printf`, `rg`, `grep`, `find`, `tree`, `sort`, `uniq`, `cut`, `diff`; `git` `status`, `diff`, `log`, `show`, `rev-parse`, `ls-files`, `blame`, `describe`, `branch` (listing only), `remote` / `remote -v`, `tag` / `tag -l`; on Windows `dir`, `type`, `where`, `findstr`, and in PowerShell `Get-ChildItem`, `Get-Content`, `Select-String`, `Get-Location`. Arguments that make one of these write or execute are refused: `find -exec/-execdir/-ok/-delete/-fprint*`, `rg --pre`, `sort -o/--compress-program`, `uniq in out`, `tree -o/-R`, `file -C`, git's global `-c`/`--exec-path`/`--git-dir` and `--output`/`--ext-diff`.
  - **How a command is read:** split into simple commands on `|`, `&&`, `||`, `;`, `&` and newlines, quotes removed, in the grammar of the shell that will run it (`/bin/sh`; `cmd.exe` for the bash tool on Windows; bash or PowerShell for Claude Code's tools). Anything it cannot read with certainty asks: command substitution, backticks and `$` expansions (`%` in cmd), output redirection other than `2>&1` or to the null device, input redirection, heredocs and process substitution, subshells and groups, cmd's `^`, PowerShell's `&` and script blocks, control characters, unterminated quotes. A leading `VAR=value` (PATH, LD_PRELOAD, DYLD_*) is not a read-only command, so it asks. Rules are matched against the command as written and again after quote removal, so `cat .e''nv` still hits the secrets rule and `d''d if=...` is still denied.
  - **Rules still apply on top:** a `deny` rule blocks in every mode, including YOLO; an `ask` rule asks; a user's `allow` rule lets the simple commands it matches run (each one checked on its own, so `npm test; rm x` still asks), but never shell syntax the reader refused. The default ruleset (destructive fs, force push, curl|sh, registry, privilege escalation, secrets) is unchanged; settings UI with a guardrails JSON editor. Each rule's **default** action is marked with a small dot on its allow/ask/deny control, and a **Reset to defaults** button at the bottom of the section (with a "N rules differ from the defaults" count) restores the shipped ruleset, dropping any custom rules. `guardrails:classify` (the command tester channel) returns the same decision the bash tool acts on, with a `not-read-only` or `shell-syntax` match explaining an ask no rule explains. Ask and YOLO modes are unchanged.
  - **Network reach:** `fetch_url` stays auto-allowed in Guardrails for the public internet, but a destination on this computer or the local network (loopback, RFC 1918, link-local including 169.254.169.254, CGNAT, unique-local, `localhost`, `.local`, `.internal`, `.home.arpa`) asks in every mode except YOLO, with a prompt that names the host; this is checked on the first URL, on every redirect hop, and in the client's own DNS resolver (no rebinding gap). When a proxy is configured for the URL (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`), the host is resolved locally to decide and the request then goes through the proxy, which resolves it again: on that path a DNS-rebinding answer between the two lookups, or a name only the proxy can resolve, is not caught. The browser tool's navigate prompt says when the address is local; the browser resolves and redirects on its own, so its approval is the gate.
  - **Acceptance:** every bypass above asks in Guardrails (`crates/nekko-tools/src/guardrails.rs` tests); read-only commands and pipes of them run; deny rules deny in all modes; the tools golden set records the new decisions; `fetch_url` to 127.0.0.1, 169.254.169.254 or a redirect into them returns a local-destination result until approved (`crates/nekko-web/tests/fetch_guard.rs`). **Git configuration** `[implemented 2026-10-22]`: a read-only git command runs whatever git's configuration names (`core.fsmonitor`, `diff.external`, textconv and filter drivers, hooks, pager), so in Guardrails writing git configuration asks (high severity) instead of being auto-allowed: anything in a `.git` directory or a `.git` file, a bare repository or worktree gitdir, `$GIT_DIR`, `~/.gitconfig`, the XDG git folder and `$GIT_CONFIG_GLOBAL`, links followed; Claude Code's Edit and Write prompts ask the same way. YOLO is unchanged. An auto-run command that runs git also gets `core.fsmonitor=false`, `core.hooksPath` set to the null device and `core.pager=cat` through `GIT_CONFIG_COUNT`, `GIT_PAGER=cat` and no `GIT_EXTERNAL_DIFF`. On Windows every command the agent runs gets `NoDefaultCurrentDirectoryInExePath=1`, so `cmd.exe` does not run a workspace `git.bat` in place of `git` (PowerShell never searches the current folder). Acceptance: `crates/nekko-tools/tests/git_guard.rs` (a write to `.git/config` asks; the hardened environment reaches auto-run git; a planted `core.fsmonitor` does not run on an auto-run `git status`). **Known limits:** `diff.external` has no value that disables it and git has no switch for textconv or filter drivers, so those rely on the write gate; a git `include.path` the user already points at a workspace file, and commands Claude Code runs (started by Claude Code, not Nekko), get no environment hardening.
- **Workspace jail** `[shipped; links resolved 2026-10-15]`, the default sandbox mode (Settings → Sandbox) confines the file tools (`read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`) to the chat's added folders; a path outside every folder is refused with a message that names the folder to add or the mode to switch. Since 2026-10-15 the check follows links as well as strings (#550): after the normalized-path comparison, the deepest existing ancestor of the target and of each workspace folder is resolved on disk (symlinks on Unix, symlinks and junctions on Windows), so a link inside a workspace that points outside it is refused even though its path reads as inside, while a link to another added folder stays allowed. A file that does not exist yet is judged by where its nearest existing parent really is. The TS host and the engine daemon (`crates/nekko-tools`) apply the same rule, held together by the tools golden set, which creates such a link at test time on each platform. `bash` and background processes remain unconfined by this mode, as before.
- **Memory** `[shipped; per-chat scope 2026-10-22]`, markdown memory store (global + per-workspace) with CRUD and a manager UI. Each chat reads everything, only its folders' notes, or none (Mode panel → Memory); an incognito chat reads none.
  - **The agent remembers what it learns about you** `[implemented 2026-10-23; not yet tried against real models]`. A chat that reads global memory offers the agent a `remember` tool: when it learns something durable about the user (who they are, preferences, how they like to work), it saves one fact per global note with a short title. Saving under an existing title (ignoring case) replaces that note, so a correction does not leave the old fact beside it. Never offered in incognito, memory-off or folders-only chats, sub-agents, goal runs or a workflow whose tool access leaves it out. The description tells the model never to save secrets or credentials; nothing enforces that beyond the model.
  - **A card in the chat for every save.** Each successful save shows a card under that turn's steps, outside the folded step list, so a finished transcript still shows it: *Memory added* or *Memory updated*, the note's title, the first lines of what was saved, and **View in Memory**, which opens the Memory tab on that note. While the Memory tab is off (it is still experimental) the link reads *Turn on Memory to view* and opens Settings. A failed save shows no card; its error stays in the step. Saves made inside a code-mode script get no card yet (a script's calls are not transcript rows).
