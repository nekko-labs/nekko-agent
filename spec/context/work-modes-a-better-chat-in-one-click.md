# Work Modes: a better chat in one click (2026-10-17)

`[v1 implemented 2026-10-17: prompt-level work modes in the Mode menu; engine-enforced phases, on-demand skill loading and the evaluation gate are still planned]` **What ships in v1:** the composer's **Mode** menu has a third column, **Work mode** (Default, Better review, Design, Best output), beside Execution and Permissions. Choosing one sets `workMode` on that chat only (`setSessionOptions`; never a saved default, never `mode`), shows it on the button (*Worktree - YOLO - Better review*), and from the next turn adds the mode's instructions plus the text of its skills to the system prompt (`WORK_MODES` / `workModePrompt` in packages/shared/src/work-modes.ts). Both engines send the same words: the TS host's `turnSystemPrompt` and the daemon's `turn_system_prompt` read the same text from the turn catalog, checked by the turn golden set. Default, absent and unknown ids add nothing. The text states that it changes no permissions, tools or guardrails; a test keeps any mode from mentioning YOLO or skipping approval. Verified by unit, component and golden tests and hidden renderer captures; not yet measured against the plain chat (see acceptance below), not yet offered on phones (`workMode` is not in the phone allowlist). Original design: [reports/modes.md](reports/modes.md). **User intent:** users forget which skills exist and when to invoke them, so a chat should improve with one click (for example *Better review*, *Design*, *Best output*) without the user typing or remembering any skill. **Decisions:** a work Mode is a per-chat harness recipe (phases, roles, per-role models, budget, and which skills apply where), run by Nekko's own engine; its content is adapted from proven public skill packs with attribution and license checks, not installed wholesale. Skills activate in three ways: *always* (tiny, for the whole chat), *phase-bound* (injected by the engine when a phase starts) and *model-chosen* (only name and description in the prompt, full text loaded on demand). Anything a Mode promises must be always-on or phase-bound, never left to the model remembering. Enabling a Mode installs the skills it needs; the `/` menu remains for manual extras. **Boundary:** a Mode never changes the permission mode (Ask / Guardrails / YOLO), disabled tools, Offline, Incognito, connectors or guardrail rules, and its sub-agents inherit the chat's ceiling; a "different model" for a critic never moves a local-only or Offline chat to a cloud provider. The session field is distinct from the existing permission `mode`. **Acceptance (when built):** one click enables a Mode for a chat; its phase and loaded skills are visible in the transcript; its expected extra cost is shown before enabling; a Mode ships only after it beats the plain chat on its own fixed evaluation set (Better review: seeded-bug precision/recall; Design: blind pairwise preference). First Modes: Better review, then Design. **Open:** the UI name (it collides with the permission "mode"), the default, and community-made Modes.
